## 1. 背景与问题

邮轮是 5000 人级封闭空间，餐厅、剧院、泳池、儿童俱乐部等公共空间容量固定、无法临时扩容。公开证据显示：

- 餐饮：自助餐高峰期“抢食”、排长队、找不到座位；免费餐厅供给与口味不足；部分乘客愿意通过付费升舱/换方案避开排队。
  - 来源：`01-dining-crowd.md`（PB，7+ 独立源 Strong）
- 娱乐/公共空间：热门节目需抢座、泳池拥挤、活动排队严重；预约制和先到先得都不是银弹。
  - 来源：`05-entertainment-public-space.md`（PO/N16，国际 Strong + 中国侧已闭合）

现有信息系统（预订/账单/预约）彼此割裂，App 没有实时拥挤度或排队时间展示；船员主要靠巡场目测、对讲机确认、广播通知，信息滞后且无法定向触达。

## 2. 产品定位

**一句话**：实时感知船上餐厅与公共空间占用状态 → 确定性计算各空间满载率/排队/等待时间 → AI 生成替代推荐与话术 → 船员审批后通过既有渠道触达乘客，让乘客“少排队、不错过、不白跑”。

**非目标**：
- 不做 C 端乘客 App 本体，只输出接口与推荐内容；
- 不建设船载屏/硬件终端；
- 不做消费引导/付费推荐（策略配置仅预留扩展位）；
- 不管理船岸交汇点（港口、海关、岸上游）。

## 3. 功能模块

### M1 全船公共空间状态感知（确定性层）

- **输入**：摄像头客流计数（仅计数不识别）、预订/POS 数据、活动日程/票务数据（Demo 可模拟数据源）。
- **输出**：餐厅/剧院/泳池/儿童俱乐部等空间的满载率、排队人数、预计等待、剩余容量、短时趋势。
- **规则**：计数/排队/等待/步行时间全部确定性计算；LLM 不参与算术。

### M2 分流与替代推荐（AI 建议层）

- **餐饮**：满载率超阈值 → 推荐替代餐厅（结合口味/距离/等待）→ 分批触达。
- **娱乐/公共空间**：热门场次/区域容量不足 → 推荐替代活动/时间场次 → 船员确认后触达。
- **AI 角色**：LLM 只做三件事——结构化数字翻译成人话、按乘客分群生成不同推荐理由、解释推荐依据（证据卡片）。
- **关键机制**：分批去重，避免把所有人引导到同一处。

### M3 船员调度台

- **核心 UI**：
  - 全船公共空间热力总览；
  - 建议卡片（每条附证据：数据来源、计算公式、推荐理由）；
  - 审批队列；
  - 事件/预警工作台。
- **关键机制**：证据抽屉 + 审计包，每个动作可回溯“读了哪条数据、算了什么公式、谁批准”。

### M4 触达输出（接口层）

- **输出渠道**：船公司既有乘客 App、船载屏、船员端。
- **输出物**：结构化建议 JSON（场景/目标空间/预计等待/话术/时间窗）+ 触发规则（何时推、给谁推、频控）。
- **Demo 边界**：可用静态/模拟视图展示触达效果，不建设 C 端 UI。

## 4. 跨模块规则

| 规则 | 内容 |
|---|---|
| R1 确定性保底 | 计数/排队/时间窗/安全约束全部确定性计算，LLM 不参与算术 |
| R2 分层降级 | LLM 不可用 → 规则推荐；感知不可用 → 上一快照 + 标注 |
| R3 审批门 | 写操作/全量推送必须经过审批，执行路径不经 LLM |
| R4 证据可追溯 | 每个建议/动作带证据抽屉与 trace_id |
| R5 分批去重 | 推荐数量受目标空间容量约束，防羊群效应 |
| R6 仅计数不识别 | 摄像头数据不做个体识别 |
| R7 Demo 红线 | 可 mock 数据源，不可 mock 计数/推荐核心逻辑；MOCK_MODE/REAL_MODE 显式分离 |

## 5. 边界与接口

| 角色 | 已有系统 | 我方接口 |
|---|---|---|
| 信息源（读） | 摄像头客流计数；预订/POS；活动票务系统 | 标准化数据接入 |
| 执行端（写） | 船司乘客 App/船载屏；船员端 | 推荐 JSON/消息输出 |
| 扩展预留 | 船上餐饮/娱乐调度未来可对接“港岸协同与航变响应系统（B 线）” | 空间状态事件订阅接口（B 线预留） |

## 6. 非功能要求

- **性能**：感知→建议闭环 ≤3 分钟（船载局域网内）。
- **离线**：船载边缘推理 + 本地小模型降级；卫星链路仅异步增强。
- **合规**：隐私（仅计数不识别）；船载网络安全边界。
- **安全**：审批门代码级实现；审计日志不可篡改。
