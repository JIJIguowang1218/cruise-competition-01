## 一、产品定义

### 一句话

**邮轮智能分流系统**——用船载摄像头+AI实时感知各区域人群密度，动态引导乘客前往空闲区域，消除排队、缓解拥挤、提升全船体验。

### 解决的核心问题

邮轮是一个"5000人同时存在、资源固定、无法扩容"的封闭空间。当3000人同时涌向3个免费餐厅时，不是"服务差"的问题——是物理规律。船不能加餐厅、不能加座、不能让午餐时间延长3小时。唯一能做的是：**把人从拥挤处引导到空闲处**。

这不是"推荐系统"。这是一个实时空间调度问题。

## 二、用户画像与三问分析

### 谁会用这个产品？

| 角色 | 使用场景 | 核心需求 | 使用方式 |
|------|---------|---------|---------|
| **乘客**（第一用户） | 午餐时间不知道去哪吃、排队排到烦、不想挤 | "告诉我哪里不挤、怎么走" | 手机App/船载屏幕看到实时热力图+推荐 |
| **船员（运营）**（第二用户） | 管理餐厅、泳池、剧院等区域的客流 | "帮我看到全船哪里在堵" | 船员Dashboard看到全局热力图+预警 |
| **邮轮公司**（买单者） | 降低投诉率、提高NPS、优化运营 | "让乘客更满意、少投诉" | 看运营数据报告 |

### 用了之后能省什么/赚什么？

| 指标 | 当前 | 目标 | 依据 |
|------|------|------|------|
| 餐厅高峰期排队时间 | 15-30分钟 | 减少50% | 钛媒体报道"餐厅内人满为患" |
| 投诉率（排队/拥挤相关） | — | 下降30% | 钛媒体报道"服务下降"与拥挤直接相关 |
| NPS | — | 提升5-10分 | 体验优化的核心指标 |
| 船员处理客流问题的时间 | 每天2-3小时 | 减少70% | 解放船员去做高价值服务 |

### 为什么是现在？

1. **技术上**：计算机视觉（YOLO/OpenCV）的人流计数可支撑实时决策（注：旧文"精度 95%+"出处无法复现，见批3 07 流；精度需原型实测）。LLM 的语义推理能力（Gemini 2.5/3.0）可以生成自然语言建议而非冰冷数据。
2. **业务上**：新船设计阶段可以规划摄像头布点和船载屏幕位置——这是前装优势，不是改造痛点。
3. **市场上**：钛媒体报道证明排队/拥挤是中国邮轮乘客最大痛点之一，不是我们凭空想象。

## 三、场景叙事——Demo剧本

> 借鉴 **Globot Shield** 的"4:55PM危机"预写场景模式。不依赖实时AI生成，用精心设计的场景承载所有能力展示。

### 场景：11:45 AM 午餐高峰

**画面开场**：邮轮App主屏，顶部横幅"午餐时间！当前拥挤度"

**第1幕：感知**
- 三个免费餐厅的摄像头画面（模拟），AI实时计数
- 主自助餐厅：红色 🔴 92%满载，排队约25分钟
- 船尾自助餐厅：黄色 🟡 78%满载，排队约10分钟  
- 三楼意式餐厅：绿色 🟢 45%满载，即刻入座

**第2幕：决策**
AI推理链逐行展示（借鉴Synt的"推理剧场"）：
> 🧠 分析中...
> - 主自助餐厅满载92%，剩余座位47个，排队人数89人
> - 船尾自助餐厅满载78%，剩余座位84个，排队人数23人
> - 三楼意式餐厅满载45%，剩余座位112个  
> - 您当前位置：7层客舱，步行至船尾餐厅约3分钟、意式餐厅约5分钟
> - 您的偏好标签：中式餐饮 > 西式（从历史消费推断）
> - 建议：船尾自助餐厅，步行3分钟，当前排队10分钟，提供中式面档

**第3幕：推送 + 行动**
- 乘客App弹出卡片："船尾自助餐厅现在有位，步行3分钟→"
- 点击后显示甲板导航路线图
- 乘客到达船尾餐厅后，系统自动识别（通过WiFi/蓝牙定位）并更新状态

**第4幕：结果**
- 15分钟后，主自助餐厅满载降至75%
- 系统记录：本次分流减少主餐厅排队时间约8分钟
- 乘客满意度评分弹窗

## 四、技术架构——借鉴Hackathon成功模式

### 4.1 整体架构：AI感知 + 确定性计算分离

> 直接借鉴 **Spatial Engine** (B+/61) 和 **Scam Swarm** (A/84) 的核心模式。

```
┌─────────────────────────────────────────────────┐
│                   感知层（Perception）              │
│  船载摄像头 → YOLO/OpenCV人头计数                  │
│  WiFi/蓝牙定位 → 乘客位置追踪（脱敏）                │
│  餐厅POS系统 → 当前容量/翻台率                      │
└────────────────────┬────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────┐
│              规则引擎层（Deterministic）            │
│  > 借鉴 Scam Swarm 的启发式引擎                    │
│  - 阈值触发：区域满载 > 80% → 触发分流              │
│  - 容量计算：可用座位 / 排队人数 → 等待时间           │
│  - 步行时间：位置坐标 × 甲板图 → 路径距离             │
│  - 安全约束：消防通道不推荐、SOLAS区域限制            │
└────────────────────┬────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────┐
│              AI推理层（Semantic）                  │
│  > 借鉴 Scam Swarm 的 LLM语义层                   │
│  - 乘客偏好匹配：历史消费 → 推荐餐厅类型              │
│  - 自然语言生成：数据 → "船尾餐厅步行3分钟，人少"     │
│  - 时序预测：当前趋势 → "30分钟后这里会空"            │
│  - 去重优化：避免把所有人引导到同一区域                │
└────────────────────┬────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────┐
│              OODA自主循环（Synt A/87）              │
│  观察→判断→决策→行动→再观察                          │
│  每3分钟重新扫描，动态调整建议                        │
└─────────────────────────────────────────────────┘
```

### 4.2 为什么用双层架构而不是纯AI？

| 纯AI方案 | 双层架构（规则+AI） |
|---------|-------------------|
| 让Gemini看摄像头图片→判断拥挤→推荐 | 规则引擎做精确计数和阈值判断 |
| 可能把"红色墙壁"误判为"人群" | 规则引擎用计数而非推理，不会错 |
| API调用延迟2-3秒 | 规则引擎毫秒级响应 |
| 每次推理成本高 | 只有语义建议部分调用LLM |

这正是Scam Swarm的核心设计哲学：**规则引擎做精确匹配，LLM做语义理解，各取所长**。

### 4.3 多Agent但职责单一

> 借鉴 **Globot Shield** (A/81) 的多Agent模式。每个Agent职责清晰，评委3分钟能理解。

| Agent | 职责 | 借鉴自 |
|-------|------|--------|
| **感知Agent** | 摄像头计数+定位数据融合 | — |
| **评估Agent** | 规则引擎：阈值触发+容量计算 | Scam Swarm启发式引擎 |
| **推荐Agent** | LLM：偏好匹配+自然语言生成 | Scam Swarm LLM层 |
| **调度Agent** | 去重+分批推荐（避免把人群引导到同一处） | Synt OODA循环 |

反模式警示：不是为了"多Agent"而贴5个Agent标签——每个Agent有独立的输入输出和运行逻辑。

### 4.4 预写场景 + High-Fidelity Mock

> 借鉴 **Globot Shield** 的Demo策略。

- Demo中摄像头画面用预录视频（不是实时）
- 人群计数用确定性脚本（每次演示结果一致）
- 只有LLM生成的推荐文本是真实调用的
- 评委看到的是"产品逻辑真实+数据mock"

这和Globot的"Financial Hedge公式是真活、数据源是mock"策略一致。

## 五、AI能力边界分析

### AI擅长的（我们用它做这些）

| 能力 | 用法 | 置信度 |
|------|------|:--:|
| 模式识别 | 从消费历史推断乘客餐饮偏好 | 高 |
| 自然语言生成 | 把"78%满载/排队10分钟"变成"船尾餐厅人少，步行3分钟到" | 高 |
| 时序预测 | 根据当前趋势预测"30分钟后这个区域会空出来" | 中 |
| 多模态融合 | 综合摄像头+WiFi+POS多源数据做决策 | 高 |

### AI不擅长的（我们用确定性方法）

| 能力 | 为什么不让AI做 | 用谁做 |
|------|---------------|--------|
| 精确人头计数 | CV模型可能误判 | OpenCV/YOLO（成熟的CV方案） |
| 步行时间计算 | LLM不擅长空间计算 | 甲板图坐标+曼哈顿距离公式 |
| 消防/安全约束 | 安全规则必须100%正确 | 硬编码规则（借鉴AMRShield规则引擎） |
| 隐私保护 | AI可能泄露个人信息 | 预处理：数据脱敏后再给AI |

### 邮轮特有的AI边界

| 约束 | 影响 | 对策 |
|------|------|------|
| **网络离线** | 卫星网络延迟2-5秒，不能实时依赖云端AI | 摄像头→本地NUC推理→船上WiFi推送，不依赖卫星 |
| **隐私** | 不能识别人脸、不能追踪个人行踪 | "仅计数不识别"、位置数据脱敏、乘客可选择退出 |
| **安全** | 不能引导乘客去限制区域 | 规则引擎内置SOLAS/消防通道约束 |
| **误判代价** | "推荐去A餐厅结果满座"会让乘客更不满 | 推荐前先确认（借鉴DQ Sentinel的审批门模式） |

## 六、从Hackathon作品中学到的具体点子

### 🟢 可直接套用的

| 点子 | 来源 | 怎么用 |
|------|------|--------|
| **规则引擎触发 + LLM解释** | Scam Swarm (A/84) | 摄像头检测到>80%→触发→Gemini生成推送文本 |
| **High-Fidelity Mock Demo** | Globot Shield (A/81) | 用预写场景做演示，确保每次演示一致可靠 |
| **推理过程透明化** | Synt (A/87) | 乘客看到"正在分析全船人群分布..."而非黑箱结果 |
| **AI感知+物理计算分离** | Spatial Engine (B+/61) | 人头计数用CV、步行时间用公式、偏好推荐用LLM |
| **分步工作流** | DQ Sentinel (A-/76，评分已更正) | 感知→评估→推荐→推送→验证，每步都可中断 |

### 🟡 改造后可用的

| 点子 | 来源 | 怎么改造 |
|------|------|---------|
| **审批门模式** | DQ Sentinel (A-/76) | 不是人审批AI，是AI确认"推荐的区域真的有空位"后再推送 |
| **双AI引擎热切换** | Scam Swarm (A/84) | 如果Gemini API超时，降级到纯规则引擎推荐（"3楼有空位"而非个性化推荐） |
| **管道+人类校验** | Voiceless Voice Agents (A/75) | 在Demo中展示"船员看到AI建议后点确认"的过程 |
| **渐进式揭示动画** | CityGuard (C/45) | CityGuard在UI上做得极好——但注意：内容必须是真实的 |

### 🔴 必须避免的

| 反模式 | 来源 | 为什么 |
|--------|------|--------|
| **做假Dashboard** | CityGuard (C/45) | 如果热力图是硬编码PNG，评委一眼看穿 |
| **贴Multi-Agent标签** | NeuroStudy (C/52) | 不要声称4个Agent协作但实际是同一个prompt |
| **MCP标签** | MallCore (C/45) | 不要说"摄像头MCP"——说摄像头做了什么 |
| **1次提交** | CityGuard/NeuroStudy | 用小步提交展示开发过程 |

## 八、风险与对策

| 风险 | 概率 | 影响 | 对策 |
|------|:--:|:--:|------|
| 产品太薄——"人多→告诉你人少"没有技术含量 | 中 | 高 | 加入时序预测层+偏好匹配层，从"告警"升级为"决策支持" |

| 隐私顾虑 | 低 | 中 | 明确标注"仅计数不识别"，Demo中加入模糊化处理演示 |
| 摄像头部署依赖前装 | 中 | 低 | 方案定位为新船设计，前装恰恰是优势 |
| 评委认为"这不就是个导航App" | 中 | 高 | 强调实时性（3分钟循环）、预测性（10分钟后预测）、系统性（多源融合） |
