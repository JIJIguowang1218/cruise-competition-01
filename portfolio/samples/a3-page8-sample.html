Multi-Agent Architecture

不是多个 Agent 贴纸，而是有分工、有通信、有回路的决策架构。

ClarSyn 的多 Agent 架构不是“同一个 LLM 调五次”，而是把航变响应拆成 11 个职责单一的模块，每个模块有独立输入、输出、状态和回滚边界，再通过结构化接口串成完整决策链路。

为什么需要多 Agent，而不是一个大模型

邮轮航变响应涉及气象、船期、港口、客服、条款、资源等多个领域。如果让一个大模型从头到尾自由发挥，很难保证每一步都引用正确数据、计算正确影响、并且在审批前留下可审计证据。多 Agent 的价值不是“看起来智能”，而是把复杂链路拆成可验证、可回滚、可审计的环节：每个模块只做一件事，但必须把这件事做完整。

11 个核心模块

1
多源事件接入统一气象、船期、港口、客服信号，输出标准化事件对象。
2
事件分类与严重度判断事件类型、等级与影响范围，决定后续路由。
3
库外异常识别发现未收录的弱信号组合，生成提醒卡，只提醒不执行。
4
确定性计算内核排队、时间窗、影响人数、资源缺口全部用确定算法，不交给 LLM。
5
知识检索 RAG检索策略、条款、事故模式，返回可引用原文。
6
方案组合与推演按事件→影响→资源→方案顺序，组合可审批候选方案。
7
推理附件生成为每个判断生成结论、置信度、证据链与替代方案。
8
证据与置信度检查低信度、证据不足、规则冲突时强制转人工。
9
权限路由与审批门按 L1–L4 路由，所有写操作必须过审批门。
10
执行触达按投放审核矩阵核准级别，输出到各触达渠道。
11
审计与事故记忆append-only 记录并回写事故模式记忆库。

模块之间如何通信与编排

模块之间通过结构化事件对象通信，而不是自由文本。每个模块只读取自己需要的字段，输出固定 Schema。主链路是顺序执行：接入 → 分类 → 计算 → 检索 → 推演 → 附件 → 检查 → 审批 → 触达 → 审计。库外异常走旁路，直接生成提醒卡并按 L1–L4 路由；超时未审批会回流到审批门；审计结果会回流到知识检索，形成“事故模式记忆”。这种设计保证每个环节都能单独回滚、单独测试、单独审计。

Agent Loop
O
Observe：接入气象、船期、港口、客服信号。
O
Orient：分类、异常识别、态势整合。
D
Decide：影响推演、预案组合、推理附件。
A
Act：审批、触达。
L
Learn：审计回写事故模式记忆库，持续优化。
每个模块输入输出独立，可回滚、可审计；不是“一个 Agent 干所有事”。
