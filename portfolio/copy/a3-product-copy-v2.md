## 第 3 页：一页看懂

**主标题**
ClarSyn：邮轮港岸协同决策层。

**正文**
邮轮公司在登离船、港口接驳、航变响应三个场景中长期依赖人工拼图。信息分散在船司、OTA、港口、客服、天气等多个系统中，关键决策靠人现场汇总，导致响应慢、口径不一、难以追溯。ClarSyn 的目标不是替代人，而是把“信息搜集、影响判断、预案准备”这些重复且高强度的认知工作交给系统，让人专注于审批和最终决策。

ClarSyn 的价值体现在四个层面：

1. **快速调用多源 API 与系统数据**：把气象、船期、港口、客服信号汇成统一态势，避免决策者在多个系统之间人工搬移信息。
2. **接收外部航变决定、识别下游影响性弱信号**：航变预警与航变决定由外部体系负责（气象/海事发预警、船公司决定、船长安全确认）；ClarSyn 在决定成立后识别”单独看正常、组合起来可疑”的下游影响信号（登离船/接驳/时间窗连锁），提前给出影响推演与预案。
3. **自动完成影响推演与预案准备**：基于事件分类、影响人数、资源缺口和策略库，生成可审批的候选方案，而不是让人从零开始推导。
4. **全链路审计**：每个判断都附带证据、置信度、审批记录与执行回执，让“AI 为什么这么建议”可以被追问和复核。

**关键数据**
- 人工拼图：20–45 分钟 `[待验证]`
- 航变响应传统逐批沟通：8 名客服连续 5h+ `[待验证]`
- 系统目标：感知→建议→审批任务生成 ≤3 分钟

## 第 4 页：问题定义——船↔岸交界为什么难

**主标题**
三处断裂：登离船、港口接驳、航变。

**正文**
邮轮乘客在“船↔岸”交界处体验断裂最明显，而这些问题不是单一部门能解决的。它们共同指向一个核心：关键运营信息分散，决策层缺乏统一、实时、可预测的态势。

**问题一：登离船动态不可见**
登船日同一时段集中到达，排队长度不可见；离船日靠广播/纸质通知分层下船，乘客不知道自己的准确时间窗。根据证据线 A，从停锚到码头约 1 小时，分层下船再等近 3 小时。现有方式不是没有流程，而是流程依赖人工广播和纸质通知，无法根据港口实际状态动态调整。

**问题二：港口接驳信息静态**
官方接驳信息以静态 PDF 为主，乘客不知道出租车、网约车、短驳分别要等多久。宝山区政府连续两年承认交通秩序问题，出租车拒载/宰客现象多次被报道。这说明问题不是单一公司能解决的，而是需要船方在信息层面向乘客提供更透明的接驳建议。

**问题三：航变响应靠人工拼图**
事件发生后，通知链存在多层衰减；口径不一致，乘客在信息真空中产生不信任。2026 台风“白海豚”事件导致数百人拒下船。航变场景的难点不仅在于通知，更在于事件发生后需要快速判断影响范围、资源缺口、条款依据和替代方案，而这些都是跨系统信息整合问题。

**结论**
现有系统是“人工拼图”，不是“决策系统”。ClarSyn 的目标是把决策准备从小时级压缩到分钟级，并让每一次判断都有依据、有审批、有留痕。

## 第 5 页：价值场景对比——登离船 / 港口接驳 / 航变

**主标题**
同一套系统，三个场景，都从“人肉拼图”变成“分钟级决策”。

**场景 1：登离船动态调度**
- 现状：固定批次、广播/纸质通知、排队不可见；乘客和船员都无法提前感知整体压力。
- ClarSyn：通过接入船期、泊位、乘客清单和可获得的码头状态，生成动态时间窗；当码头状态变化时，自动调整批次并定向触达。
- 提升：决策准备时间从小时级压缩到分钟级；乘客获得更准确的时间窗，减少现场聚集和等待。

**场景 2：港口接驳协同**
- 现状：官方信息是静态 PDF，乘客不知道出租车、网约车、短驳分别要等多久；现场引导压力大。
- ClarSyn：把港口静态资料与船期、离船批次结合，生成可执行接驳建议；在无法获得实时数据时退回静态指引，并显式标注信息边界。
- 提升：减少乘客滞留不确定性，缓解现场引导压力，降低投诉与纠纷。

**场景 3：航变响应**
- 现状：事件发生后靠人工逐批沟通，预测与预案准备几乎空白；客服和船员在信息不完整的情况下承担解释压力。
- ClarSyn：快速调用气象、船期、港口、客服 API，发现航变/气象弱信号，提前生成影响预测与应变预案；再进入 L1–L4 审批与统一触达。
- 提升：把“事后解释”变成“事前预测 + 预案准备 + 快速决策”，让船长在决策窗口内看到选项，而不是等人拼好信息再拍板。

**ROI 口径**
不做货币化，用“相对量级 + 显式假设”表达。例如航变响应中，客服高峰人力小时数下降、决策准备时间压缩一个量级等，均为待船司真实数据校准的假设。

## 第 6 页：用户、角色与产品边界

**主标题**
给谁用？管什么？不管什么？

**核心用户与任务**
- 船长：需要基于多源信息的拍板依据，而非等待人工汇总；在高后果事件中需要看到“证据、置信度、替代方案”。
- 运营经理：需要分钟级态势与预案选项；负责日常调度与跨部门协调。
- 值班/客服：需要统一事实与条款依据；避免逐个人工解释产生口径偏差。
- 法务：需要可审计的决策链路；当赔偿或合规问题出现时，能够回溯每个判断的依据。

**产品边界**
- 管：船方触达渠道、船司内部调度、可合法获取的气象/港口/船期数据。
- 不管：不指挥海关/边检/港调/交管；不替代港口或口岸系统；不处理不在船岸调度范围内的客服事件。

**数据可用性**
按“可用 / 待接入 / 不可得”分层管理。主文档直接呈现产品能力，不反复强调模拟数据；数据边界与接入状态进入附件说明。

## 第 7 页：系统架构总览

**主标题**
感知 → 决策 → 触达，分层清晰。

**架构分层**
- 感知层：港岸状态感知，接入气象、船期、港口、客服等多源数据；负责把外部信息标准化为系统可处理的信号。
- 决策层：包含登离船调度、港口接驳、航变响应、运营调度台；这里完成事件分类、影响计算、预案组合、审批路由。
- 触达层：面向乘客 App、船载屏、广播、船员端输出统一触达内容；所有触达都带有 trace_id，可回溯到事件和审批。

**部署形态**
- 船载边缘：实时闭环，保证离线可用；排队、时间窗、影响人数等确定性计算全部在边缘完成。
- 云端：异步增强；长文档解析、法规更新、模型更新等非实时任务放云端。
- 卫星：仅异步同步；不承担实时决策链路。

**关键原则**
能规则不用 ML；能用小模型不用大模型；能离线不用云端。这个原则保证系统在海上网络不稳定时仍然能完成核心闭环。

## 第 8 页：多 Agent 架构与 Agent Loop

**主标题**
不是多个 Agent 贴纸，而是有分工、有通信、有回路的决策架构。

**核心模块**
1. 多源事件接入：把气象 API、船期、港口、客服信号统一标准化。
2. 事件分类与严重度判定：判断“发生了什么、严重吗、属于哪类事件”。
3. 库外异常识别：对未收录的弱信号组合生成提醒卡，只提醒不执行。
4. 确定性计算内核：排队、时间窗、影响人数、资源缺口全部用确定算法。
5. 知识检索 RAG：从策略库、条款库、事故模式记忆库中检索已有方案。
6. 方案组合与推演：事件 → 影响 → 资源 → 方案，形成完整决策链路。
7. 推理附件生成：每个方案附带结论、置信度、证据链与替代方案。
8. 证据与置信度检查：低信度或证据不足时强制转人工。
9. 权限路由与审批门：L1–L4 分级，写操作/高后果动作必须过审批。
10. 执行触达：按投放审核矩阵核准级别后输出。
11. 审计与事故模式记忆：append-only 审计并回写记忆库，支持下一次预测与预案。

**Agent Loop**
- Observe：接入气象、船期、港口、客服信号。
- Orient：分类、异常识别、态势整合。
- Decide：影响推演、预案组合、推理附件。
- Act：审批、触达。
- Learn：审计回写事故模式记忆库，持续优化。

**编排规则**
- 顺序主链路 + 库外异常旁路 + 超时升级回流 + 审计回流。
- 每个 Agent 输入输出独立，可回滚、可审计；避免“同一个 LLM 调五次”的贴纸式多 Agent。

## 第 9 页：审计与追溯体系

**主标题**
每个判断都能回答：依据了什么、谁批准的、执行了什么。

**追溯链**
trace_id：事件 → 建议/推理附件 → 审批签署 → 端口执行日志 → 审计包。

**机制说明**
- append-only + 哈希链防篡改：一旦写入，不能修改或删除；每条记录通过哈希链连接，保证可检测篡改。
- 四档签署：L1 自动，L2 电子确认，L3 电子签署可导出 PDF，L4 紧急后补签。
- 审计包内容：多源数据引用、推理附件、审批签署、执行回执；一键导出 PDF，可打印。
- 人工接管登记：即使执行权移交现有系统，也保留“人工接管”标记和最小登记，不绕过审计。
- 审计回流：处理结果回写事故模式记忆库；模型坏例回到评测集，支撑 Bad Case 双轨回归。

**价值**
审计不是事后补充，而是每个 AI 判断的默认交付物。它让船长、法务和外部审计都能回答“为什么这么做”。

## 第 10 页：AI 控制体系①——事件治理与权限流转

**主标题**
AI 建议，人审批；权力始终在人手上。

**机制说明**
- L1 自动分发基层：轻事件、低后果、个人定向触达可自动执行。
- L2 值班确认：需要值班/客服确认后执行。
- L3 经理/法务审批：涉及统一口径、赔偿或公共可见触达时必须审批。
- L4 船长拍板：最高后果事件由船长/最高层决策。
- 审批超时自动升级：防止事件在等待中失控；每个等级设置处理时限。
- 任意节点可转人工接管：系统停止自动执行，转为观察、记录、建议；执行移交船司现有调度系统。
- 投放审核矩阵：根据可见性、可撤回性、后果决定审批级别；公共广播/船载屏必须人工确认。

**价值**
这套机制不是给审批“加流程”，而是让 AI 在建议层发挥价值，同时把执行权和责任留在人身上。它也回应了评审对“AI 自主性”的质疑：ClarSyn 的自主性体现在持续推理和主动提醒，而不是自动执行高后果动作。

## 第 11 页：AI 控制体系②——反幻觉与可信护栏

**主标题**
幻觉不可根除，但我们把错误成本降到最低。

**三层兜底**
1. 多源 API 与知识库事实锚：条款、策略、数据必须可回溯；RAG 引用原文编号，禁止无出处承诺。
2. 结构化约束：JSON Schema / 模板槽位，让模型在“选择和填空”里工作，而不是自由写作。
3. 置信度 + 人工兜底：低信度、证据不足、规则冲突时强制转人工。

**降级机制**
T0–T3：熔断 / 回退 / 快照 / 人工接管。AI 不可用时，系统回退到规则模板和本地缓存，不影响确定性计算与审批。

**金句**
AI 的错误成本，从“一次错误执行”降级为“一次多余知会、一次更早的人工介入”。

## 第 12 页：AI 价值高地①——开放域异常发现

**主标题**
看见规则系统看不见的“库外异常”。

**案例说明**
X-0001 是一个库外弱信号：楼层滞留偏离历史、密度异常抬升。系统发现这个信号不在事件库中，于是生成提醒卡，并路由到值班船员核实。值班李工确认滞留属实后，将其升级为正式事件 E01，进入标准事件管线，同时回写事件分类库。

**为什么规则做不到**
规则系统只能对已录入的模式触发；新事件一旦不在规则表里，系统就“看不见”。开放域异常发现是 ClarSyn 与“旧系统 + 规则升级”的本质差异之一。

**技术栈**
无监督异常检测 + 向量检索相似度 + LLM 语义判断 + 规则复核。它不追求“AI 自己下结论”，而是让 AI 提出“这可能值得关注”，最终由人确认。

## 第 13 页：AI 价值高地②——长链路推演与弱信号整合

**主标题**
推演没写过的组合，把 20–45 分钟拼图压成分钟级局势。

**案例说明**
E09 台风航变中，港口靠泊窗口取消、侧风 34kn、AI 赔付风险升高，三个信号单独看都不一定触发传统规则，但叠加起来意味着航变风险正在上升。ClarSyn 将弱信号整合后，由 AI 判据自动升级 L4，并生成影响推演与预案重排。

**价值表述**
- 提前发现气象/航变弱信号，而不是等事件发生后解释。
- 快速生成“影响预测 + 预案准备”，让船长在决策窗口内看到选项。
- 规则系统需要预写所有分支，AI 能推演未见过的组合。

**技术栈**
多 Agent/Workflow 串联（事件 → 影响 → 资源 → 方案）+ 本地小/中模型 + RAG。

## 第 14 页：AI 价值高地③——推理附件与可解释性

**主标题**
每个 AI 判断都自带理由。

**内容说明**
推理附件不是附加品，而是判断的交付物。它覆盖事件分类、影响推演、方案组合、库外异常提醒、客服问答、审批决策、升级判定等所有 AI 参与环节。每个附件至少包含：结论、置信度、关键证据、替代方案和引用编号。

**案例**
E-L4 船长决策卡展开推理附件后，可以看到系统为什么建议确认执行方案：依据包括侧风、港口窗口、赔付风险；同时给出替代方案“等待窗口”，并标注置信度。决策后进入审批流，最终生成审计包。

**技术栈**
LLM 摘要 + 确定性校验 + RAG 引用编号 + trace_id。附件生成后还要经过确定性校验，确保引用编号真实存在、置信度在有效范围、公式可复算。

## 第 15 页：技术选型总表——场景 × 环节 × 模型/技术

**主标题**
每个 AI 环节都回答：用什么、部署在哪、为什么。

**技术选型原则**
- 能规则不用 ML：确定性计算、审批门、超时升级、哈希审计全部用代码实现。
- 能用小模型不用大模型：事件分类、意图识别、话术生成等实时环节用本地小模型。
- 能离线不用云端：船载边缘保证实时闭环，云端只承担非实时任务。
- 云端永不进入 3 分钟实时闭环。

**选型表**
| 环节 | 技术形态 | 模型/算法 | 部署位置 | 理由 |
|---|---|---|---|---|
| 事件分类 | 有监督/少样本分类 + 规则复核 | 轻量分类模型 | 本地 | 实时、低延迟、可离线 |
| 库外异常 | 无监督异常检测 + 向量检索 | 特征模型 + embedding | 本地 | 覆盖未见过的组合 |
| 长链路推演 | 多 Agent/Workflow | 本地 7B–14B 量化 | 船载边缘 | 实时闭环、可回滚 |
| 条款/策略检索 | RAG + reranker | 本地 embedding + 规则匹配 | 本地 | 确定性优先、引用可溯 |
| 话术生成 | LLM 生成 + 模板约束 | 0.5B–8B 小模型 | 船载边缘 | 离线、短文本 |
| 长文档解析 | 云端大模型 | 云端 API | 云端异步 | 非实时、批量处理 |

**上下文窗口判断**
实时链路各环节 prompt 都是短输入，4K–8K 上下文窗口足够；只有离线长文档解析需要长上下文云端模型。

**多模态边界**
B 线 MVP 以结构化数据 + 文本信号为主；摄像头只作为外部计数接口，不引入图像理解模型。多模态感知属于外部子系统通过事件接口接入。

**内容来源**
- `design/b-port-shore-and-itinerary/ai-architecture-and-value.md` 部署与模型选型、§3.9

## 第 19 页：差异化与风险 / 为什么是现在

**主标题**
为什么是 ClarSyn，而不是旧系统、聊天 AI 或导航系统？

**差异化**
- vs 传统规则系统：规则系统看不见库外、推演不了新组合、解释不了为什么。三块 AI 高地是 ClarSyn 的核心差异。
- vs 聊天式 AI：不是帮人写话术，而是快速调用 API、发现弱信号、生成预案，并通过审批与审计闭环。
- vs 港口/机场排队系统：我们做船岸协同决策层，不是单点排队；价值在跨系统整合与航变响应。

**为什么是现在**
2026 航变/港口接驳是官方与媒体双确认的持续痛点；气象 API、本地小模型等条件已经成熟；AI 能力刚好补规则系统空白。评委关注“为什么不是旧系统 + 规则升级”，而 ClarSyn 的三块 AI 高地正是对这一质疑的直接回应。

**风险与对策**
- 外部数据不可得：按可用性分层，能接则接，不能接不假设。
- 模型幻觉：多源事实锚 + 结构化约束 + 人工兜底。
- 组织边界：不越权，只做船方权限内。
- 离线：T0–T3 降级，核心闭环不依赖网络。
