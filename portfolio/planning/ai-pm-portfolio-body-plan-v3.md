## 3. P8 产品方案总览 / 系统组成

### 3.1 页面任务

- 把 P7 的 AI 价值翻译成“系统由什么组成”
- 让读者看到 ClarSyn 不是一个大模型，而是有明确边界、不同分工、相互协作的系统
- 为 P9-P20 的详细页建立“系统地图”

### 3.2 页面理解：三类不同性质的内容

P8 不能把“处理流程、系统组件、端口边界”混在同一层级。

- 处理流程：事件是如何被处理的（不是模块）
- 核心引擎：实际存在的系统组件
- 端口边界：输入和输出如何分类

### 3.3 输入端口分类

| 类别 | 示例 |
|---|---|
| 岸基/外部预警源 | 气象、台风路径、港口窗口、海事通告、岸基运营指令 |
| 外部信息 API | 船期、港口、客服工单、乘客清单、票务/POS、岸上游 |
| 船内实时信号 | 船员上报、现场感知、设备状态、排队计数、客服反馈 |
| 外部 AI 感知 | 火灾识别、拥堵识别、人群密度、异常行为识别 |
| 船外协同端口 | OTA、旅行社、交通、港口/口岸公告 |

### 3.4 事件处理主线

```text
接入 → 事件标准化 → 识别/推演 → 方案生成 → 审批 → 输出/执行 → 回写
```

- 事件标准化 = 规则内核 + AI 推理共同完成
- 识别/推演 = 规则内核 + AI 推理共同完成
- 审批 = 审批/权限服务
- 输出 = 输出编排/端口管理
- 回写 = 审计/记忆服务

### 3.5 核心引擎（实际组件）

- 规则/确定性计算内核
- AI 推理引擎
- 事件模型/状态存储
- 审批/权限服务
- 审计/记忆服务
- 输出编排/端口管理

### 3.6 输出端口分类

| 类别 | 示例 | 输出内容 |
|---|---|---|
| 业务协同下游 | 客服系统、法务赔偿系统、港口协同 | 风险预警、航变预警、方案预制、审计材料 |
| 执行端 | 船长端、运营调度台、船员端 | 任务指令、处置提醒、审批请求 |
| 乘客触达 | 乘客 App、船载屏、广播、短信 | 通知、引导、时间窗、接驳建议 |
| 审计/归档 | 审计系统、导出 PDF | 留痕、追溯、证据包 |

### 3.7 推荐构图

```text
输入端口（分类）          事件处理主线            输出端口（分类）
┌────────────────┐   ┌────────────────────┐   ┌────────────────┐
│ 外部信息 API     │   │ 接入 → 标准化      │   │ 业务协同下游     │
│ 船内信号端口     │──▶│ → 识别/推演        │──▶│ 执行端          │
│ 外部 AI 感知     │   │ → 方案 → 审批      │   │ 乘客触达        │
│ 船外协同端口     │   │ → 输出 → 回写      │   │ 审计/归档       │
└────────────────┘   └────────────────────┘   └────────────────┘
                              │
               ┌──────────────▼──────────────┐
               │ 核心引擎（实际组件）          │
               │ 规则/确定性计算内核           │
               │ AI 推理引擎                  │
               │ 事件模型/状态存储             │
               │ 审批/权限服务                │
               │ 审计/记忆服务                │
               │ 输出编排/端口管理             │
               └─────────────────────────────┘
```

### 3.8 关键关系

- 事件处理主线是流程，不是模块
- 核心引擎是组件，负责支撑处理主线
- 输入/输出是端口分类，不是模糊的“适配器”
- 输出必须区分：给下游业务系统、给执行端、给乘客、给审计
- 事件标准化不是独立模块，而是规则内核和 AI 推理共同完成的处理环节


### 3.9 岸基 ⇄ 船基协同结构（2026-09-01 补充）

ClarSyn 不是单一系统，而是“岸基决策协同层 + 船基实时执行协同层”。

- 岸基子系统：接收气象/台风/港口/海事/岸基运营指令，做航次级影响评估，生成航次变化方案，协同总部/船长确认，再下发船基。
- 船基子系统：接收岸基航次方案 + 本船实时状态，做下船/接驳/时间窗/船员任务推演，生成安全与乘客服务方案，触达船员/乘客/港口，执行回写。
- 岸基 → 船基：航次变化方案、台风/港口预警、修订 ETA、港口窗口、赔偿/客服策略。
- 船基 → 岸基：本船状态、乘客数量、执行结果、现场反馈、事件升级。
- 部署：岸基云端/中心 + 船载边缘/本地/离线。

## 4. P9 核心业务场景流程（泳道图画法）

P9 用业务泳道图展示“ClarSyn 如何在真实业务场景里跑通”，一个核心场景占一页。

### 4.2 场景拆分

- P9-1 台风航变响应
- P9-2 登离船动态调度
- P9-3 库外信号升级（X-0001）

### 4.3 泳道设置（横向泳道，时间从左到右）

| 泳道 | 名称 | 职责 |
|---|---|---|
| 1 | 岸基/外部预警源 | 气象、台风、港口、海事、岸基运营指令 |
| 2 | 船内/本船实时信号 | 现场感知、船员上报、设备状态、客服反馈 |

| 4 | 船长/运营决策 | L4 审批、安全确认、方案调整 |

### 4.4 图形约定

### 4.5 P9-1 台风航变响应 · 传递顺序

```text
岸基系统：
气象/台风/港口/海事信号
→ 航次级影响评估

→ 触达船员/乘客/港口协同
→ 执行回写
```

### 4.6 P9-1 审核点

- 船长 L4 审批：查看决策卡、推理附件、安全风险，批准/驳回/要求调整。
- 安全确认/方案调整：确认安全下船方案、迎接方案、接驳安排、乘客触达内容。

### 4.8 P9 泳道图补充：事件识别子系统与输入信息分类（2026-09-01）

画泳道图前先区分：

- 输入信息 = 原始信号，不带判断
- 事件识别/判断子系统 = 把输入信息加工成事件/警报/风险信号
- 事件分类与严重度判定 = 判断“这是什么事件、什么等级”
- 影响推演与方案生成 = 在事件判断之后

```text
输入信息（岸基 / 船基）
  → 事件识别/判断子系统（岸基 / 船基）
  → 事件分类与严重度判定
  → 影响推演与方案生成
```

#### 岸基事件识别/判断子系统

- 航次与航线变更研判子系统
- 港口与口岸态势研判子系统
- 岸侧高流量预警子系统
- 气象与航行风险评估子系统
- 外部安全事件研判子系统

#### 船基事件识别/判断子系统

- 火灾与烟雾预警子系统
- 船内设备异常监测子系统
- 人员拥挤/聚集识别子系统
- 乘客安全与健康事件监测子系统
- 乘客流与排队状态研判子系统
- 船舶靠离泊风险监测子系统
- 库外异常识别子系统

#### 输入信息分类（原始信号）

岸基输入：气象/海洋环境、港口/口岸状态、岸基交通与接驳、岸基客流、海事/航行通告、岸基运营指令。

船基输入：船舶状态、船内安全传感、船内设备状态、乘客/船员状态、船内客流/排队、客服/船员上报、外部 AI 感知结果。

#### 人工审核级别（用于泳道图标注）

- L1：自动分发，无人工审核
- L2：值班船员/客服确认
- L3：运营经理/法务审批
- L4：船长/最高层决策


### 4.9 系统运行主循环图（简化版，2026-09-01 确认）

主循环图不绑定具体业务，也不展开 L1-L4 细节。

```text
输入信息（岸基/船基）
  → 事件识别与标准化（岸基/船基识别子系统）
  → 事件分类与风险判定（输出事件类型 + 等级）
  → 主系统：AI 影响推演 → 候选方案组合 → 预警与决策卡
  → 人工控制 / 权限升级通道（L1-L4 简化为一个通道）
  → 执行与输出
      ├── 系统自动执行
      ├── 人员执行
      └── 下游协同/告知
  → 审计回写 / 学习回流
```

旁侧画：

```text
环形箭头：事件进入 → 判断 → 推演 → 审批 → 执行 → 回写 → 学习 → 再次判断
```

一句话说明：

> ClarSyn 的本质：事件从输入到执行回写形成闭环，AI 负责判断与推演，人保留升级与审批控制。

### 4.10 执行端分类

- 系统自动执行：审批通过后，由系统直接触发渠道触达、状态更新、审计写入；不需要再找一个人手动发。
- 人员执行：系统生成任务/指令，由船员/运营人员到现场或系统内执行，例如调整下船批次、增开通道、协调接驳。
- 下游协同/告知：把预警或信息交给下游业务系统/岸基通知端口，例如客服、法务赔偿、港口、OTA。

### 4.11 循环监控机制（简略示意）

执行与输出后，事件并不都直接终止：

- 终止型事件：例如航变预警下船方案通告，告知港口送达即可。
- 持续监控型事件：例如拥堵事件、局部意外导致的堵塞，需要定期复检直至事件解决。

主循环图内只画一个简略的“监控/复检”虚线环，表示：

```text
执行与输出 →（未解决）→ 定期复检/挂起再检 → 事件状态更新
                                      ↓
                              解决后 → 闭环关闭/归档
```

不展开详细复检周期、升级规则，具体留给事件治理/挂起再检页面。
