## 3. P8 产品方案总览 / 系统组成

### 3.1 页面任务

- 把 P7 的 AI 价值翻译成“系统由什么组成”
- 让读者看到 ClarSyn 不是一个大模型，而是有明确边界、不同分工、相互协作的系统
- 为 P9-P20 的详细页建立“系统地图”

### 3.2 页面理解：三类不同性质的内容

P8 不能把“处理流程、系统组件、端口边界”混在同一层级。

- 处理流程：事件是如何被处理的（不是模块）
- 核心引擎：实际存在的系统组件
- 端口边界：输入和输出如何分类

### 3.3 输入端口分类

| 类别 | 示例 |
|---|---|
| 岸基/外部体系（预警源 + 航变决定） | 气象、台风路径、港口窗口、海事通告、岸基运营指令 → **外部已成立航变/靠离泊决定**（ClarSyn 接收决定、不做航变决定） |
| 外部信息 API | 船期、港口、客服工单、乘客清单、票务/POS、岸上游 |
| 船内实时信号 | 船员上报、现场感知、设备状态、排队计数、客服反馈 |
| 外部 AI 感知 | 火灾识别、拥堵识别、人群密度、异常行为识别 |
| 船外协同端口 | OTA、旅行社、交通、港口/口岸公告 |

### 3.4 事件处理主线

```text
接入 → 事件标准化 → 识别/推演 → 方案生成 → 审批 → 输出/执行 → 回写
```

- 事件标准化 = 规则内核 + AI 推理共同完成
- 识别/推演 = 规则内核 + AI 推理共同完成
- 审批 = 审批/权限服务
- 输出 = 输出编排/端口管理
- 回写 = 审计/记忆服务

### 3.5 核心引擎（实际组件）

- 规则/确定性计算内核
- AI 推理引擎
- 事件模型/状态存储
- 审批/权限服务
- 审计/记忆服务
- 输出编排/端口管理

### 3.6 输出端口分类

| 类别 | 示例 | 输出内容 |
|---|---|---|
| 业务协同下游 | 客服系统、法务赔偿系统、港口协同 | 风险预警、航变后影响推演、方案预制、审计材料 |
| 执行端 | 船长端、运营调度台、船员端 | 任务指令、处置提醒、审批请求 |
| 乘客触达 | 乘客 App、船载屏、广播、短信 | 通知、引导、时间窗、接驳建议 |
| 审计/归档 | 审计系统、导出 PDF | 留痕、追溯、证据包 |

### 3.7 推荐构图

```text
输入端口（分类）          事件处理主线            输出端口（分类）
┌────────────────┐   ┌────────────────────┐   ┌────────────────┐
│ 外部信息 API     │   │ 接入 → 标准化      │   │ 业务协同下游     │
│ 船内信号端口     │──▶│ → 识别/推演        │──▶│ 执行端          │
│ 外部 AI 感知     │   │ → 方案 → 审批      │   │ 乘客触达        │
│ 船外协同端口     │   │ → 输出 → 回写      │   │ 审计/归档       │
└────────────────┘   └────────────────────┘   └────────────────┘
                              │
               ┌──────────────▼──────────────┐
               │ 核心引擎（实际组件）          │
               │ 规则/确定性计算内核           │
               │ AI 推理引擎                  │
               │ 事件模型/状态存储             │
               │ 审批/权限服务                │
               │ 审计/记忆服务                │
               │ 输出编排/端口管理             │
               └─────────────────────────────┘
```

### 3.8 关键关系

- 事件处理主线是流程，不是模块
- 核心引擎是组件，负责支撑处理主线
- 输入/输出是端口分类，不是模糊的“适配器”
- 输出必须区分：给下游业务系统、给执行端、给乘客、给审计
- 事件标准化不是独立模块，而是规则内核和 AI 推理共同完成的处理环节


### 3.9 岸基 ⇄ 船基协同结构（2026-09-01 补充）

ClarSyn 不是单一系统，而是“岸基决策协同层 + 船基实时执行协同层”。

- 岸基子系统：接收气象/台风/港口/海事/岸基运营指令，做**"已成立航变决定"后的**航次级影响评估，生成航次变化执行方案，协同总部/船长确认，再下发船基。（2026-09-04：航变**决定本身**由船公司做、船长安全确认，ClarSyn 不做航变决定）
- 船基子系统：接收岸基航次方案 + 本船实时状态，做下船/接驳/时间窗/船员任务推演，生成安全与乘客服务方案，触达船员/乘客/港口，执行回写。
- 岸基 → 船基：航次变化执行方案、台风/港口预警、修订 ETA、港口窗口、赔偿/客服策略。
- 船基 → 岸基：本船状态、乘客数量、执行结果、现场反馈、事件升级。
- 部署：岸基云端/中心 + 船载边缘/本地/离线。
- 常规调度审批落在 L2/L3（宾客运营线），船长知会/抄送不阻塞；仅安全/群体/法定/不可逆触发升 L4 船长决策区（§4.2.4）。

### 4.5 P9-1 航变后的登离船与接驳调度响应 · 传递顺序

```text
外部体系（起点=已成立决定，非 ClarSyn 发现台风）：
气象/台风/港口/海事发预警与提醒
→ 船公司（岸基）生成航次变化方案（自主决定）
→ 与总部/船长协同确认（船长安全否决/最终确认权）
→ 航变决定成立 → 下发船基系统

船基系统（ClarSyn）：
接收外部航变决定 + 本船实时状态
→ 下船批次/接驳/时间窗/船员任务推演（影响链）
→ 生成安全方案与乘客服务方案
→ 常规：值班确认 → 运营经理/航次经理审批（L2/L3）
→ 船长：知会/抄送（不阻塞）
→ 执行期出现 安全/群体/法定/不可逆 → 升级 L4 船长决策区
→ 触达船员/乘客/港口协同
→ 执行回写
→ 学习回流
```

### 4.6 P9-1 审核点

- 常规调度：值班确认 → 运营经理/航次经理审批（涉赔偿法务复核）；**船长知会/抄送、不阻塞执行、不增加船长审批负载**。
- **船长 L4 决策区（仅安全/群体/法定/不可逆触发）**：查看决策卡、推理附件、安全风险，批准/驳回/要求调整；紧急决策事后补签。
- 安全确认/方案调整：确认安全下船方案、迎接方案、接驳安排、乘客触达内容（安全相关确认可留在运营线 + 船长知会，仅在危及安全时升船长）。

#### 输入信息分类（原始信号）

岸基输入：气象/海洋环境、港口/口岸状态、岸基交通与接驳、岸基客流、海事/航行通告、岸基运营指令。

### 4.9 系统运行主循环图（简化版，2026-09-01 确认）

主循环图不绑定具体业务，也不展开 L1-L4 细节。

```text
输入信息（岸基/船基）
  → 事件识别与标准化（岸基/船基识别子系统）
  → 事件分类与风险判定（输出事件类型 + 等级）
  → 主系统：AI 影响推演 → 候选方案组合 → 预警与决策卡
  → 人工控制 / 权限升级通道（L1-L4 简化为一个通道）
  → 执行与输出
      ├── 系统自动执行
      ├── 人员执行
      └── 下游协同/告知
  → 审计回写 / 学习回流
```

旁侧画：

```text
环形箭头：事件进入 → 判断 → 推演 → 审批 → 执行 → 回写 → 学习 → 再次判断
```

一句话说明：

> ClarSyn 的本质：事件从输入到执行回写形成闭环，AI 负责判断与推演，人保留升级与审批控制。

### 4.10 执行端分类

- 系统自动执行：审批通过后，由系统直接触发渠道触达、状态更新、审计写入；不需要再找一个人手动发。
- 人员执行：系统生成任务/指令，由船员/运营人员到现场或系统内执行，例如调整下船批次、增开通道、协调接驳。
- 下游协同/告知：把预警或信息交给下游业务系统/岸基通知端口，例如客服、法务赔偿、港口、OTA。

### 4.11 循环监控机制（简略示意）

执行与输出后，事件并不都直接终止：

- 终止型事件：例如航变后下船方案通告，告知港口送达即可。
- 持续监控型事件：例如拥堵事件、局部意外导致的堵塞，需要定期复检直至事件解决。

主循环图内只画一个简略的“监控/复检”虚线环，表示：

```text
执行与输出 →（未解决）→ 定期复检/挂起再检 → 事件状态更新
                                      ↓
                              解决后 → 闭环关闭/归档
```

不展开详细复检周期、升级规则，具体留给事件治理/挂起再检页面。

### 4.12 P9-1 执行侧机制标注（2026-09-04 补充，P9-1 泳道须体现）

> 来源：`event-governance-framework.md` §4.2.5–4.2.7 / §4.14–4.15。P9-1 泳道图在执行侧需画清楚以下机制：

1. **前置决策支持（画在外部航变决定成立之前，虚线"可选"通道）**：多源弱信号 → 前置推演 → 决策支持卡（运营/经济/风险/综合价值四维）→ 船司选案 → 船长安全确认 → 决定成立；
2. **执行侧三子行 + AI 手边界**：决策层（L2/L3/L4 审方案）→ 组织执行层（L2 收任务包、认领、向 +1 转达）→ 现场执行层（L1 用现有系统接 +1 指挥）；"AI 手边界"虚线画在组织执行层与现场执行层之间（AI 信息止于任务包，现场提示经 +1 转达，末端零新增负载）；
3. **执行反馈池**：L2 包状态 / L1 最小登记 + 端口感知 → 反馈池（append-only）→ 接回监测/恢复点；
4. **挂起复检块（画在"转人工接管"分支之后）**：接收三个连入（L3 转接管 / 被拒不重审 / 执行受阻），输出三线——只记日志（虚线回环 + 循环提醒）、信息源变化 → 回执行期动态调整、物理劣化/安全阈值 → 派生子事件（parentTrace）→ L4；
5. **血缘线**：派生/子事件用 `parentTrace` 虚线连回主事件（不重复"发现"）。

### 5. P13 核心 AI 子系统内容要点（2026-09-04 补充）

> P13 = "核心 AI 子系统：航变响应影响推演/事件推演"。本页要讲透的不只是"决定后的影响链推演"，还包括**决定之前的前置决策支持**（ClarSyn 的参谋价值）：

**5.1 前置决策支持子系统（航变决定前，§4.15）**
- 输入：气象/海洋、船期/泊位、港口窗口/管制、接驳运力、乘客与特殊人群、条款/判例、历史事故模式、资源清单；
- 决策考虑因素（对每个备选航变方案输出四维价值）：运营影响（确定性内核）、经济影响（相对量级+假设）、风险影响（与 L4 判据联动）、综合价值分；
- 角色与时点：ClarSyn=参谋（不做决定）；船司=业务选案；船长=安全否决/最终确认；决定成立后进入"确认基线"；
- 动态：决定前增量刷新（版本/频次闸）+ 重推闸门（3 候选全不满足才重推）；决定后走影响链动态调整。

**5.2 影响链推演（决定成立后）**
- 接收"已成立航变决定 + 本船状态" → 登离船/接驳/时间窗/船员任务推演 → 方案（含推理附件）→ 审批/递送/执行/反馈闭环；
- 方案审批一次 + 修订三形态 + 三级递送粒度（§4.2.5/4.2.6）。
