## 第 1 页：产品定位与价值主张
> 英文标题（完整）：Product Positioning and Value Proposition

### 页面目标

让读者第一眼知道：ClarSyn 是什么、给谁解决什么问题、核心价值是什么。

### 核心信息

- 一句话定位：把船↔岸交界的混乱，变成分钟级清晰决策。
- 产品性质：面向邮轮公司的港岸协同决策层，不是导航工具，不是聊天机器人。
- 核心记忆点：看见没见过的、推演没写过的、解释说不清的。
- 价值闭环：不是多一个告警，而是把事件变成“发生了什么 → 影响谁 → 下一步怎么办 → 谁审批 → 如何回写”。

### 正文内容

1. 产品名称：ClarSyn
2. 中文定位：基于多 Agent 协同的邮轮靠港接驳动态调度系统
3. 英文定位：Multi-Agent Collaborative Dynamic Scheduling System for Cruise Berthing & Shore Connection
4. 一段 3 行式说明：
   - 谁：邮轮公司运营决策层
   - 场景：登离船、港口接驳、航变响应
   - 价值：多源信息快速汇聚、弱信号提前发现、影响推演与预案准备、全链路审计
5. 一句话收束：AI 建议，人审批，全链路审计。

### 呈现方式

- 左：品牌与标题文字
- 右：船长端 / 运营端深色 UI 缩影
- 底部：3 个价值标签
- 形式：图 + 文 + 标签，不堆正文

## 第 2 页：宏观设计背景
> 英文标题（完整）：Macro Design Context (Industry Landscape and Stakeholder Chain)

### 页面目标

用简洁的宏观叙述解释：为什么邮轮行业、为什么是船岸交界、为什么是现在。

### 核心信息

中国邮轮市场正在复航与新船交付期，船↔岸交界是体验断裂最明显、利益链最长、决策最依赖人工跨系统核对的环节。

### 正文内容

1. 行业背景：
   - 中国邮轮市场复航，新船陆续交付，乘客规模大；
   - 船岸交界是登离船、接驳、航变等多类问题集中爆发的地方；
   - 邮轮公司、港口、OTA、旅行社、本地交通、政府监管共同构成复杂利益链。

2. 利益链相关方：
   - 邮轮公司：承担品牌、客诉、合规与赔偿风险
   - 乘客：关注等待时间、信息透明、行程确定性
   - 港口：负责通关、接驳、交通秩序
   - OTA / 旅行社：承担销售与退改沟通
   - 本地交通：出租车、网约车、短驳供给
   - 政府 / 监管：关注公共秩序、乘客权益、交通治理

3. 为什么是现在：
   - 2026 年航变与港口接驳是官方与媒体双确认的持续痛点；
   - 本地小模型、气象 API、RAG 等技术条件成熟；
   - 新船前装设计窗口允许我们把 AI 决策层作为系统能力设计进去。

4. 宏观判断：
   - 邮轮公司不缺单一信息系统，缺的是把多源信息变成决策依据的协同层。
   - 很多环节不是没人负责，而是缺少跨系统的统一闭环。

### 呈现方式

- 上半页：一段宏观叙述文字 + 3 个关键行业标签
- 下半页：一张利益链示意图（邮轮公司 / 乘客 / 港口 / OTA / 交通 / 政府）
- 呈现：文为主，图为辅，信息量克制

## 第 3 页：研究流程
> 英文标题（完整）：Research Process and Methodology (Nine-Stage Convergence Chain)

### 页面目标

用一张总体研究流程图说明：整个项目经历了从行业认知、问题定义、用户调研、证据验证、业务梳理、目标确认、AI 匹配、方案细化到验证迭代的完整研究过程。

### 核心信息

ClarSyn 的研究路径不是“先有方案再找问题”，而是多源证据、业务边界和 AI 能力反复收敛后得出的产品判断。

### 正文内容

1. 总体研究流程主链（九段）：

```text
宏观行业研究
→ 问题定义与场景锁定
→ 用户与干系人调研
→ 痛点证据收集与交叉验证
→ 业务梳理与系统边界
→ 目标确认与指标假设
→ AI 能力匹配与技术边界
→ 方案细化与原型设计
→ 验证迭代与试点路径
```

2. 每个阶段的输入与输出：

| 阶段 | 输入 | 输出 |
|---|---|---|
| 宏观行业研究 | 邮轮市场、参考船型、媒体报道、官方答复 | 行业利益链认知、重点场景判断 |
| 问题定义与场景锁定 | 宏观背景、行业断点 | 登离船 / 港口接驳 / 航变三类核心场景 |
| 用户与干系人调研 | 船长、运营、客服、法务、乘客、港口角色 | 用户任务、采购者、决策链与使用链 |
| 痛点证据收集与交叉验证 | 公开资料、用户 UGC、媒体调查、政府答复 | 痛点清单、证据等级、三类痛点聚类 |
| 业务梳理与系统边界 | 现有系统、接口现实、组织权限 | 系统边界、数据三态、接口关系图 |
| 目标确认与指标假设 | 基线证据、业务目标 | 设计目标区间、显式假设、验证口径 |
| AI 能力匹配与技术边界 | Hackathon 高分案例、竞品方案、技术可行性 | AI 三高地、规则与 AI 边界、模型选型 |
| 方案细化与原型设计 | PRD、AI 架构、事件治理框架 | M1–M6 方案、多 Agent 架构、高保真原型 |
| 验证迭代与试点路径 | 62 条事件案例、指标假设、高保真原型 | 演示链路、评测结果、单港试点路径 |

3. 研究方法标签：

- 桌面研究
- 多源交叉验证
- 案例挖掘
- 产品三角验证（业务证据 × AI 能力 × 工程边界）
- 断点诊断（发现 / 影响判断 / 协同 / 回写）

4. AI PM 视角：

- 先证明“我如何理解行业”
- 再展示“我如何定义问题、调研用户、验证证据”
- 然后说明“我如何梳理业务边界、确认目标、判断 AI 边界”
- 最后落到“我如何细化方案、设计原型并验证迭代”

### 呈现方式

- 主视觉：总体研究流程图（九段纵向主链 + 每段下方输入/输出小卡）
- 也可使用“两行蛇形流程图”控制页面高度
- 阶段之间用箭头连接，强调“层层收敛”
- 底部放研究方法标签
- 呈现：图为主，文为辅，页面核心是流程图本身

#### 官方答复 / 官方资料 —— 制度性承诺与治理口径

- 宝山区政府在 2025-03-10 的公开答复中承认吴淞口国际邮轮港存在“交通秩序、停车难、短途出租运营模式”问题；在 2026-03 的答复中再次提及同类问题，并针对邮轮港公共交通配套与游客往返体验提出改进方向。
  - 来源：宝山区政府 / 上海市政府门户（2025-03、2026-03）
- 宝山区政协在 2026-03-17 的提案答复中提出“强化邮轮港公共交通配套、优化游客往返体验”，内容涉及加强公共交通衔接、改善出租/网约车候车秩序、提升游客离港效率。
  - 来源：宝山区政协（2026-03-17）
- 爱达邮轮官方《岸上游指南》为 55 页静态 PDF，未提供实时排队、动态发车或在线可查询的接驳状态。指南中不同港口的接驳方案存在差异：济州江汀港仅提供出租车，公交车站位于距码头约 2km 的位置；舞鹤港提供付费接驳车，路线为“舞鹤港—舞鹤海鲜市场”，单程约 15 分钟；新潟港提供付费接驳车，路线为“新码头—新市中心”，单程约 50 分钟；函馆港提供免费接驳车，路线为“函馆码头—函馆市中心”，单程约 20 分钟。
  - 来源：爱达邮轮官方《岸上游指南》（2026-08）

#### 媒体报道 —— 规模化事件与舆论关注

- 新闻晨报 / 网易于 2025-08-04 发布吴淞口国际邮轮港打车难调查，报道中提到出租车存在“近的拒载、远的宰客”现象；同时记录出租车司机侧的情况：“苦等两小时接一单仅赚 48 元”。报道内容同时涉及乘客叫车难、司机短途单收入低、港口现场交通秩序三方面。
  - 来源：新闻晨报 / 网易（2025-08-04）
- 新浪财经 / 扬子晚报于 2026-08-07 报道爱达魔都号因 2026 年台风“白海豚”提前返航，事件中出现数百人拒不下船、新一批客人无法正常登船的情况；后续舆论中出现“万元房费仅赔千元”的赔偿争议，并有海事局对提前返航是否与赔付减少有关的回应。
  - 来源：新浪财经 / 扬子晚报（2026-08-07）
- 新京报于 2025-07-24 报道邮轮船票存在退改难题，提到早鸟促销以较低票价吸引预订，同时捆绑较高退改成本；2026-03-29 又报道法院在一起因目的地战乱导致邮轮行程取消的案件中，判决旅行社全额退款。
  - 来源：新京报（2025-07-24、2026-03-29）
- 搜狐 / 媒体转载于 2024-04 报道首个回归中国大陆市场的国际邮轮出现“上下船拥挤、用餐秩序混乱”的情况，内容涉及复航初期集中出现的排队、秩序与服务压力。
  - 来源：搜狐 / 媒体转载（2024-04）

#### 用户评论 —— 微观现场与个体经历

## 第 5 页：痛点分析与需求
> 英文标题（完整）：Pain-Point Analysis and Requirements Definition (Three-Layer Diagnosis)

### 页面目标

把第 4 页调研事实进行综合，形成有判断力的痛点总结，并说明这些总结背后的需求与优先级。

> 本页只描述业务问题与需求，不预设技术方案；技术路线是否适合、用在哪里，留到后续机会判断页再论证。

### 核心信息

调研事实综合后可以看到：船岸交界的问题不是几个并列痛点，而是由外向内嵌套的三层结构——最外层是乘客体验问题，中层是流程协同问题，最内层是决策治理问题。

### 正文内容

1. 痛点总结（综合判断）：

体验层：

- 离船流程的时间承诺与实际执行严重脱节，乘客在不确定中长时间等待。
- 登离船批次与现场状态缺乏联动，导致排队和聚集难以被提前化解。
- 港口接驳信息以静态文档为主，乘客无法在决策前获得可比较、可依据的交通方案。

流程协同层：

- 航变等事件发生后，运营人员需要跨系统收集与核对信息，决策准备时间长，且高度依赖个人经验。
- 面向大规模乘客的沟通依赖逐批人工解释，工作量大且口径难以保持一致。
- 各渠道信息不同步，导致乘客端接收到的通知滞后于船司内部决策。

决策治理层：

- 航变与赔偿类问题缺少透明、可追溯的依据，容易从个体不满升级为群体事件。
- 事件处理过程留痕不足，事后难以完整回答“为什么这样做、谁批准的”。
- 多个不明显的迹象同时出现时，现有流程难以提前判断风险正在积累。
- 面对新出现的异常情况，缺少清晰的处理路径与责任归属。
- 局部事件发生后，对后续环节的连锁影响难以快速推演，容易遗漏关联影响。
- 决策者很难快速理解“为什么选择这个方案、依据是什么、还有哪些选择”。

2. 痛点类别图（建议视觉）：

图名：**痛点不是并列的三类，而是由外向内嵌套的三层**

- 外层 · 体验层：乘客感受得到的等待、排队、信息不确定
- 中层 · 流程协同层：跨系统核对、逐批沟通、渠道同步、口径一致
- 内层 · 决策治理层：风险迹象积累、新情况识别、连锁影响推演、决策理由解释、透明留痕

相关说法：

> 三层不是并列关系：体验问题是表象，流程协同问题是中层机制，决策治理问题藏在运营最深处，并影响前两层是否能够顺畅运转。

2.5 从闭环视角看：四类断点（参考视角）

把调研事实放到“事件闭环”视角下，可以看到船岸交界的痛点可归纳为四类断点：

- 发现慢：风险迹象积累、排队与聚集、航变苗头没有被提前识别；
- 影响不清：跨系统核对慢、连锁影响难推演，不知道事件会影响哪些批次、接驳、时间窗和交付；
- 动作分散：船司内部多角色各自处理，依赖群聊、表格和电话，缺少统一任务入口；
- 结果没回写：系统状态过期、事后难审计、经验未沉淀，闭环没有真正形成。

> 四类断点不是替代三层痛点，而是从“事件闭环是否完整”的另一个角度解读同一批事实。

3. 需求定义（暂不预设技术）：

- R1 事件信息组织与呈现：把分散在不同系统中的信息，整理成决策者可理解的事件状态。
- R2 风险迹象积累提示：当多个迹象同时出现时，提醒相关人员关注潜在升级风险。
- R3 连锁影响推演与候选方案：快速推演事件对后续环节的影响，并提供可选择的处理方案。
- R4 决策理由可见：让决策者看到依据、可选方案和选择理由。
- R5 人工审批、接管与留痕：高后果动作保留人工控制，全过程可追溯。
- R6 可复算的执行计算：时间窗、批次、触达等保持可计算、可复核。

4. 需求优先级是怎么来的：

- 不采用“痛点一一映射成功能”的方式，而是综合三条判断：
  1. 严重度：调研中反复出现的高后果问题；
  2. 可介入性：在船司权责边界内，系统能够实际干预；
  3. 现有手段覆盖不足：当前流程/规则/信息方式难以稳定解决。
- 优先级结果：
  - P0：风险迹象积累提示、连锁影响推演与候选方案——高后果、现有流程最难覆盖；
  - P1：事件信息组织与呈现、决策理由可见——直接影响决策质量和信任；
  - P2：人工审批、接管与留痕、可复算执行——治理与执行保障。

5. 产品定义视角补充：

- 本页只给出问题与需求，不说明技术路线；
- 技术路线是否适合、用在哪、为什么必须采用，属于后面的机会判断；
- 没有经过论证前，不应直接说“这个需求需要某种特定技术解决”。

- 中部：痛点分层图（三层嵌套结构，由外向内：体验层 → 流程协同层 → 决策治理层）

## 第 7 页：AI 机会判断
> 英文标题（完整）：AI Opportunity Assessment (Value Identification Through Four Breakpoints)

### 页面目标

用第 5 页已经建立的四类业务断点，解释 ClarSyn 的 AI 为什么不只是“多一个告警”，而是在规则和人工都难以稳定覆盖的位置上提供不可替代价值。

本页只讲 AI 价值判断，不展开系统架构、技术选型或控制实现；那些留给第 8 页起的 harness 章节。

### 核心信息

邮轮现场的问题，不是“没有人管”，而是事件没有形成闭环：

- 发现慢：
  - 事件状态缺少统一监控入口，信号分散在系统、现场、群聊里；
  - “发现 → 判断 → 升级 → 上报”链路依赖人，人无法持续盯住所有环节；
  - 小问题累积成事故；航变响应慢于游客情绪，缺少提前预警和灵活策略。
  核心症结：发现和升级链路依赖人工，缺乏持续监测、主动提醒和标准升级判断。

- 影响不清：
  - 上船拥堵不是单点问题，会传导到下船批次、接驳、排队、时间窗、船员任务、客户交付；
  - 影响没有关联到统一事件状态和次序；
  - 跨系统信息分散，人难以及时维护多约束关系。
  核心症结：缺少“事件 → 影响链”的关联和推演能力；多约束连锁关系超出人脑和规则的短期处理能力。

- 动作分散：
  - 船上各部门、上下船、港口、交通各管一段；
  - 动作散落在群聊、表格、电话里，缺少统一任务入口；
  - 动作之间缺少先后依赖和状态同步。
  核心症结：有分工、无协同；动作没有和统一事件任务流绑定，缺少整体闭环视图。

- 结果没回写：
  - 处置结果停留在群聊、表格、电话里，系统状态仍然过期；
  - 决策理由、依据、批准记录没有结构化沉淀；
  - 事后难回溯“为什么这样做、谁批准的”，经验无法复用。
  核心症结：闭环缺最后一段，执行结果没有形成可审计、可复用的资产。

ClarSyn 的 AI 不是去替代人盯每个环节，而是补在这些断点中最需要判断的位置：
把“影响不清”变成可推演的连锁影响；
把“发现慢”变成“判断值不值得升级”；
把“动作分散”变成“候选动作 + 审批路由”；
把“结果没回写”变成“推理附件 + 审计回写”。

### 正文内容

#### 1. 四类断点与 AI 价值的关系

| 业务断点 | ClarSyn 的 AI 价值 | 角色定位 | 实现标签 |
|---|---|---|---|
| 影响不清 | 长链路推演 + 弱信号整合：多系统弱信号组合、多约束连锁影响推演、候选方案 | 核心 AI 价值 | 调用多源 API · 跨系统整合 · 影响链推演 |
| 发现慢 | 库外/低置信度/复合信号 → 判断是否值得升级、升级到哪一级，生成提醒卡由人确认 | 事件治理分支 | 弱信号融合 · 升级判断 · 提醒路由 |
| 动作分散 | 生成候选动作，说明影响、约束、审批人；不替人拍板 | Agent 辅助层 | 候选动作 · 约束标注 · 审批路由 |
| 结果没回写 | 推理附件自动生成判断依据、置信度、替代方案；沉淀审计材料 | 信任与审计支撑层 | 推理附件 · 证据留痕 · 审计回写 |

需要强调的边界：

- “动作分散”不是 AI 核心价值；统一任务入口也需要工作流与组织协同，AI 只是生成候选动作和统一视图。
- “发现慢”不是“AI 能看见”，现代感知/系统也能发现信号；AI 的增量是判断“是否值得升级、升级到哪一级”。
- “结果没回写”不是“AI 做审计”，审计是工程机制；AI 的贡献是让每个判断自带可核对、可追溯的推理附件。

#### 2. 三个 AI 不可替代位置

（说明：下面三个位置不是并列功能，而是从核心、分支、支撑三个角色来理解同一套 AI 价值。）

1. 核心：长链路推演 + 弱信号整合

- 业务表现：一个局部事件发生后，能快速推演它对下船批次、接驳车辆、排队方案、时间窗、船员任务、客户交付的连锁影响。
- 为什么规则不够：规则只能执行预写分支，难以表达“多系统弱信号组合 + 多约束连锁影响”；人工又受限于沟通延迟和工作记忆。
- 业务价值：把“影响不清”变成决策者可看到的完整影响链和候选方案。
- 实现标签：调用多源 API · 跨系统整合 · 影响链推演

2. 分支：库外/低置信度信号 → 事件治理升级

- 业务表现：当信号还不足以成为正式事件时，判断它是否值得提醒、是否可能升级、升级到哪一级，并路由给人确认。
- 为什么规则不够：规则很难回答“不在清单里的信号是否值得升级”；低置信度复合信号也容易被淹没。
- 业务价值：把“发现慢”变成“在苗头阶段提前关注”，避免小问题累积成大问题。
- 实现标签：弱信号融合 · 升级判断 · 提醒路由

3. 支撑：推理附件 / 可解释性 / 审计回写

- 业务表现：每个 AI 判断都附带结论、置信度、关键证据、替代方案，可展开、可核对、可打印；处理结果回写为后续可用的记忆。
- 为什么规则不够：规则能返回模板，但给不出“为什么是它”的论证。
- 业务价值：把“结果没回写”变成“可审批、可审计、可追责”的闭环。
- 实现标签：推理附件 · 证据留痕 · 审计回写

#### 3. 三个真实场景价值卡

场景 1：X-0001 · 库外/低置信度信号 → 事件升级

- 过去：现场已经出现密度、滞留等信号，但传统流程只按已收录清单判断；低置信度复合信号容易被淹没，苗头长期游离在流程外。
- ClarSyn：接入这些信号，综合判断是否值得关注，生成提醒卡并路由值班确认；确认后升级为正式事件进入标准管线；只提醒、不执行。
- 价值：把“感知到但未治理”的信号，变成“可治理的事件”。

场景 2：E09 · 外部航变决定成立后 → 长链路推演 + 弱信号整合

- 过去：运营人员需要人工打开船期、气象、港口、乘客等多个系统核对，决策准备约需 20–45 分钟；弱信号组合和多约束连锁影响容易遗漏；例如航变后局部拥堵/受伤会连锁影响下船批次、接驳车辆、时间窗、船员任务。
- ClarSyn：**接收已成立的航变/靠离泊决定 + 本船状态**（航变预警与航变决定由外部体系负责：气象/海事发预警、船公司决定、船长安全确认——ClarSyn 不做”发现台风/判断是否航变”），自动整合弱信号、做多步影响推演（登离船/接驳/时间窗/船员任务），生成候选方案与推理附件；常规调度路由 **L2/L3 + 船长知会（不阻塞）**，**仅执行期安全/群体/法定/不可逆触发才升 L4 船长决策区**。
- 价值：决策准备从小时级压缩到分钟级，并且覆盖人容易漏掉的跨约束连锁影响。

场景 3：船长决策区事件（安全触发）· 推理附件 → 信任与审计支撑

- 过去：决策高度依赖个人经验，难以快速回答”为什么选 A 不选 B”；事后审计和纠纷处理缺少完整依据。
- ClarSyn：每个判断附带结论、置信度、关键证据和替代方案；附件可展开、可核对、可打印；**船长决策区（安全/群体/法定/不可逆触发）的决策同样带完整推理附件与事后补签**。
- 价值：让核心 AI 价值能被审批、被审计、被追责。

#### 4. 为什么规则系统不够（总结）

- 规则能处理已收录分支，但难以表达“多系统弱信号组合 + 多约束连锁影响”；
- 库外/低置信度信号不是规则看不见，而是规则很难判断“是否值得升级、升级到哪一级、要不要进入正式事件治理”；
- 规则能返回模板，但给不出“为什么是它”的论证，无法支撑高后果审批与审计。

#### 5. 收束金句

> AI 价值不是概念，而是每个具体场景都能回答：过去多慢、多险、多难解释；现在能更快、更早、更清楚。
>
> 更进一步：ClarSyn 不是又多了一个系统，而是把散落在船司、港口、客服、现场之间的决策断点，补成一条可追溯的闭环。

- 规则/确定性计算内核
- AI 推理引擎
- 事件模型/状态存储
- 审批/权限服务
- 审计/记忆服务
- 输出编排/端口管理

| 类别 | 示例 | 输出内容 |

#### 6. 关键关系

- 事件处理主线是流程，不是模块

#### 审核点

- 常规调度：值班确认 → 运营经理/航次经理审批（涉赔偿法务复核）；**船长知会/抄送、不阻塞执行、不增加船长审批负载**；
- **船长 L4 决策区（仅安全/群体/法定/不可逆触发）**：查看决策卡、推理附件、安全风险，批准/驳回/要求调整；紧急决策事后补签；
- 安全确认/方案调整：确认安全下船方案、迎接方案、接驳安排、乘客触达内容（安全相关确认可留在运营线 + 船长知会，仅在危及安全时升船长）。

```text
输入信息（岸基/船基）

  → 影响推演与方案生成
```

- 船基事件识别子系统：火灾与烟雾预警、船内设备异常监测、人员拥挤/聚集识别、乘客安全与健康事件监测、乘客流与排队状态研判、船舶靠离泊风险监测、库外异常识别

#### P9-1 前置与执行侧机制标注（2026-09-04 补充，泳道须体现）

> 来源：`design/b-port-shore-and-itinerary/event-governance-framework.md` §4.2.5–4.2.7 / §4.14–4.15。这些机制是事件治理与架构设计的核心内容，P9-1 与 P13 均要可视化：

**A. 前置决策支持（画在"外部航变决定成立"之前，虚线可选通道）**
多源弱信号（气象/船期/港口/接驳/历史事故）→ 前置推演 → **决策支持卡（运营 / 经济 / 风险 / 综合价值四维评估）** → 供船司选案、船长安全确认 → 航变决定成立。ClarSyn 是"参谋"：综合方案含经济价值与风险预估价值，但**决定权在船司 + 船长**（§4.15）。

**B. 执行侧三子行 + AI 手边界**
决策层（L2/L3/L4 审方案）→ 组织执行层（L2 收任务包、认领、向 +1 转达）→ 现场执行层（L1 用现有系统接 +1 指挥）；"AI 手边界"虚线画在组织层与现场层之间——**AI 信息止于任务包，现场提示经 +1 转达，末端零新增信息负载**（§4.2.6）。

**C. 方案审批与修订**
方案只由 L3 **决策审批一次**；不通过走"参数重算 / 备选切换 / 受限动作编辑"三形态（不默认 AI 重推）；L2/L1 收任务包不再重审方案（§4.2.5）。

**D. 执行反馈池与挂起复检**
L2 包状态 / L1 最小登记 + 端口感知 → 反馈池 → 接回监测/恢复点；"转人工接管"分支之后接**挂起复检块**：只记日志（虚线回环+循环提醒）/ 信息源变化 → 回执行期动态调整 / 物理劣化·安全阈值 → 派生子事件（parentTrace）→ L4（§4.2.7/§4.14）。

**E. 血缘线**
派生/子事件用 `parentTrace` 虚线连回主事件——**同一链路监控，不重复"发现"**；复合交叉事件按"资源-触达聚合"在决策层收敛（§4.14）。

### III-1 AI 决策支持与责任边界（Decision Support & HITL）〔内容稿〕
> 英文标题（完整）：AI Decision Support and Human-in-the-Loop Accountability Boundaries
> 缩写沿用：Decision Support & HITL

- **导语**：高利害决策遵循责任与权限一致原则：决策主体对结果负责，系统仅提供决策支持。
- **核心表述（本页主文）**：
  > 航变决策窗口短、后果不可逆、责任不可转移。依照海事治理规则，船长对航行安全的最终权威不可让渡，经营层面的方案取舍由船公司承担。系统由此被界定为决策支持主体而非决策主体：在航变决定成立之前，系统对多源弱信号执行前置推演，将候选路径——维持原计划、延期、改靠、换港——组织为可比较的方案集，并对每一候选输出四维影响评估：运营可行性、乘客影响、经济影响与风险影响。评估以相对量级结合显式假设呈现，不作货币化承诺。
- **机制逻辑**：
  1. 输入汇聚：气象、船期、港口窗口、接驳运力、乘客结构等信号进入前置推演；
  2. 方案组织：候选方案共享同一评估框架，保证维度间的可比性；
  3. 决策支持卡呈送：船司依据运营与经济维度行使方案选择权，船长就安全维度行使确认与否决权，涉赔偿事项经法务复核；
  4. 权限边界：决定成立与否由人类决策者控制，系统输出仅作为决策输入材料，不构成执行指令。
- **边界说明**：本机制不产生任何形式的自主航变建议表达；经济维度止于相对量级比较与假设标注。

- **经济影响**：赔付估算 / 停售损失 / 港口费差 / 改靠与差旅分摊——**相对量级 + 显式假设，不做货币化承诺**；

- **综合价值分**：加权评分，权重可配、可解释（计算依据进推理附件）。

### III-2 事件判定与库外识别（Event Framing & Out-of-Knowledge Detection）〔内容稿〕
> 英文标题（完整）：Event Framing and Out-of-Knowledge Detection
> 缩写沿用：Event Framing & OOK Detection

- **导语**：事件是治理单元的最小业务边界，事件化机制回答"什么值得进入治理管道"。
- **核心表述（本页主文）**：
  > 系统不凭空发现事件，而将值得治理的信号转化为事件，转化遵循两条通道。其一为弱信号累积：多条独立观察无异常、组合后可疑的信号进入信度评估，达到阈值后升级为事件；未达标的信号停留于态势监测与前置提醒，不打扰执行层。其二为强信号直达：火警、人员落水等突发强信号即时判定为事件，按安全等级处理。两类事件汇入统一的分类匹配流程。
- **机制逻辑**：
  1. 双通道事件化：弱信号信度升级与强信号直达，是事件仅有的两个来源；
  2. 分类匹配：库内匹配的事件进入标准治理管道；库内无匹配或复合信号进入库外识别出口；
  3. 库外处置：系统生成提醒卡提请人工复核，复核结论——忽略、观察、升级入库——回写知识库，识别能力随处置沉淀而扩展；
  4. 概念边界：库外识别面向"事件已成立而知识未覆盖"的情形，与事件形成前的弱信号状态相区别。
- **边界说明**：等级的正式判定与变更不属于本机制范围。

#### III-2 机制拆解与绘图参考（v1.0 补充 · 绘图工作稿，不进页面正文）

| 部件 | 职责 | 输入 | 输出 |
|---|---|---|---|

三个概念必须分开画（防评审误读）：

- **弱信号状态**：事件形成**前**——信度不足时停留为态势 chip / 前置提醒，不占时间轴、不是事件；
- **库外事件（X）**：事件候选**已成立**、在分类匹配阶段库内无对应（分类失配 / 复合事件）——X1–Xn 自由编号，不占 E 号；
- **强信号**：火警、人员落水等突发信号——跳过信度累积，直接判入事件，按安全等级处理。

**3. 环节流程拆解（主链 8 环节）**

```text
[1] 信号接入      感知 / 接口 / 人工上报 → 标准化（只接入、不判断）
[2] 双通道形成    弱信号：信度评估 → 达标升级为事件候选 ｜ 强信号：直接判入
[3] 分类匹配      事件候选 → 7 大类事件库匹配

      └─ 未匹配 / 复合可疑 → 库外出口 [4]
[4] 异常风险评估  AI 输出：风险等级（L1–L4 语义）+ 置信度 + 依据信号列表
[5] 提醒卡生成    A18：信号摘要 + 可能发展路径 + 为何值得注意 + 建议观察/预检动作

[6] 分级路由      A19：L1 低风险 → 值班 ｜ L2 → 值班 + 抄送运营经理

[7] 人工处置      忽略 / 存档观察 / 升级为正式事件 / 触发预案
[8] 闭环回写      升级入库 → 回写事件分类库（识别能力随处置沉淀）
```

### III-3 受约束的方案生成（Constrained Planning & Quantified Execution）〔内容稿〕
> 英文标题（完整）：Constrained Planning and Quantified Execution
> 缩写沿用：Constrained Planning & Quantified Execution

- **导语**：方案生成遵循两重纪律：方案来源受约束，量级来源可复现。
- **核心表述（本页主文）**：
  > 受约束的方案生成包含两层约束。第一层约束方案的来源：系统依据事件类型、影响范围与实时状态，从动作库、策略库、条款库中选择动作组合并编排次序，方案内容不源于模型的自由发挥。第二层约束方案的量级：动作库所载为动作的语义定义与参数槽，不携带数值——例如"增开备用通道"仍需确定通道编号、启用时刻、引导点位与开放时长；这些量级由确定性执行模型求解，而非 AI 推断。
- **机制逻辑**：
  1. 语义组合：事件经影响评估后完成动作组合选择与次序编排，AI 在此环节识别连锁影响并说明组合依据；
  2. 实例化求解：动作组合连同实时状态输入分域执行模型——人流拥挤场景以客流与疏散模型为内核，模拟人群在通道与闸口的流动、密度与瓶颈，进而求解分批规模、路径分配、批次间隔与资源点位；接驳运力、设施时序与窗口编排各有对应模型；
  3. 模型参数（通行速度、容量上限、密度阈值等）以显式假设标注并可供校准，求解过程可复现、可审计；
  4. 产物封装：实例化结果按递送层级封装为任务包，携带目标与量级，执行末端保留现场自由度。
- **边界说明**：模型未覆盖的非常规情形，相关量级显式标注为待标定并转入人工处置；AI 不参与量级算术。同一生成机制按场景域覆盖人流拥挤、登离船调度与接驳中断等各类事件。

#### III-3 机制拆解与绘图参考（v1.0 补充 · 绘图工作稿，不进页面正文）

**1. 机制定位**

| 部件 | 职责 | 输入 | 输出 |
|---|---|---|---|

**3. 两段式生成主链（本页主图）**

第一段 · 语义组合（AI 增值区）：

```text
[1] 影响评估    C2.1 确定性内核：影响人数 / 资源缺口 / 时间窗
[2] 知识检索    C2.3 策略库 / 条款库 / 事故记忆（条款编号 R8）
[3] 动作组合    从动作库 A01–A19 选动作 + 编排次序

[4] 备选生成    C2.2 候选 A/B/C（差异标注：约束 / 资源 / 口径）
[5] 附件挂载    C2.4 推理附件（读了哪些信号 / 算了什么 / 引哪条条款 / 置信度 / 备选对比）
```

第二段 · 实例化求解（确定性区）：


**4. 双重约束（本页核心概念，建议作视觉主线）**

- **分区语义**：AI 区（组合 / 识别 / 解释）与确定性区（算术 / 求解）用不同底色区分，中间画"AI 不参与算术"分界线。

### III-4b 人审闭环与修订回路（Human Review Loop）〔初稿〕
> 英文标题（完整）：Human Review Loop and Revision Cycle (Single Approval Principle)
> 缩写沿用：Human Review Loop

- **标题**：人审闭环与修订回路——一次审批、受控修订、超时兜底
- **一句话**：方案由决策层审批一次；不通过时按"三形态"修订重审；超时按双路径收口——不让流程死锁，也不让风险无声。
- **图上要传达的要素**：
  1. 审批状态机主图：待审 → 通过（=确认基线，交 III-5）→ 驳回 → 修订 → 重审（R1→R2…循环）；任一步可转人工接管（旗标，III-7 详讲）；
  2. **修订三形态**三小卡：改参数（重算受影响部分）/ 换备选（A/B/C 之间）/ 调整动作（动作库里选）——共同点：都不是"让 AI 重想一遍"；
  3. **超时双路径**两出口：常规 → 默认执行 + 事后审计；涉风险 → 自动升到更高审批；
  4. 每次修订的痕迹：diff + 原因 + 轮次编号（页脚小注）。
- **关键点**：决策审一次、执行不重复审（效率与责任）；修订=受约束编辑（可审计）；不默认 AI 重推（时间与确定性）。
- **边界**：升 L4 后不再"修改-重审"循环（一次决策、事后补签）。
- **对照格（P9-2）**：日常事件审批时限更短（分钟级），同一状态机。

### III-4c 异常升级机制（Escalation Path）〔初稿〕
> 英文标题（完整）：Escalation Mechanism (Control Transfer Pathways)
> 缩写沿用：Escalation Path

- **标题**：异常升级机制——审批超时与状态恶化两条上坡路，收口于更高决策层
- **一句话**：事件等级上升只有两个触发：批不下来拖超时了（审批侧），或情况真的恶化了（状态侧）；两条路最终都指向同一出口——更高一级的人/船长决策区。
- **图上要传达的要素**：
  1. **路 A（审批超时）**：审批倒计时 → 超时 → 升级上一级（L2→L3→L4），附时限参照（30–60 分钟量级，来源小注：应急管理/民航延误惯例）；
  2. **路 B（状态恶化）**：监控判"物理劣化/安全阈值" → 升等级（如 L2→L3、拥挤→安全事件）→ 画升级线（时间轴"关系 A"）；
  3. 两路汇于"更高层决策 / 船长决策区"；
  4. 升级必带痕迹：谁触发、为什么、超时多久/哪个阈值。

- **边界**：升级不是惩罚，是"不留死区"的保障。
- **对照格（P9-2）**：日常事件超时升级同样生效，只是时限更短。

| C5.2 监测模式 P1（现场端口） | 盯本系统感知端口（排队 / 闸机 / 设备） | 事件发生与恢复看同一批端口，**自证自闭环**；复检判据可与 C2.5 模型预期曲线对照（预期 vs 实测偏差） |
| C5.3 监测模式 P2（外部信息源） | 盯外部传入源（船期 / 港口窗口 / 天气） | **可读性分层**：源可读 → 判"是否仍成立"；不可读 → 用影响副作用（排队 / 接驳余量）代测；仍不可读 → 人工接管 + 最小登记 |
| C5.4 周期复检 | 挂起后按周期重新判定 | `still` 仅记日志 ｜ `recovered` 关闭监测 ｜ `upgrade/accident` 派生（走 C5.6） |
| C5.5 循环提醒 | 挂起 / 接管期不无限静默 | 态势快照 + 一句标准建议；连续 N 次未解除 → 升更高层知会 + 提频 |

**3. 状态机拆解**

```text
执行中 → 恢复（绿点闭合）
       → 挂起（琥珀空心点）→ 周期复检（虚线环）
             ├─ still：仅日志
             ├─ recovered：关闭
             └─ upgrade：派生事件 → 升级线（III-4c 出口）
长期未决 → 循环提醒升级（值班 → 运营经理 → 船长知会）
```

**4. 图上信息层级**

- 主链层：状态机（执行中 / 恢复 / 挂起 / 复检）；
- 部件层：P1 / P2 双栏对比表 / 复检三出口；
- 标注层：任务型（墙钟）vs 持续型（物理劣化）判据注记、监控轻负载注记（呼应 III-5b）。

**5. 绘图要素清单**

- **状态机主图**：三出口线型区分——记日志 = 虚线回环 / 恢复 = 绿点 / 恶化 = 升级线箭头；
- **P1/P2 双栏**：左"看谁"（自己端口 vs 外部源）、中"怎么判"、右"判不动怎么办"（P2 的可读性分层三级递降是画面重点）；
- **模型锚点注记**：P1 复检对照预期曲线（衔接 III-3），表达"监控有模型基准，不是纯阈值"；
- **防误读注记**：挂起不画矩形占车道（琥珀空心点即可）——可视化纪律本身来自 §4.2.3 用户拍板。

**6. 术语对照**

- 运行监测与状态恢复（Observability & Recovery）
- 挂起即闭合（Suspend-as-Closed）
- 自证闭环（Self-verifying Loop，P1）vs 可读性分层（Source-readability Layering，P2）

### III-7 人工接管机制（Human Override）〔初稿〕
> 英文标题（完整）：Human Override Mechanism (Copilot + Dashcam Mode)
> 缩写沿用：Human Override

- **标题**：人工接管与可控性兜底——任意节点可接管，系统退居观察 / 记录 / 建议
- **一句话**：任何节点人都可以一键接管，把执行交回船司现有系统；系统不消失，而是变成"副驾驶 + 行车记录仪"。
- **图上要传达的要素**：
  1. 四个触发口图标：审批时主动接管（最常见）/ 超时后接管 / 系统故障降级时 / 现场先处置后补录；
  2. 接管后状态图：系统转三件事——观察（继续读数据）/ 记录（时间线自动记）/ 建议（标准流程"如果照做会怎样"，仅供看）；执行走既有 UHF 对讲 + PA 广播 + 乘客 App 推送
  3. 最小登记示意：人只需一句"已启动人工接管，处置单 #xxx"，不填表单；
  4. 循环提醒：接管后系统持续提醒，N 次未解除 → 自动升更高层知会（人想静默也不行）。
- **关键点**：接管=执行权移交、审计不中断（痕迹继续记）；原有调度系统就是人工接管端口。
- **边界**：接管不取消时限压力；事件仍受监控直至恢复。
- **对照格（P9-2）**：现场领班觉得系统建议不适合实际 → 一键转人工按老办法做，系统只记录。
