## 第 1 页：产品定位与价值主张

### 页面目标

让读者第一眼知道：ClarSyn 是什么、给谁解决什么问题、核心价值是什么。

### 核心信息

- 一句话定位：把船↔岸交界的混乱，变成分钟级清晰决策。
- 产品性质：面向邮轮公司的港岸协同决策层，不是导航工具，不是聊天机器人。
- 核心记忆点：看见没见过的、推演没写过的、解释说不清的。

### 正文内容

1. 产品名称：ClarSyn
2. 中文定位：基于多 Agent 协同的邮轮靠港接驳动态调度系统
3. 英文定位：Multi-Agent Collaborative Dynamic Scheduling System for Cruise Berthing & Shore Connection
4. 一段 3 行式说明：
   - 谁：邮轮公司运营决策层
   - 场景：登离船、港口接驳、航变响应
   - 价值：多源信息快速汇聚、弱信号提前发现、影响推演与预案准备、全链路审计
5. 一句话收束：AI 建议，人审批，全链路审计。

### 呈现方式

- 左：品牌与标题文字
- 右：船长端 / 运营端深色 UI 缩影
- 底部：3 个价值标签
- 形式：图 + 文 + 标签，不堆正文

## 第 2 页：宏观设计背景

### 页面目标

用简洁的宏观叙述解释：为什么邮轮行业、为什么是船岸交界、为什么是现在。

### 核心信息

中国邮轮市场正在复航与新船交付期，船↔岸交界是体验断裂最明显、利益链最长、决策最依赖人工跨系统核对的环节。

### 正文内容

1. 行业背景：
   - 中国邮轮市场复航，新船陆续交付，乘客规模大；
   - 船岸交界是登离船、接驳、航变等多类问题集中爆发的地方；
   - 邮轮公司、港口、OTA、旅行社、本地交通、政府监管共同构成复杂利益链。

2. 利益链相关方：
   - 邮轮公司：承担品牌、客诉、合规与赔偿风险
   - 乘客：关注等待时间、信息透明、行程确定性
   - 港口：负责通关、接驳、交通秩序
   - OTA / 旅行社：承担销售与退改沟通
   - 本地交通：出租车、网约车、短驳供给
   - 政府 / 监管：关注公共秩序、乘客权益、交通治理

3. 为什么是现在：
   - 2026 年航变与港口接驳是官方与媒体双确认的持续痛点；
   - 本地小模型、气象 API、RAG 等技术条件成熟；
   - 新船前装设计窗口允许我们把 AI 决策层作为系统能力设计进去。

4. 宏观判断：
   - 邮轮公司不缺单一信息系统，缺的是把多源信息变成决策依据的协同层。

### 呈现方式

- 上半页：一段宏观叙述文字 + 3 个关键行业标签
- 下半页：一张利益链示意图（邮轮公司 / 乘客 / 港口 / OTA / 交通 / 政府）
- 呈现：文为主，图为辅，信息量克制

## 第 3 页：研究流程

### 页面目标

用一张总体研究流程图说明：整个项目经历了从行业认知、问题定义、用户调研、证据验证、业务梳理、目标确认、AI 匹配、方案细化到验证迭代的完整研究过程。

### 核心信息

ClarSyn 的研究路径不是“先有方案再找问题”，而是多源证据、业务边界和 AI 能力反复收敛后得出的产品判断。

### 正文内容

1. 总体研究流程主链（九段）：

```text
宏观行业研究
→ 问题定义与场景锁定
→ 用户与干系人调研
→ 痛点证据收集与交叉验证
→ 业务梳理与系统边界
→ 目标确认与指标假设
→ AI 能力匹配与技术边界
→ 方案细化与原型设计
→ 验证迭代与试点路径
```

2. 每个阶段的输入与输出：

| 阶段 | 输入 | 输出 |
|---|---|---|
| 宏观行业研究 | 邮轮市场、参考船型、媒体报道、官方答复 | 行业利益链认知、重点场景判断 |
| 问题定义与场景锁定 | 宏观背景、行业断点 | 登离船 / 港口接驳 / 航变三类核心场景 |
| 用户与干系人调研 | 船长、运营、客服、法务、乘客、港口角色 | 用户任务、采购者、决策链与使用链 |
| 痛点证据收集与交叉验证 | 公开资料、用户 UGC、媒体调查、政府答复 | 痛点清单、证据等级、三类痛点聚类 |
| 业务梳理与系统边界 | 现有系统、接口现实、组织权限 | 系统边界、数据三态、接口关系图 |
| 目标确认与指标假设 | 基线证据、业务目标 | 设计目标区间、显式假设、验证口径 |
| AI 能力匹配与技术边界 | Hackathon 高分案例、竞品方案、技术可行性 | AI 三高地、规则与 AI 边界、模型选型 |
| 方案细化与原型设计 | PRD、AI 架构、事件治理框架 | M1–M6 方案、多 Agent 架构、高保真原型 |
| 验证迭代与试点路径 | 62 条事件案例、指标假设、高保真原型 | 演示链路、评测结果、单港试点路径 |

3. 研究方法标签：

- 桌面研究
- 多源交叉验证
- 案例挖掘
- 产品三角验证（业务证据 × AI 能力 × 工程边界）

4. AI PM 视角：

- 先证明“我如何理解行业”
- 再展示“我如何定义问题、调研用户、验证证据”
- 然后说明“我如何梳理业务边界、确认目标、判断 AI 边界”
- 最后落到“我如何细化方案、设计原型并验证迭代”

### 呈现方式

- 主视觉：总体研究流程图（九段纵向主链 + 每段下方输入/输出小卡）
- 也可使用“两行蛇形流程图”控制页面高度

## 第 4 页：问题证据与痛点聚类

### 页面目标

证明“问题是从真实证据和调研中得出的”，而不是根据产品反向推导。

> 注：总体研究流程已在第 3 页展示，本页聚焦证据渠道、证据等级与痛点聚类。

### 核心信息

通过公开资料、媒体报道、用户评论、官方答复等多渠道交叉验证，船岸交界的问题不是单一排队，而是多系统、多角色、多时段的信息割裂。

### 正文内容

1. 研究流程回顾（详见第 3 页）：

```text
公开资料 → 媒体报道 → 用户评论 → 官方答复
→ 多源交叉验证 → 证据等级标注 → 痛点聚类
```

2. 证据渠道与代表要点：

#### 官方答复 / 官方资料

- 宝山区政府连续两年在公开答复中承认吴淞口国际邮轮港存在“交通秩序、停车难、短途出租运营模式”问题，说明港口接驳不是偶发个案，而是跨年份未根治的系统性问题。
  - 来源：宝山区政府 / 上海市政府门户（2025-03、2026-03）
- 爱达邮轮官方《岸上游指南》以 55 页静态 PDF 下发，各港接驳方案差异明显：有的港口提供免费短驳，有的为付费接驳，有的仅有出租车。
  - 来源：爱达邮轮官方手册（2026-08）

#### 媒体报道

- 新闻晨报 / 网易调查发现，吴淞口邮轮港存在“出租车近的拒载、远的宰客”现象；司机侧也在抱怨“苦等两小时接一单仅赚 48 元”，说明问题同时影响乘客与运力供给两端。
  - 来源：新闻晨报 / 网易（2025-08-04）
- 新浪财经 / 扬子晚报报道 2026 年台风“白海豚”事件：魔都号数百人拒不下船，后续出现“万元房费仅赔千元”的赔偿争议。
  - 来源：新浪财经 / 扬子晚报（2026-08-07）
- 新京报曾报道邮轮船票退改条款苛刻，以及法院判旅行社全额退款的判例，说明航变退赔已存在可引用的规则与司法依据。
  - 来源：新京报（2025-07-24、2026-03-29）

#### 用户评论（含平台来源）

- 携程差评（爱达地中海号）：“离船回国更是一场战斗……从 8:00 要求我们离开房间，到我们下船 15:00 才出来，中间 6–7 个小时没有一杯水一次餐饮。”
- 携程差评（爱达地中海号）：“福冈下船按岸上游顺序排队，从 11:30 到下午 3 点多下船，足足排了 3–4 小时。”
- 携程差评（海洋光谱号）：“船司提前 16 小时通知目的地变更，而携程邮件在航程前 2 小时、电话在前半小时才通知；乘客只能在两种吃亏方案里选。”
- 小红书评论（爱达魔都号）：“当时叫到了 28 号，派给我是 49 号，一直到 2 点 10 分才开始登船手续……”说明已有叫号分批机制，但信息不透明、无法动态调整。

#### 由公开证据推导的基线估算（待船司数据校准）

> 以下数字不是实测结果，而是基于公开事件链与运营参数进行的推演估算，用于量化问题量级；正式值需要船司真实数据校准。

- 一次航变发生后，运营人员需要分别打开船期系统、气象平台、港口接驳资料和乘客清单，再通过电话、对讲机向多个部门确认，才能形成一份可供决策的整体情况。基于现有流程推断，这一过程约需 20–45 分钟。
- 按 5000 人级船舶、约 10% 乘客需要逐批沟通、每人约 5 分钟估算，航变后逐批解释约需 8 名客服连续工作 5 小时以上。

3. 痛点总结：

- 体验/秩序：登离船等待长、接驳不确定、现场拥挤
- 效率/人力：跨系统核对慢、逐批沟通、口径不一致
- 风险/合规：航变群体事件、赔偿争议、信息真空

4. 总结判断：

这三个聚类不是三个独立问题，而是“船岸交界缺少统一决策信息层”的三类表现。

### 呈现方式

- 中部：研究流程回顾小带（从第 3 页浓缩）
- 左侧：证据渠道与代表要点列表（每条标注来源平台/媒体）
- 右侧：痛点聚类卡（体验 / 效率 / 风险）
- 底部：总结判断条
- 呈现：表 + 列表 + 图 + 文，重点突出“来源可溯”和“估算有推导依据”

## 第 5 页：业务理解

### 页面目标

在原第 3 页“利益链与信息流”基础上，进一步理解现有业务架构，并明确 ClarSyn 的采购者、使用者、系统边界与可干预范围。

### 核心信息

ClarSyn 不是接管港口、海关、交管的超级系统，而是在邮轮公司权限范围内、基于现有业务架构增加一个协同决策层。

### 正文内容

1. 利益链与信息流（原利益链页内容并入）：

- 邮轮公司：拥有乘客触达渠道和内部调度权
- 港口：拥有通关、泊位、接驳现场资源
- OTA / 旅行社：掌握销售与退改沟通
- 乘客：处于信息接收末端，等待确定性与透明性
- 当前关键断点：
  - 船司内部信息分散在船期、预订、客服等系统；
  - 港口数据不可得或静态；
  - 乘客端缺乏统一、实时、可追溯的信息。

2. 现有业务架构理解：

- 船司内部角色：船长、运营经理、值班/客服、法务
- 现有系统：船期管理、预订/POS、乘客 App、客服系统、港口静态资料
- 外部机构：海关、边检、港调、交管
- 接口现实：外部系统给什么数据，我们就基于什么能力设计

3. 用户与采购者：

| 角色 | 类型 | 核心任务 |
|---|---|---|
| 邮轮公司运营/数字化部门 | 采购者 | 选择可落地、可审计、可降级的解决方案 |
| 船长 | 使用者 | 需要可追溯的拍板依据 |
| 运营经理 | 使用者 | 需要分钟级态势与预案 |
| 值班/客服 | 使用者 | 需要统一事实与条款依据 |
| 法务 | 使用者 | 需要可审计的决策链路 |

4. 系统边界：

- 管：
  - 船方乘客触达渠道
  - 船司内部调度
  - 可合法获取的气象、船期、港口静态资料
- 不管：
  - 不指挥海关/边检/港调/交管
  - 不替代港口或口岸系统
  - 不处理与船岸调度无关的客服事件
- 数据三态：
  - 真实可用
  - 待接入
  - 不可得（不假设、不假装）

5. 业务理解收束：

> 我们不是在真空中设计系统，而是在现有业务架构里找一个“船司有权、有责、有利”的决策层位置。

### 呈现方式

- 上半页：利益链 + 信息流断裂图（原第 3 页内容）
- 中左：现有业务架构与系统关系图
- 中右：用户与采购者 JTBD 表
- 下部：管 / 不管 / 数据三态边界区
- 呈现：图 + 表 + 文，页面信息量较大，但分区清楚

## 第 6 页：AI 机会判断

### 页面目标

在业务理解之后，回答“为什么规则系统不够、AI 到底补了什么”。

### 核心信息

在可干预边界内，最大瓶颈不是“没有系统”，而是“没有能发现弱信号、推演复杂影响、解释决策理由的协同层”。

### 正文内容

1. 最大瓶颈：

- 多源信息割裂：气象、船期、港口、客服分散在不同系统；
- 事件组合复杂：单个信号正常，组合起来可能是航变风险；
- 决策口径不统一：人工逐批沟通导致说法不一致。

2. 为什么规则系统不够：

- 规则系统看不见库外异常；
- 规则系统推演不了没写过的组合；
- 规则系统解释不了“为什么选这个方案”。

3. AI 的三块不可替代高地：

| 高地 | 一句话 | 对应价值 |
|---|---|---|
| 开放域异常发现 | 看见没见过的 | 库外异常提醒，只提醒不执行 |
| 长链路推演 + 弱信号整合 | 推演没写过的 | 影响预测与预案准备 |
| 推理附件 / 可解释性 | 解释说不清的 | 每个 AI 判断都带理由、置信度、证据 |

4. 人机协同边界：

- AI 负责：快速调用信息、发现弱信号、影响推演、方案组合、解释推荐理由
- 人负责：审批、接管、最终决策
- 系统负责：审计、留痕、超时升级

5. AI 机会收束：

> 我们不是用 AI 给规则引擎化妆，而是把系统立在规则引擎到不了的三块地上。

### 呈现方式

- 上部：规则系统能做到 vs AI 增量对比表
- 中部：三高地图（每个高地配一句话 + 一个小案例标签）
- 底部：人机协同闭环条（AI 建议 → 人审批 → 审计回流）
- 呈现：表 + 图 + 文，核心金句单独放大
