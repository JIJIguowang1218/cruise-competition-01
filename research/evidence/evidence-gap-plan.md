## 1. 总判断

**同意用户的判断：先补齐证据链，再收敛边界。** 理由：

1. `scope-and-boundary.md` 的 6 个待讨论问题中，5 个直接依赖"现有系统的真实状态"（App 接口、船上系统、港口数据、航变 SOP、预订系统）——这些正是 source-archive 各文件"待补强"清单的内容；
2. 证据线 A（旧模式基线）是 `ai-value-case.md` 双线论证中唯一未完成的半边，而它又决定"AI 增量"的说法能不能立住；
3. 若不先补，收敛边界时会产生大量"等资料"的悬空决策，回头返工成本更高；
4. 但注意"补齐"不等于"补到完美"：登录墙/付费/访谈类资料受时间与资源限制，应分级处理（见 §6）。

## 3. 证据线 A（旧模式基线）补法

### 3.1 定位与素材来源

为 ai-value-case §2 表内 5 个场景各写一行"没有我们的系统时，真实运营链路"。素材来源：

| 来源 | 提供什么 |
|---|---|
| source-archive 01–05 场景化描述草稿 | 现状链路叙事雏形（船员用对讲机确认餐厅状态、分层下船靠广播、客服逐批解释等） |
| reference-ships.md / ②流船型基线 | L2 物理基线：魔都号 9 餐厅（3 免费自助）、最大餐厅 1500 人、载客 5246、船员 1292；花城号 5232 人/2130 客房 |
| 08 竞品流 | 现有数字化基线：通关 10 秒、AI 无感登船、App 值船/预订/导航/消息、V-Count/Outsight 感知组件存在 |
| v3/turnaround（PT） | 补给/翻台时间窗极紧（Moderate） |
| UGC（04/05 流） | 可量化等待（"靠岸到码头 1 小时、分层下船再等近 3 小时"）、付费升舱避排队（付费意愿） |
| 国际参照（🔴 用户提醒 2026-08-17） | 对照各国最好/最普遍做法：⑧流 P1–P7（国际 App/机场/主题公园/感知组件）+ 04b 国际 UGC + 09 国际项目；检索方案见 `key-items-public-search.md` §6 |

> 基线结论的写法：每个场景 = **国内现状**（现状链路，本节表格）+ **国际参照**（§8.1 表）两栏；AI 增量 = 相对两者的差距，缺一不可。

### 3.2 每条基线的填写模板（证据分级）

| 字段 | 说明 |
|---|---|
| 现状步骤链 | 谁→做什么→用什么工具→耗时/延迟 |
| 信息回路 | 数据在哪、怎么流动、船员/乘客看到什么 |
| 人工成本 | 多少船员的多少小时（可量化才写） |
| 已知痛点证据 | 引用 source-archive 编号 + 证据等级（L0/L1/L2） |
| 待验证项 | 无公开证据的环节 → 标注"用户研究假设"，不写死 |

### 3.3 纪律（沿用 round2 标准）

- 不使用专家直觉当证据：每条标注 L0–L3；L3 推断不得作为结论依据。
- 与 v3 §8 的红线对齐：不引用复购率 20–30%、800 人剧院（更新为"近千人"）、5.5 万设备等已禁数字。
- **连带修正**：`research/scenarios/reference-ships.md` 仍写"800 人大剧院"，与 ②流"近千人"冲突，需同步更新；`design/direction-1-deep-dive.md` 含旧数字与单餐厅叙事，等证据线补完后按升级版范围重写（gate1 待办已列）。
