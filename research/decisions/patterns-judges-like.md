# 评委喜欢的产品模式 — 从30个黑客松作品提炼

> 从 Hackathon-reading 的 Rapid Agent(21篇) + Gemini3(10+篇) 分析中提炼。
> 用途：为邮轮竞赛方案设计提供"评委买账什么"的叙事参考。

---

## 一、正向模式（6个）

### 模式1：AI感知 + 确定性计算分离

**代表作品**：Spatial Engine (B+/61)、AMRShield (A/80)、Scam Swarm (A/84)

**核心逻辑**：让 AI 做它擅长的（看图、读文字、做判断），让确定性公式做 AI 不擅长的（物理计算、规则匹配、精确算术）。

Spatial Engine 用 Gemini Vision 识别窗户尺寸和朝向，但热传递计算用硬编码物理公式；Scam Swarm 用规则引擎检查 URL 黑名单和关键词，LLM 只做语义理解；AMRShield 用 Cockcroft-Gault 公式计算肾清除率，Gemini 只做语义级的指南合规审查。

**评委为什么买账**：这证明你理解 AI 的边界——你不是"把问题丢给 AI 就完事了"，而是知道什么时候该信任 AI、什么时候该用传统方法。

**邮轮场景映射**：客舱温度优化（AI 识别热源分布 + 流体力学公式计算气流）、能耗预测（AI 识别使用模式 + 电力工程公式计算负载）。

---

### 模式2：多Agent协作，但每个Agent职责单一

**代表作品**：Globot Shield (A/81)、Scam Swarm (A/84)、AMRShield (A/80)

**核心逻辑**：不是"一个万能 Agent 解决一切"，而是多个 Agent 各自专注一个领域，然后汇总。Globot Shield 的五个 Agent 分别负责市场感知、物流调度、金融对冲、合规审查和红蓝对抗辩论。Scam Swarm 的三个"侦探"各自审查消息的不同维度（链接/心理/金融）。

**评委为什么买账**：容易理解、容易演示。"这个 Agent 在看卫星图、那个 Agent 在算期权价格"——评委3分钟就能建立起心智模型。

**邮轮场景映射**：安全预警系统（一个 Agent 看监控画面、一个 Agent 查船员排班、一个 Agent 分析乘客行为模式）。

---

### 模式3：闭环自主决策循环

**代表作品**：Synt (A/87)、Globot Shield (A/81)

**核心逻辑**：不是"AI 给个建议然后等人点确认"，而是 AI 自己循环：观察→判断→决策→行动→再观察。Synt 的 OODA 循环（Observe/Orient/Decide/Act）让 Agent 持续调查直到所有假设被确认或排除。Globot Shield 的红蓝对抗辩论让系统内部交叉验证。

**评委为什么买账**：这展示了 AI 的"自主性"——不是被动回答问题，而是主动推进流程。而且循环本身就是一个很好的 Demo 叙事框架。

**邮轮场景映射**：设备故障预警（监测→识别异常→评估影响→建议行动→跟踪结果→迭代学习）。

---

### 模式4：预写场景承载能力展示

**代表作品**：Globot Shield (A/81)

**核心逻辑**：不用让 AI 实时生成所有内容。用一个精心设计的场景（霍尔木兹海峡扣船、4:55PM 危机时刻）承载所有 AI 能力的展示。数据是 mock 的，但产品逻辑是真实可部署的。

**评委为什么买账**：Demo 不翻车。评委不需要关心"这个数据是假的"，他们在乎的是"这个产品逻辑讲不讲得通"。Globot 团队的"High-Fidelity Mock"策略是 Hackathon 的正确选择。

**邮轮场景映射**：设计一个"邮轮厨房制冷故障，AI 在15分钟内完成故障定位→影响评估→备件调配→替代方案"的场景。

---

### 模式5：推理过程透明化

**代表作品**：Synt (A/87)、Globot Shield (A/81)

**核心逻辑**：不让 AI 给一个"黑箱结论"，而是让用户看到 AI 每一步在做什么。Synt 的"推理剧场"界面同时展示 AI 的思维流、图数据增长和最终报告。Globot Shield 的打字机式思维链让用户看到每个 Agent 在干什么。

**评委为什么买账**：解决了 AI 最核心的信任问题。评委（尤其是非技术评委）看到 AI"正在查询福冈港口天气数据"比看到"建议改道好望角"更有说服力。

**邮轮场景映射**：任何涉及 AI 建议的场景都可以加"推理链"展示层。

---

### 模式6：TurboTax类比 — 低端颠覆

**代表作品**：Spatial Engine (B+/61)

**核心逻辑**：不跟现有巨头正面竞争。不试图替代人类专家，而是服务"请不起专家"的长尾市场。Spatial Engine 不挑战 Autodesk——它帮"请不起能源顾问的小业主算电费"。TurboTax 没有取代 CPA，它只是让简单报税不用请 CPA。

**评委为什么买账**：展示了产品思维，不是技术炫耀。"我们不替代船长，我们帮大副做他每天做但没时间做好的事情"比"AI 驾驶邮轮"更可信。

**邮轮场景映射**：AI 不是替代船员，是帮船员处理"重复但必需"的工作（设备巡检、排班优化、库存清点）。

## 二、反面模式（4个）

### 反模式1："电影布景" — UI精美，AI是假的

**代表作品**：CityGuard AI (C/45)、Agentic Essay Evaluator (D/34)

**症状**：前端动画精美，但按钮点击后渲染的是硬编码数据。Agent 推理步骤是预先写好字符串而非实时生成。"Run Scenario" = `setTimeout(resolve, 600)`。

**为什么会死**：Hackathon 评委见过太多精美 Demo。他们会优先检查"AI 真的在工作吗"。一旦发现 AI 是假的，前面所有 UI 努力归零。

**邮轮场景警告**：不要做一个"看起来在监控邮轮"的 Dashboard 而实际数据全是 mock。

---

### 反模式2："Multi-Agent贴纸" — 五个Agent其实是同一个prompt

**代表作品**：NeuroStudy AI Agents (C/52)

**症状**：声称"五个 AI 老师同时给你上课"，实际是同一个 LLM 调了五次，每次 prompt 改几个词。没有 Agent 间通信、没有并行执行、没有编排。`agent_manager.py` 是空文件。

**为什么会死**：Multi-Agent 是有真实工程含义的——编排、通信、分工、状态管理。如果只是"调五次 API"，评委一眼看穿。

**邮轮场景警告**：如果方案说有3个 Agent 协作，必须能说清楚它们之间怎么通信、谁等谁、不一致时谁决定。

---

### 反模式3："MCP标签" — 声称用了MCP但实际没接入

**代表作品**：MallCore Agent (C/45)、CityGuard AI (C/45)

**症状**：README 列出 Google Cloud MCP、Elastic MCP、MongoDB MCP，但 `package.json` 里一个 SDK 都没有。声称 MCP 是提高"技术深度"分的捷径，但评委能看出来。

**为什么会死**：MCP 是一个实现细节，不是产品价值。评委关心的是"你解决了什么问题"，不是"你用了什么协议"。

**邮轮场景警告**：不要把"5G+卫星 MCP"、"AIS 数据 MCP"作为方案亮点——说清楚它们帮你解决了什么问题。

---

### 反模式4："1次提交" — 没有迭代的项目是快照，不是产品

**代表作品**：NeuroStudy AI Agents (C/52)、CityGuard AI (C/45)

**症状**：Git 历史只有1个 commit。说明整个项目是一次性批量生成的，没有迭代、没有重构、没有 Bug 修复。没有 Git 历史 = 没有"产品如何演化的故事"。

**为什么会死**：评委不仅看最终结果，也看"这个团队是怎么工作的"。好的 Git 历史（小步提交、有重构、有 Bug 修复）本身就是最好的项目文档。

**邮轮场景警告**：即使是一个人做，也要用小步提交展示思考过程。
