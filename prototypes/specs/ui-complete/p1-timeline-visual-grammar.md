## 0. 坐标系与对齐规则（必须严格一致）

- **横向 = 时间**：左 = 更早，右 = 更晚。右侧一根**实时竖线**贯穿所有车道，代表"当前时刻"。
- **底部时间轴**（位于 L1 车道与 X·库外 车道之间）与实时竖线**构成同一坐标系**：
  - 时间轴左端 = 车道背景左边界（同一 x）；
  - 时间轴右端（刻度"现在"）= 实时竖线所在 x，实时竖线必须**垂直落于刻度"现在"上**，不得错位。
- **车道背景**：每个等级一条浅灰背景矩形；所有车道的左右边界 x 一致（左 = 时间轴左端，右 = 实时竖线）。
- **事件矩形边界约束**：任何事件矩形/线段**必须完全落在所属车道背景之内**（左右不越界、上下不出车道）。
- **等级标签位置**：固定在车道背景**左侧外部**、垂直居中于该车道；任何时候不得随内容移动。

## 1. 车道分配（当前船长视角 v1）

| 车道 | 位置 | 相对高度 | 承载事件数（当前示例） |
|---|---|---|---|
| L4 | 最上 | 最窄 | 1 |
| L3 | 上 | 较窄 | 2 |
| L2 | 中 | 中等 | 5 |
| L1 | 下 | 最宽 | 9–10（细条堆叠） |
| X·库外 | 最下（时间轴之下） | 独立 | 只提醒，虚线框 |

- 高度向下递增以容纳低等级的大量事件；**高等级车道在上且窄**（当前取向，待用户最终确认是否改为按角色自适应）。
- 同级事件矩形条高一致；多事件在车道内**按行错开，禁止重叠**。

## 2. 基础事件图形语法（正常事件）

一个基础正常事件从左到右 = **至少：发现段 + 移交竖线 + 执行段 + 恢复点/开放末端**。

```
  ┌───────发现段───────┬───────执行段───────┐
  │   (识别色)   ❘(移交竖线)  (执行色)    ❘  ※端线
  └──────────────────────────────┘  ●恢复点(绿点,端线中点)
```

- **发现段**：事件矩形开头，识别色。
- **移交竖线**：一道比事件条稍高/稍粗的**竖向线**，正常交接 = 绿色；紧贴发现段右端。
- **执行段**：执行色。
- **恢复点**：执行结束且观测到数据恢复时，在**末尾竖线中点**画一个**绿色圆点**。
- **开放事件**（仍在执行中、未结束）：右边直达实时竖线，**无端线、无恢复点**。
- 事件矩形上**不写字**（"发现/执行/恢复"等字样一律不放）。

## 3. 异常事件图形语法

```
  ┌──发现段──┬──执行段──┬──────────────────────┐
  │识别色  ❘ 执行色  ❘(异常红竖线)  异常段(红)   │
  └──────────┘        └──────────────────────┘
```
- **交接异常竖线**：红色、比正常移交竖线**更长/更醒目**；其后转为**异常段（红色）**。
- 异常事件**只有最终结束**（数据恢复/处置闭环）才在端线中点出现绿点；未结束则红段直达实时竖线。

## 4. 升级事件图形语法（重点，务必按此）

- 下级事件**异常段末端**（"末尾红色竖线"）→ 从这里**向上**连到上一级车道，红色连线为**实线**（非虚线）。
- 上级事件矩形**开头（左边缘）就从红竖线落点处开始**，按"发现段"识别色向右生成；连读即：**红竖线落点 = 上级矩形左起点**。
- 即：`下级红段终点 ──红色实线↑── 上级发现段起点（同 x）`。
- 上级事件随后按基础语法推进（移交竖线/执行段/恢复点）。

## 5. 状态 → 颜色对照（低保真阶段临时取值）

| 状态 | 图形 | 色（hex） |
|---|---|---|
| 发现/识别/待处置 | 发现段 | #f5a623（琥珀） |
| 正常移交 | 移交竖线（稍高/稍粗） | #57be6c（绿） |
| 执行中 | 执行段 | #57be6c（绿） |
| 已恢复 | 端线中点绿点 | #2e8b57（深绿点） |
| 交接异常 | 红色竖线（更高/更醒目） | #e53945（红） |
| 异常持续 | 异常段 | #e53945（红，可半透明） |
| 升级传导 | 红色实线↑接上级开头 | #e53945（红，实线） |
| 库外异常 X | 虚线框（X 车道内） | #4a7fbf（蓝虚线框） |

## 6. 禁止事项（返工红线）

- 事件矩形上不得有文字。
- 同级事件条高/分段比例不得随意不一致。
- 事件不得越出车道背景、不得与实时竖线/时间轴错位。
- 等级标签位置不得随意变动。
- 升级连线必须是实线且接到上级矩形开头（不是接到上级矩形末端/任意处）。

## 8. v2 修订（2026-08-20 用户二轮，取代 §1/§2 中冲突处）

> 用户强调"理解再动手"。以下为本轮强制规则；与上文冲突处**以本节为准**。

### 8.1 统一细高（关键）
- **所有等级的所有事件矩形高度完全一致、一样细**（取 L1 的细度）。不得为了强调高级别而把矩形加高/加粗。没有任何拉伸/加高要求。
- 行与行之间拉开距离，不得挤在一起（靠车道内的虚线导轨定位）。

### 8.2 虚线导轨 / 车道高度按比例
- 每个等级灰色背景内，画**与背景等宽的水平灰色虚线**若干条；事件矩形就落在这些虚线之上。
- 固定条数（本轮）：**L4=2、L3=4、L2=6、L1=10**。
- **每个等级车道的高度由其虚线条数按比例决定**（不能随意定）：条数越多车道越高（L1 最高、L4 最矮）。
- 事件行就座落在某一条虚线上（一行可空置，事件分散不重叠）。

### 8.3 正常结束 = 恢复点，不要黑竖线
- 事件正常结束（数据恢复）只在**末端放一个绿色恢复点**。
- **禁止在事件末尾画黑色/深色短竖线**（去掉端线；恢复点自身即结束标记）。

### 8.4 升级红线必须真正接上
- 上级事件矩形的**左起点**与下级异常红段的**右末端**必须处在**同一条 x（同一垂直线上）**，红色实线从下级矩形末端**无缝**连到上级矩形起点，**不能有缝隙/错位**。

### 8.5 库外（X）事件
- X 事件用**灰色矩形**表示（不是蓝/虚线框）。
- 行为：观察中 → 继续向右延长；**决定升级 → 按升级画法画**；**决定忽略 → 直接停止延长**。
- **X 事件矩形附近不得有任何文字**（车道标签除外）。

### 8.6 时间轴 = 半小时实时时刻标点
- 时间轴标点用**真实时钟时刻**、每半小时一个，自实时竖线（当前时刻，如 06:00）**向左**推移：05:30、05:00、04:30……
- 不是"提前 N 分钟"的负数表述，而是"哪个时刻"。
- 例：实时竖线=06:00，左邻=05:30，再左=05:00，以此类推。

### 8.7 事件分布
- 各事件长度与前后位置尽量分散、留白，不要挤成一团。

## 9. v3 精细修订（2026-08-20 用户三轮，取代冲突处）

1. **虚线垂直居中**：每级车道内的虚线组必须**在该级灰色矩形内上下居中**（顶部与底部留白相等），不得偏上或偏下。
2. **恢复点样式**：正常结束点的绿点改为**深绿色空心圆**，直径 = 事件矩形高度（=9px），圆心白色。
3. **事件长度按升级时限**：非升级事件不得画得过长；应按各等级升级时限约束长度：
   - L1≈耗时→上限约 15′（短）
   - L2≈上限约 30′
   - L3≈上限约 60′
   - L4=立即（短）
   参考升级时限：L1/L2 15′、L2/L3 30′、L3 60′、L4 立即（来自 PRD/升级时限）。
4. **右侧实时竖线**：从 L4 顶部一直延伸到 **X（库外）车道灰色背景底部**。
5. **时间轴右端不要箭头**：去掉 marker 箭头。
6. **等级名放在等高铁框内**：每个等级名称放进**一个与该级灰色背景等高的矩形**，矩形**不是灰色**（用非灰/白底+描边以突出名称）。

### 9.1 恢复点不得遗漏（防再犯）
- **任何呈现"最终末端"（右侧有竖直硬边终点）的事件矩形，末端必须带空心恢复点**（深绿空心圆，直径=矩形高）。
- 进行中的事件**不得**呈现一个"假末端"：要么右端直达实时竖线并明确是"开放"（无点），要么就以带空心点的形式结束。**绝不允许出现"有末端却没有空心点"的中间态**。
- 改图后自检：数一遍每个等级的"最终末端"数量与空心点数量，必须一致。

## 10. 持续运营/容量型事件的可视化语义（2026-08-20 补）

> 回应评审："排队/高峰/活动这类事件会持续很久，按现行'墙钟超时→升级'会被误升级"——可视化与判据必须区分**任务型**与**容量受限型**事件。

### 10.1 事件的"处置语义类型"（入库元数据，决定升级语义）

| 类型 | 定义 | 时限语义 | 升级触发 | 典型事件 |
|---|---|---|---|---|
| **任务型 Task-like** | 有明确"完成"动作（改批、增开通道、修复、审批） | 处理时限=墙钟；超时=未响应/卡住 → 升级 | 墙钟超时（现行 §4.9 适用） | E02/E05/E06/E17… |
| **持续运营型 Sustained/Capacity-bound** | 无"一次完成"点，只能靠容量/条件变化**自然回落** | **时长≠失败**；不因墙钟升级 | 仅"**物理劣化判据**"或"安全阈值"触发 | E01/E03/E04/E27、餐厅/剧场/上下船高峰 |
| **峰值计划类 Scheduled-peak** | 持续型特例：时段可预测（午餐/散场） | 列入"计划内预分流"正常管线 | 仅当溢出安全容量才升级 | 午餐高峰、演出散场、接驳高峰 |

- 依据：人流/秩序类事件 E01/E03/E04、活动协调 E27（治理框架 §4.4/§4.9）；餐饮高峰/剧场容量（`pain-ai-matching` #7/#11、`catering-growth/SYNTHESIS` 排队管理）。

### 10.2 新增可视化段（在 §8 基础上扩展，不写字）

1. **受控持续段（Holding / 监测中段）**——持续运营型事件在"执行分流/引导后"进入的持续监视段：
   - 含义：系统按**容量/健康判据**持续管理，**不按墙钟升级**；
   - 画法：紧跟执行段之后，追加**等厚持续段**，用 `实底加深 + 上沿一条细虚线` 与普通执行段区分（高度仍与所有事件一致、同细）；
   - 结束方式仍守则：**判据恢复→空心点；判据失守→升级红竖线**。
2. **计划内峰值标记**——峰值计划类事件在**发现段左端加一个竖向短刻点/双短线**（视觉编码、不写字），表示"可预测高峰、非异常苗头"。
3. **迟滞恢复点（Hysteresis Recovery）**——持续型事件"恢复"= 指标回落到阈值下**并持续 N 分钟（初版 N=10′）**，避免抖动误恢复；通过后落常规空心绿点。
4. **双因升级标注**——升级红竖线分两种原因，视觉加区分：
   - 流程超时升级（任务型/无人响应）：现行红色实线；
   - 物理劣化升级（持续型/容量或安全阈值失守）：红实线靠上端点**再叠一段更粗更深的红**，且在操作台日志/卡片标注"升级原因=物理劣化（容量/安全）"。

### 10.3 升级判据改写（对应调整 §8 的"事件长度按升级时限"）

- "长度按升级时限"只对**任务型**严格；**持续运营型**用"受控持续段"表达，**不因墙钟强制升级**。
- "有最终末端必有空心点"保持；持续型末端 = 迟滞恢复通过（空心点）或判据失守（升级线）。

### 10.4 需接入的观测/判据接口（回答"要有拥挤/排队/异常事件接口接入"）

- 判据来自**感知与接口而非纯墙钟**：人流计数/密度（摄像头仅计数，R6）、吞吐速率、队列长度/等待时长、**区域容量余量**、安全阈值（疏散/踩踏）。
- E01/E03/E04/E27 的"升级规则"应扩展为附注"**容量阈值或安全阈值触发**"，而不仅是"15 分钟未处理"。
- 动作侧 A01/A02/A09/A10/A11/A16（分流/增容/引导）作用于容量；**动作无法改变物理高峰时，系统保持"受控持续"，不升级**。
- 确定性分层：容量/排队/时间窗判定走**排队论/仿真/规则**（非 AI）；开放域高峰异常苗头走 X 系列提醒（AI 只提醒不执行）。

## 11. 瞬时移交线完整规则（含"错误-恢复"，2026-08-20 补）

### 11.1 一句话总则
- **横向"段" = 有时间长度的状态**；**竖向"线/点" = 瞬时事件（无时长）**。
- 所有瞬时事件统一用**极性色**表达：**绿色=正常/成功**，**红色=异常/失败**；升级用红实线接上级开头；正常结束用空心深绿点。
- **系统自身不对"拥挤是否正常/异常"下判据**（见 §10.4）：该判据来自外部端口，作为**瞬时"信号接入线"（T1）**进入系统——它是"瞬时移交"的一种。

### 11.2 瞬时移交线全表
| ID | 瞬时事件 | 含义 | 正常(绿)形态 | 异常(红)形态 | 后续 |
|---|---|---|---|---|---|
| T1 | **信号/判据接入** | 感知或外部端口判据进入（事件诞生）：端口判"本次拥挤=正常高峰/异常超阈" | 绿色接入线 → 正常/受控持续路径 | 红色接入线 → 异常/库外路径 | 进入发现段 |
| T2 | **阶段移交** | 处理由一阶段/执行者交到下一阶段 | 绿高竖线（稍高于条） | 红更高竖线 | 接执行段 / 接红段 |
| T4 | **错误后恢复移交** | 交接失败后重新建立 / 被修复 | 在红段末端再落一条绿色高竖线 | — | 恢复正常色段继续推进 |
| T6 | **升级触发** | 超时或物理劣化 → 升到上级 | — | 红竖线 + 红色实线接上级开头 | 上级以发现段重开 |
| T7 | **恢复判定** | 数据/指标恢复正常（任务型=处置完成；持续型=迟滞通过） | 末尾**空心深绿点**（非线，不画黑端线） | — | 事件结束 |

> 说明：命令下达/触达投递暂并归 T2 系列（不单独画）；触达回执属端口审计范畴（进日志），不占时间轴。

### 11.3 错误并恢复的完整链路（关键）
```
… 执行(绿) ─❘(T2绿)─ 执行中 ─❘(T3红·更高)─ 红段(异常持续) ─❘(T4绿·修复)─ 恢复执行(绿)… ─●(T7 恢复点)
                                                                   │(若红段持续到事件终仍未修复)
                                                                   ▼
                                                              T6 升级（红实线↑上级开头）
```
- **红段是有界的**：起点 = 红色异常移交竖线（T3），终点 = 绿色"修复移交"竖线（T4）；之后回到正常执行色继续推进。
- 若红段一直未修复到事件结束：要么升级（T6），要么指标最终恢复正常后以空心点结束（T7）。

### 11.4 外部判据接入（T1）的说明
- 系统**不做**"拥挤是否正常"的最终判定：端口给什么信号就是什么信号（R6：外部感知仅计数/给判据）。
- 端口判据的"绿/红"极性决定事件开场路径：
  - 端口判"正常高峰 / 计划内" → T1 绿 → **计划内峰值标记** → 受控持续路径（§10.2）；
  - 端口判"异常 / 超阈值 / 库外" → T1 红 → 异常 / 库外路径。
- **判据错误也能恢复**：先收到"异常"（T1红）后端口修正为"正常"（后续再次 T1 绿 或 T4 修复移交）→ 回到正常路径；这同属 §11.3 的"错误-恢复"链路。

## 12. 待确认/待审批等待段（2026-08-20 补，修复"移交竖线被误用为时长"）

> 用户指出：信息送达经理 → 经理开始处理 → 确认/拒绝/接管，之间是**真实时长**，不是瞬时；当前模型把这段塞进了"瞬时移交竖线"，是错的。

### 12.1 图形（一个事件的完整解剖）
```
发现段 → ❘(移交竖线·瞬时：送达/接手) → ▭待确认/待审批段(时长+倒计时)
        → ❘(确认/拒绝/接管·瞬时) → 执行段 → ●恢复点
            └ 超时 → 红竖线↑上级(升级 §8.4/§11-T6)
```

### 12.2 待确认/待审批段规则
- **类型**：时长型分段（有持续时间），出现在"移交竖线（瞬时送达）之后、执行段之前"。
- **画法**：与所有事件同细；质感 = **半透明琥珀 + 竖向细斜纹**（区别于"发现段=实底琥珀、执行段=纯绿"）。倒计时不写在图上（图上不写字），用**卡片/横幅**展示。
- **起点** = 移交竖线落点（送达那一刻）。
- **终点** = 人动作（确认/拒绝/转接管）或**超时**。
  - 确认 → 该段末端落一条**瞬时绿移交竖线** → 进执行段；
  - 拒绝 → 事件以"拒绝"闭合（可回写发现类/转人工接管标记）；
  - 转人工接管 → 该段末端做**接管标记**（特殊），进入受监控人工模式（不再自动进执行段，保留循环提醒红点）；
  - 超时 → 该段末端红竖线 + 上升级（同 §4.9 时限 / §11 T6）。

### 12.3 与既有段/线的区分（防混淆）
| 元素 | 类型 | 含义 | 有无时长 |
|---|---|---|---|
| 发现段 | 段 | 信号接入、判定事件 | 有 |
| 移交竖线 | 线(瞬时) | 责任/信息正式交付下一角色 | 无 |
| **待确认/待审批段** | 段 | 人在处理/等待处理（含时限倒计时） | **有** |
| 执行段 | 段 | 已确认、执行中/落地 | 有 |
| 受控持续段 §10 | 段 | 容量型事件监测中、不升钟表 | 有 |
| 交接异常竖线/升级线 | 线(瞬时) | 失败/升级时刻 | 无 |
| 恢复点 | 点 | 判据恢复（含持续型迟滞 §10） | 无 |

### 12.4 判据影响
- 待确认/待审批段**时长上限 = 该等级时限**（L1/L2 15′、L2/L3 30′、L3 60′、L4 立即）；超时 → 升级。
- 持续运营型事件：值班确认分流方案也可能经历一次"待确认段"，确认后进入"受控持续段"（§10），此后不因墙钟升级。

## 13. 挂起与再检语义（2026-08-22 用户拍板，取代 §10.2「受控持续段」与本文件冲突处）

> 用户决策：可视化图用于监督**异常/重大事件**，低风险挂起不得长期生成矩形占据车道；挂起后一切后续=新事件；关联只在日志。

### 13.1 挂起=琥珀空心点闭合（关键）

- **判定挂起**：事件在`执行段`之后若被判定"挂起"，时间轴**到此为止**，以**琥珀空心点**（沿用检测色 #f0a43f）闭合。
- **不再渲染受控持续段矩形**：`§10.2` 中"受控持续段（Holding/监测中段）"从时间轴撤下；持续监测内容改为**操作台日志**呈现（每轮再检一行）。
- **闭合点双轨语义（与 §9.1 区分）**：
  | 闭合点 | 颜色/样式 | 语义 |
  |---|---|---|
  | 正常恢复点 | 深绿空心圆（直径=矩形高，圆心白） | 判据已恢复，事件正常结束（含迟滞通过 §10） |
  | **挂起点** | **琥珀空心圆（直径=矩形高，圆心白）** | 判定挂起，转后台监测 |
- 一个事件同一时刻**只有一个闭合点**（绿=恢复 / 琥珀=挂起），不得并存、不得缺失。

### 13.2 挂起后的再检与衍生事件（不画线）

```
  发现段 → 移交 → 待确认段 → 执行段
      ├─ 迟滞恢复通过 → ●绿点（正常结束）
      └─ 判定挂起 ────→ ●琥珀点（闭合）
              │  周期再检（进日志，不进时间轴）
              ├─ verdict=still      → 仅日志"仍同类拥堵·保持监测"  ★不生成新事件
              ├─ verdict=recovered  → 仅日志"恢复·关闭监测"（无新事件）
              ├─ verdict=upgrade    → 生成衍生新事件（如 L2→L3），parentTrace 关联
              └─ verdict=accident   → 生成衍生新事件（如 拥挤→E13/E20），parentTrace 关联
```

- **衍生新事件**：按自身等级落在**自己的车道**、自己的时间轴，**绝不画回到原挂起事件**、**绝不画流转线**。
- **两条血缘线必须分清**：
  - 关系 A（同异常演化·**要画线**）：X 升级为正式事件、L3→L4 升级、超时升级 = 同一条异常抬头 → 红竖线/红实线接上级左起点（§8.4 / §11-T6）。
  - 关系 B（挂起后独立事件·**仅日志**）：再检/衍生 = 另起的新事件 → 仅 `parentTrace` 在日志中可查（§13.3）。
- X 车道（§8.5）不在此列：X 的观察→升级→忽略仍按原规则（它属于关系 A 的升级画法）。

### 13.3 日志血缘（parentTrace）

- 衍生新事件携带 `parentTrace`（来源事件 trace_id）；操作台日志可查"该起拥挤 → 某时刻再检升级/衍生事故 → 新事件号"，时间轴不显示任何连线。

### 13.4 对 §12 的配套修正

- §12.4 末句"确认后进入受控持续段（§10）"改写为：**确认后进入执行段；若判定挂起 → 琥珀点闭合；若判据恢复 → 绿色恢复点**。
- §12.3 表中「受控持续段 §10」一行撤销（不再作为时间轴元素），持续监测进日志。
