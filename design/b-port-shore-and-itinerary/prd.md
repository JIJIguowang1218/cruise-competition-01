## 1. 背景与问题

邮轮乘客在“船↔岸”交界的环节体验断裂最明显，且高利害事件一旦处理不当会升级成群体事件。

- 登离船：登船日同一时段集中到达，排队长度不可见；离船日靠广播/纸质通知分层下船，等待 3–4 小时；离船日 8:00 被要求离开房间、15:00 才下船。
  - 来源：`02-embark-disembark.md`（PC，8+ 独立源 Strong）
- 港口接驳：官方信息是静态 PDF 手册，各港方案不一；出租车拒载/宰客；宝山区政府连续两年承认交通秩序问题。
  - 来源：`03-port-transport.md`（PA/N3，官方 L0 + 媒体 Strong）
- 航变/赔偿：2026 台风“白海豚”导致数百人拒下船；通知链存在多层衰减（船司 16h / OTA 2h / 电话 30min）；赔偿标准不透明。
  - 来源：`04-itinerary-change-compensation.md`（PD/PA，8+ 独立源 Strong）

现有信息系统彼此割裂：船方、OTA、港口、客服各说各话；关键决策靠人工拼图，导致信息滞后、口径不一、取证困难。

## 2. 产品定位与边界

### 2.1 一句话定位

做一个 B 端“港岸协同与事件响应决策层”——在邮轮公司权限和能力范围内，实时感知可得的码头/通关/接驳/船期状态 → 确定性计算时间窗与影响 → AI 进行事件分类、跨系统态势整合、影响推演与方案组合，并附证据与置信度 → 人审批后通过既有渠道统一触达，每个动作留痕可审计。

### 2.2 管理边界

**管 / 可伸手接触**：
- 船方自己的乘客触达渠道：既有 App、船载屏、广播/短信、船员端；
- 邮轮公司内部的登离船批次、乘客时间窗、通知口径；
- 邮轮公司可合法获取/接入的港口开放数据或第三方接驳信息；
- 航变事件中船方需要向乘客传达的事实、条款依据、方案与审批。

**不管 / 管不到**：
- 海关、边检、移民等口岸核心流程与系统：**给什么数据就用什么，不对这些机构提额外要求**；
- 港口调度、交管、出租车行业规则：**不能直接指挥或执法**；
- 港口未开放的实时数据：**不得在系统里假设存在**；
- 岸上游/目的地商家：不纳入；
- 船上餐饮/娱乐调度（A 线）：不进入 B 线 MVP，仅留接口示意；
- 极端天气本身：不预测/不干预，只做“事件发生后如何响应”。

### 2.3 现实约束

- **不做大一统调度系统**：B 线面对跨部门、跨境、多机构业务，系统定位是“协同决策层”，不是替代港口/海关/交管的超级系统。
- **接口现实优先**：外部系统提供什么能力，我们就基于什么能力设计；不能提供的，用“接口假设 + 待验证”标注，Demo 中可用模拟数据但不假装已接入。
- **能力边界诚实**：出租车拒载/宰客不能靠我们直接解决，只能通过信息透明、推荐合规交通方式、提示价格区间、提供投诉入口等方式，在船方权限内缓解。

### 2.4 沿用已拍板结论

- Q1=A：我们定义 L2/L3 接口规范，船公司自行接入既有 App/触达渠道。
- Q2=按推荐：接口按“信息源（读）/执行端（写）/两者”分类。
- Q3=A：港口实时数据在 Demo 中用模拟数据 + 诚实标注。
- Q4=按推荐：航变关键动作走三级审批。

## 3. AI 价值判断与架构选型（概要）

> 核心判断：**AI 不是“帮忙写通知”，而是做人做不快、做不全、做不规律的工程判断与长链路调度建议。**
> 详细论证与案例见 `ai-architecture-and-value.md`。

| AI 价值 | 一句话 |
|---|---|
| 事件分类与态势判断 | 判断“发生了什么、严重吗、属于哪类事件” |
| 跨系统高并发整合 | 港口/船期/天气/乘客/客服/现场感知同时读入，分钟级出局势图 |
| 长链路推理与影响推演 | 局部事件 → 影响传播 → 资源调度 → 是否需要更高权限 |
| 方案组合而非编造 | 从事件库、策略库、条款库中组合已有方案 |
| 证据与信度控制 | 每个判断给依据、置信度、替代方案；低信度转人工 |
| 人机协同与权限分级 | AI 建议、人审批；高后果动作过代码级审批门 |

**架构选型原则**：确定性系统做骨架，RAG 做知识接入，LLM 做语言表达，少量 Agent/模块做流程编排，人做审批。详细组件选型见 `ai-architecture-and-value.md`。
**AI 价值立场（2026-08-18 强化）**：本系统与"旧系统 + 规则升级"的差异集中在三块 AI 高利益区间——**①开放域异常发现（看到库里没有的）②长链路推演 + 弱信号整合（推演没写过的）③推理附件/证据链（解释说不清的）**。确定性计算、审批门反而刻意不用 AI。逐环节的 AI 不可替代性论证见 `ai-architecture-and-value.md` §3.6；推理附件推广到分类/影响/方案/异常/客服/审批/升级全部环节见 §3.7。

## 4. 事件治理与权限流转（概要）

> 原则：**不是所有事件都要打扰高层，也不是所有事件都可以自动执行。**
> 详细分类、等级、知识库与升级机制见 `event-governance-framework.md`。

- 事件分类：人流/秩序、设施/设备、外部环境、安全/健康、合规/赔偿、信息与运营沟通（仅限船岸调度相关信息，不在船上的客服事件不纳入）、特殊人群 7 大类 + **库外/未分类（X 系列）**。
- 事件等级：L1 自动分发基层 → L2 值班确认 → L3 经理/法务审批 → L4 船长/最高级。
- 核心机制：轻事件自动分发并监控；重事件人工审批；超时自动升级；低信度/证据不足强制转人工。
- 知识库：事件分类库、事件等级库、策略库、条款库、权限升级矩阵、**事故模式记忆库**、端口库、动作库。
- **推理附件（全量标配）**：每个 AI 方案/策略都附带逻辑梳理的推理与证据链文本（详情说明角色，可展开可打印）；发现异常苗头时附件提权为着重提醒（主界面风险横幅 + 高亮可疑环节）。详见 `event-governance-framework.md` §4.11。
- **库外异常识别与提醒（2026-08-18 新增）**：库内事件走标准管线；库外/复合/异常信号由 AI 输出风险等级与“提醒卡”，按 L1–L4 路由到对应决策端并决定抄送层级，**只提醒不执行**，人处置后可升级为正式事件回写事件库。详见 `event-governance-framework.md` §4.11。
- **投放审核矩阵（2026-08-18 新增）**：审批级别由“可见性 × 可撤回性 × 后果”决定——公共可见（广播/船载屏）必须先人工确认（≥L2），个人定向可 L1 自动；统一口径/赔偿类必须 L3/L4。详见 `event-governance-framework.md` §4.10。
- **人工接管机制（2026-08-18 新增）**：系统是"决策增强层"而非"执行替代层"——保留船司现有调度系统（广播台/对讲/App 后台/纸质 SOP）作为人工接管端口；接管后系统转"观察 + 记录 + 建议"，**不要求人补充结构化信息**，只做最小登记（一句话/处置单号），所有痕迹通过 trace_id 与现有系统日志关联。详见 `event-governance-framework.md` §4.12。
- **确认签署与痕迹管理（2026-08-18 新增）**：确认分四档（L1 自动/ L2 电子确认/ L3 电子签署可导出 PDF/ L4 紧急后补签）；端口执行日志 append-only 存储、哈希链防篡改、审计包一键导出可打印；人工登记文本与系统记录区分标注。详见 `event-governance-framework.md` §4.13。
- 用户投诉/情绪升级边界：常规投诉归 C 端/客服；B 系统只通过接口接收信号、输出统一口径；若发生在邮轮紧急/安全场景，则按安全事件处理。
- 系统韧性：断电/断网/本地 AI 故障按 T0–T3 分级降级（降级路径用“熔断/回退/快照/人工接管”标准表述），详见 `event-governance-framework.md` §4.5。
- 响应规范：事件响应按“决策端 + 执行端动作 + 告知端口 + 升级规则”从端口库/动作库组合，AI 不自由编造。

## 5. 功能模块（M1–M6，已按接口地图/AI 组件关系图回校）

> 本节为当前基线；字段级接口定义、实时性、降级细节仍会在接口清单中继续深化。

### M1 港岸状态感知（L2 确定性层）

- 输入：
  - 船方内部：船期/泊位计划、乘客/舱房/行李清单、预订/POS（待验证）；
  - 外部可得：公开气象/台风路径、港口静态接驳资料（官方 PDF）；
  - 外部不可得：码头/口岸实时排队、海关/边检进度 → 标注“不可得/模拟”。
- 处理：确定性算法计算排队、等待、时间窗、影响人数、资源缺口。
- 输出：结构化状态数据，供 M2/M3/M4 使用。
- 集成等级：真实 / 模拟 / 不可得，三态显式标注。

### M2 登离船动态调度

- 输入：M1 状态 + 乘客/舱房/行李数据。
- 处理：
  - 登船日：生成动态分时建议，缓解集中到达；
  - 离船日：生成个人化下船时间窗，并根据码头状态调整批次；
  - 触发条件与 M1 联动，按 L1/L2 权限确认后触达。
- 输出：乘客时间窗、批次通知、船员任务。
- 边界：不指挥港口/海关，只在船方可调度范围内调整。

### M3 港口接驳协同

- 输入：官方静态接驳资料（PDF）、若可接入的实时接驳/交通状态（待验证）。
- 处理：
  - 将可得的接驳信息转化为乘客可执行建议；
  - 不使用不可得的实时排队数据；没有数据时退回静态指引。
- 输出：离船时间窗 + 接驳建议、价格区间提示、投诉入口。
- 边界：不干预出租车/交管；不假设港口专线一定可接入。

### M4 航变/极端天气事件响应

- 输入：M1 状态、船期变更、天气预警、条款库/事故模式记忆库、乘客影响范围。
- 处理：
  1. 事件分类与严重度判定（L1–L4）；
  2. 确定性影响评估（受影响乘客、资源缺口、时间窗）；
  3. 策略库/条款库/事故模式检索（RAG）；
  4. 方案组合与推演（事件→影响→资源→方案）；
  5. **生成推理附件（全量标配）** + 证据与置信度检查（低信度转人工；异常苗头提权为重点提醒）；
  6. 按权限路由审批（L2/L3/L4），超时自动升级；任意节点可**转人工接管**（移交船司现有调度系统，系统转观察+记录+建议）；
  7. 统一口径触达（按 §4.10 投放审核矩阵核准级别）；
  8. 审计回写事故模式记忆库（审计包含推理附件与签署记录，可导出 PDF）。
- 涉及 AI：事件分类 + RAG + 方案组合 Agent + LLM 解释/话术 + 推理附件 + 置信度检查 + 库外异常提醒。
- 边界：赔偿/法律结论必须来自条款库并由法务/管理层审批；AI 不直接执行任何写操作。

### M4.5 客服协同与智能问答（候选模块）

- 定位：B 与 C 端客服的接口层，**不是独立 C 端产品**。
- 输入：客服系统传递的“大量同质咨询/舆情/投诉信号”。
- 处理：
  - 意图识别：查事实 / 查条款 / 投诉 / 紧急；
  - 查事实走 API，查条款走 RAG；
  - 常规投诉回到客服系统处理；
  - 紧急/安全事件升级到 L3/L4。
- 输出：统一口径、条款依据、事件时间线，供客服使用。

### M5 运营调度台

- 功能：
  - 港岸态势总览；
  - 事件队列（L1–L4）；
  - 建议卡片（结论 + 关键证据；**推理附件可展开**——全量标配，异常提醒主界面风险横幅）；
  - 审批队列与超时提醒；
  - **转人工接管入口**（每个审批/执行节点可用；L4 预置船长首页）；
  - 任务分派与执行反馈；
  - 审计包（含签署记录与各端口执行日志，一键导出 PDF）与事故模式回写。
- 与 §4 权限矩阵联动：角色只能看到/操作权限内的事件。

### M6 触达输出（L4 接口层）

- 输出渠道：既有乘客 App、船载屏、广播/短信、船员端。
- 输出物：结构化消息/推荐 JSON + 触发规则 + 审批状态 + trace_id。
- 接口要求：MOCK_MODE/REAL_MODE 显式分离；每条消息可回溯到事件、证据（推理附件）、审批人；按 $4.10 投放审核矩阵核准执行级别；端口执行日志 append-only 留存，审计包可导出 PDF。
- 人工接管：执行可移交船司现有系统（广播台/App 后台等），系统记录"人工接管"标记并最小登记。
- A 线预留：只保留“船上空间状态事件订阅”接口，不实现业务。

## 6. 跨模块规则

| 规则 | 内容 |
|---|---|
| R1 确定性保底 | 排队/时间窗/影响人数/赔偿范围全部确定性计算，LLM 不参与算术 |
| R2 分层降级 | LLM 不可用 → 规则模板；感知不可用 → 上一快照 + 标注；RAG 不可用 → 只引用已缓存条款 |
| R3 审批门结构性 | 执行路径不经 LLM；写操作/全量推送/赔偿执行必须过代码级审批；**人工接管不绕过审计**——执行权移交现有系统，记录标记"人工接管"（§4.12） |
| R4 证据可追溯 | 每个建议/动作带证据抽屉、trace_id、审批人；**每个方案标配推理附件**（§4.11），追溯不再是事后动作 |
| R5 统一口径 | 事件通知以系统生成为唯一口径源，渠道分发后不回退为人工零散解释；**人工接管时以现有系统操作 + 审计补记为准**（§4.12） |
| R6 数据源诚实 | 外部数据必须标注“真实/模拟/不可得”；MOCK_MODE/REAL_MODE 显式分离 |
| R7 权限现实 | 不假设能指挥港口/海关/交管；只在船方权限内输出建议与信息 |
| R8 条款引用纪律 | RAG/LLM 输出必须带条款原文编号或“待人工确认”标记，禁止无出处承诺 |
| R9 分级处理 | 按事件等级自动分发/审批：L1 自动、L2 确认、L3 审批、L4 紧急最高层 |
| R10 超时升级 | 每个事件等级设置处理时限，超时自动升级，不得无限等待（时限参照行业惯例，§4.2.1） |
| R11 低信度转人工 | 分类置信度低、证据不足、策略不匹配时强制人工复核；库外/异常信号进入 §4.11 提权提醒 |

## 7. 角色与权限（初始假设，合理即可，不作核心设计）

| 角色 | 可操作范围 | 审批级别 |
|---|---|---|
| 基层执行端（现场船员/港口对接员） | 接收 L1/L2 任务，现场处理并反馈 | 执行级 |
| 值班船员/客服 | 查看态势、发起确认、编辑话术草稿、使用客服问答辅助 | 确认级 |
| 运营经理/航次经理 | 审核方案、选择通知渠道、初审赔偿 | 审批级 |
| 法务 / 合规 | 审核条款适用与赔偿方案 | 审批级 |
| 船长 / 最高运营负责人 | 全量推送、正式通知、紧急决策 | 最高级 |
| 港口/外部系统 | 仅数据交换，不进入我方审批流 | 外部 |

> 公开证据无法确认邮轮公司实际组织架构；以上为行业常识的合理推断 + 接口假设。后续可用公开岗位/采访/用户经验侧面印证，但不作为核心设计阻塞项。

## 8. 非功能要求

- **性能**：目标为事件“感知→建议→审批任务生成”≤3 分钟、触达任务生成 ≤2 分钟；这些是设计目标/待仿真验证，不作为已证实指标。
- **事件时限**：L1 自动派单后须在设定时限内反馈；L2/L3/L4 审批超时自动升级（初版时限见 `event-governance-framework.md` §4.9；后续按仿真调整）。
- **离线**：船载边缘推理 + 本地规则库 + 本地缓存条款库；卫星链路仅异步增强。
- **合规**：赔偿/合同条款引用必须来自已归档条款库；隐私（若使用客流计数，仅计数不识别）。
- **安全**：审批门代码级实现；审计日志不可篡改；外部接口按 IACS 船载网络边界设计。

### 8.1 质量目标与评测闭环（2026-08-19 新增）

> 口径对齐 B7：以下指标是**目标区间 + 待原型/仿真标定**，不是承诺值；演示答辩按"诚实量化"原则表述（写区间、标依据、不写"精准预测"，参照 09b 挖掘的 P8 正模式：WorldCup 68% walk-forward 反而是加分项）。

**① 目标指标（初版）**

| 环节 | 指标 | 目标区间（待实测标定） | 验收口径 |
|---|---|---|---|
| 事件分类（M4 步骤 1） | 分类准确率（30 类映射 + X 系列识别） | ≥90% | 用首批样例集（30 事件 + 5 类库外信号）离线评测；低信度强制转人工的样本不计入分母（如实披露） |
| 分类置信度阈值语义化 | 自动 / 人工 / 仅提示 三档 | ≥0.85 自动；0.60–0.84 人工确认；<0.60 仅提示 | 阈值可配置，演示不承诺固定值（参照 Arclo 分级；阈值来源：§4.11 风险分级语义） |
| 方案组合检索 | RAG 检索命中率（策略/条款/历史预案） | Top-5 命中 ≥85% | 用条款库首批样例评测（MRR/Precision@K，口径见 `.dsh/skills/llm-evaluation`） |
| 延迟 | 感知→建议→审批任务生成 / 触达任务生成 | ≤3 分钟 / ≤2 分钟 | 设计目标待仿真，非证实指标（§8 性能） |

**② Bad Case 双轨（学习闭环，2026-08-19 新增）**

- **业务轨（已有）**：事故模式记忆库 + 审计回写——事件处置结果、推理附件、签署记录沉淀为可复用历史模式（§4.3 / §4.11.2 回写），解决"同类事件下次更快"。
- **模型轨（新增）**：坏例表 + 评测集 + 回归——分类错误、检索未命中、方案不适用、低信度误判等输出，由值班/审批人员依托推理附件旁"标记坏例"入口一键回标 → 回写评测集 → 模型/提示词/知识库更新后跑回归（参照 09b P7："LLM 功能要进 CI"；回归检测口径见 llm-evaluation 技能）。演示阶段以设计闭环呈现为主，如实说明不做真实训练迭代。

**③ 价值量化假设表（ROI 口径，2026-08-19 新增）**

> 不做货币化测算（本项目无真实财务数据）：按 B7 用"相对量级 + 显式假设"。假设值全部来自证据线 A 的 [待验证] 估算；**答辩口径：给假设、请船司拿真实数据校准**。

| 场景 | 手工基线（证据线 A） | AI 后目标 | 节省人力量级 | 假设与验证状态 |
|---|---|---|---|---|
| 航变响应逐批沟通 | 8 名客服连续 5h+（[待验证]推断） | A05 统一口径 + 多渠道同步，人审批（§4.8.1） | 客服高峰人力小时数下降（量级待仿真） | 假设：客服工作量与通知批次/渠道数线性相关；需船司数据校准 |
| 登离船/航变信息集成 | 人工拼图 20–45 分钟（证据线 B） | 分钟级局势图（V2） | 决策准备时间压缩一个量级 | 假设：数据经接口可得（M1 三态显式标注：真实/模拟/不可得） |
| 通知链一致性 | 船司 16h / OTA 2h / 电话 30min 衰减 | 单一口径源，分钟级触达（R5） | 口径不一致引发的补解释/投诉分流减少 | 来源：04 素材库 Strong；投诉下降率无数据，**不承诺** |
| 误报成本控制 | 常规广播打扰全体乘客 | 投放审核矩阵分级（§4.10） | 全船打扰次数下降（量级待仿真） | 假设：审批分级能拦截低价值投放；不可得数据如实标注 |

**④ 验证策略边界：何时能用 AB（2026-08-19 新增）**

> B 线是**高后果决策系统**，不把 AB 当通用验证手段：安全/赔偿/群体事件**无对照组、样本不足、后果不可逆**，验证走"事后审计 + 仿真 + 演习"（§4.5 韧性演习、§4.13 审计包）；**AB/灰度仅用于低风险触达环节**（通知渠道选择、文案口径、客服自助问答），且落在投放审核矩阵（§4.10）的低敏档内。完整口径（含"准确率 92%→94% vs +200ms 延迟"的权衡答案）整理进答辩 Q&A。
