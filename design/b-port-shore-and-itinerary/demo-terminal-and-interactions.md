### 1.5 服务与终端架构：单中枢 · 多终端 · 三形态（用户提问，2026-08-19）

> 回答"邮轮管理人员使用的系统服务之间是什么关系、终端前后端差异"。模型：**一套中枢服务，多种形态前端，靠"角色权限裁剪 + 终端形态差异"拉开**，不是每类人员一套独立系统。

**部署拓扑（坚持"船上本地中枢"原则）**：
- **单一中枢服务**部署在船上船载边缘节点/船载数据中心：AI 服务（事件分类/库外异常/长链路推演/推理附件）+ 确定性内核（排队/时间窗/影响人数）+ 知识库（策略/条款/事故记忆）+ 审批门 + 审计，**全部在这里**。
- 所有内部终端（调度大屏、调度 PC、值班平板、船长触控）通过**船载局域网**连同一个中枢（API 网关）；终端是**瘦客户端**——只负责渲染与输入，不装业务逻辑。
- 岸上企业服务器/云端 = **异步增强**（远程审计归档、模型更新、长文档解析），不进实时闭环，页面不依赖它（T0–T3 故障域只在中枢做）。

**权限与可见性（同一中枢，服务端裁剪）**：
- 用 RBAC（角色）× 事件等级 × 事件归属 决定"看见什么、能操作什么"；**不可见/不可操作的数据在服务端不下发**——前端隐藏不是安全边界，操作校验在服务端强制（坚持"审批门代码级"）。
- 角色可见域：值班/客服 = L1/L2 全操作 + L3/L4 只读概要；运营经理 = L2/L3 操作 + L4 只读；法务 = 涉法/赔偿事件可操作，其余只读摘要；船长 = L4 全量 + 全事件只读监控。同一事件对同一个人只出现一次，列表自动打标：**可操作 / 只读 / 不可见**。

**终端前后端差异（三种形态）**：
| 形态 | 代表终端（硬件） | 前端侧重 | 后端差异 | 对应页面 |
|---|---|---|---|---|
| ① 监控形态（大屏/PC） | 调度重心大屏、运营中心 PC | 高可视化：局势图、事件轨迹时间轴、事件队列、状态色；**低交互、只读为主**（值班位可轻确认） | 读接口 + 事件推送，只拉权限内聚合 | P1 总览、P2 时间轴 |
| ② 操作形态（触摸平板/PC） | 值班/经理/法务/船长在岗设备 | 单事件处理流：详情→确认/拒绝/电子签署→下达→跟踪；**高交互、表单化、触屏化** | 操作接口 + 服务端审批门校验 + 审计；按角色返回可操作动作集 | P3、P4、P5 |
| ③ 触达形态（乘客手机） | 乘客手机（公网） | 被动接收 + 可查（通知、可操作项）；与内部完全隔离 | 走触达接口（M6），不入审批流 | P6 |
| （边缘）执行/留痕 | 广播台、船载屏、船员端 | 状态显示 + 最小操作 | 执行回执、审计查询 | P7/P8/P9 |

**为什么这样设计（工程 + 叙事两层意义）**：
- 单中枢 → 离线降级（T0–T3）只在中枢做故障域隔离，终端只管渲染；符合"实时闭环不过卫星、断链按 T0–T3 降级"；
- 监控与操作分离 → 大屏给"态势感"（谁在盯全场），平板给"处置流"（谁在办单件事），各司其职，评委一眼看懂；
- 权限在服务端 + 审批门代码级 + 审计完整 → 前端做不出越权/绕过动作（Globot HITL 槽点反杀点）;
- 瘦客户端 + 局域网 → 一台船载边缘节点带全船终端，符合"不能加一台服务器"的空间约束叙事。

### 1.6 与既有系统的相处：不碰导航 · 融入运营 · 独立工作台（用户顾虑，专业核查后修订）

> 用户顾虑（成立并采纳）：邮轮驾驶台不是铁道调度中心；驾驶台面板已成体系（导航/推进/通信），雷达、ECDIS 等成熟导航设备既不适合改造也不该被弹窗打扰；船长平时看我们系统的频率远低于其它内容。
> 专业核查（公开行业资料）：现代邮轮驾驶台是 **IBS 集成桥楼系统**——导航工作站（radar/ARPA、ECDIS）、推进/动力定位（DP）、GMDSS 通信，受 **SOLAS 第 V 章**与船级社性能标准约束，航行值班高专注，**导航界面不被非航行业务弹窗/改造**（KONGSBERG、FURUNO 等给 Carnival/Allure 的 IBS 即此类）；"大屏调度中心"的真实先例是**岸基船队运营中心（FOC/GSOC）**（Carnival Miami FOC、Carnival Maritime FOC Hamburg 等）与船司地面运营，而非每艘船驾驶台；船上的运营协同落在**宾客运营层**（hotel/guest experience 集中工作台、值班 officer）。

**修订后的定位（三句话）**：
1. **不碰导航**：不改造、不在 radar/ECDIS/推进/GMDSS/配电监盘上弹窗；与航行安全系统互不干扰（这是一条我们要主动写进答辩的"边界诚实"）。
2. **融入运营**：乘客通知/行程/客服本来归船司宾客运营、客服、通知后台体系（PRD §2.4 Q1=A：我方定义 L2/L3 接口规范、船司接入既有 App 与触达渠道）——我们作为"接口 + 决策增强层"融入，不另起炉灶抢现有面板。
3. **独立工作台（推荐、可新建）**：提供一个"港岸协同与航变响应"参考工作台，部署在**船上宾客运营中心 / 岸基本船运营台**（非驾驶台）；大屏形态对标岸基 FOC 先例，操作形态对标值班/经理/法务在岗工作站。

**由此对 Demo 展示与答辩的影响**：
- "监控大屏/局势图"叙事载体 = **岸基 FOC / 宾客运营中心**，不是驾驶台——有 Carnival FOC 等行业先例背书；
- **船长视图 = 低侵入出口**：平时静默（不点亮），L4 / 超时升级才推送并一键进处置 + 审计回溯；第三幕正好把"升级到船长"演出来；
- **答辩口径**："我们提供的是接入/决策增强层，不把系统硬塞进驾驶台；导航设备我们明确不碰、只按接口融入既有运营体系。"
- **Demo 技术形态不变**：以上都是页面/接入定位的调整，P1–P9 与技术栈、自动化驱动方案不受影响。

## 4. 修订后的展示结构（日常轨道 + 应急三幕）

> 按意见②③合并：**先"日常是怎么工作的"，再"应急怎么升级"，最后回到闭环恢复**。

```
【开场 日常轨道 40s】事件轨迹时间轴页（ambient 滚动）
   日常事件处理轨迹：E01/ E25/ 小拥挤弱信号
   ——每条卡显示 发生→建议→确认→执行→恢复 的闭环状态条
   → 传达"系统每天都在盯，不是只响应急"

【第一幕 快过 30s】台风预警触发 E09
   局势图 + 影响人数/时间窗 确定性计算（R1 用代码）

【第二幕 AI 高地主角 90s】（你问的"第二幕演什么"=这里具体化）
   a) 弱信号整合：港口接驳巴士异常 × 离船批次冲突 × 时间接近 → 态势图高亮弱组合
   b) 库外异常（高地1）：某廊桥占用模式与历史不符 → X 提醒卡"不在事件库内，建议人工关注"
   c) 长链路推演（高地2）：E09 → 离船变更 → 接驳 → 条款触发区间 → 窗口连环更新
   d) 方案组合：A05+A06+A03，附"为什么不用 B"

【第三幕 信任层收尾 60s】
   建议卡展开推理附件（读了哪些信号/置信度/条款编号）
   → 三级审批（值班确认→经理→法务电子签署；可加超时升级剧情）
   → 投放审核矩阵分级触达（广播需确认、App 定向推送）
   → 乘客 App 效果屏 + 广播执行屏
   → 审计包导出 PDF

【收尾 20s】时间轴回到"恢复"：事件关闭，事故模式记忆回写 → 闭环
```

## 5. 可交互页面清单（要开发出来的页面）

> 原则（意见④）：**每个页面都是"完整功能模拟"**（逻辑真实、数据 mock 并标注），评委可手动点；另外用**自动化脚本**驱动走完整剧情（见 §6）。

**必做（6）**：
| # | 页面 | 承载剧情 |
|---|---|---|
| P1 | **运营调度台 · 总览**（主屏） | 态势 + 事件队列 + 建议卡 + 审批队列 + 接管入口（角色切换） |
| P2 | **事件轨迹时间轴**（滚动总览） | "日常轨道"开场 + 收尾恢复 |

| P6 | **乘客 App 效果屏** | 分批通知/排队提示/统一口径+多语言（触达效果） |

**MVP 建议先做 P1–P5（撑起主剧情）**，P6 与 P7/P8 作为辅屏补充；P9 视工作量。**（用户已拍板：MVI 先做 P1–P6）**

**形态归属（对应 §1.5）**：P1/P2 → 监控形态（大屏）；P3/P4/P5 → 操作形态（平板/PC）；P6 → 触达形态（乘客 App）；P7/P8/P9 → 执行/留痕形态。

### 5.1 页面 × 功能 × 硬件 × 屏幕 总表（做 UI 前先定这个）

> 说明：Demo 是 Web 原型，每个页面按"真实硬件视口"设计长宽比，演示时以大屏/平板/手机三种 frame 呈现；下面给的是**逻辑分辨率基准**（实际用 CSS 响应式适配）。

## 6. 自动化演示驱动（意见④的落地）

- **交互性**：P1–P9 全部可由人点击操作（模拟各角色点确认/审批）。
- **演示模式**：用自动化脚本（推荐 Playwright，或原型内嵌"剧情推进"模式）自动走完整流程——设事件状态→点击→切角色→滚动时间轴→导出，产出**流畅演示**；可录制为 ≤2 分钟展示视频（比赛要求 MP4）。
- **现场半自动**：关键步骤手动点（显"人在审批"），页面联动自动，既稳又不显假。
- **红线不变**：数据 mock 标注、核心逻辑真实可跑、推理附件必露、审批审计演出来。
