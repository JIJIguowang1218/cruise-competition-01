### 1.2 三种业务节奏（技术分层的依据）

> 这是本档提出的核心区分：**同一条业务链上跑着三种时间尺度，它们对"能不能上云、能不能用大模型"的答案完全不同。**

| 节奏 | 时限量级 | 业务 | 技术结论 |
|---|---|---|---|
| **A · 实时闭环** | 分钟级（目标 ≤3min 出建议、≤2min 出触达任务） | M1→M2/M3/M4 主链 + M6 | **必须完全本地**（船载局域网）；只用规则 + 本地小/中模型；**云端永不进入** |
| **B · 决定前支路** | 小时–天级 | C0 前置决策支持（弱信号聚合、四维价值） | 可本地中模型；**允许云端异步增强**（非阻塞、无时限压力） |
| **C · 异步离线** | 小时–天级 | 长文档/法规解析、模型更新、审计包导出、坏例回归评测、事故模式沉淀 | **唯一可以出船的一档**；云端大模型在此档 |

#### 1.2.1 决定端的时间尺度（2026-09-15 取证，回答议题 2）

> 问题：C0 前置决策支持（"决定成立前"的那段）到底算不算实时闭环？答案取决于**船公司多久之前才拍板**。取证结论是：**它不是一个尺度，是四个**。

| 档 | 提前量 | 是什么 | 证据 |
|---|---|---|---|
| **0 趋势层** | 72–120h | 气象/海事给出"可能有事"的趋势与预警——**不是决定** | 台风路径预报时效已延至 72/96/120h；预警发布本身无统一提前量规定 |
| **1 计划性决定** | 24–72h | 船公司拍板、正式发公告（邮件/短信） | RCI 口径"开航前 48–72h 决定"（二手汇总，非官方）；**合同层面无最低提前量**——RCI/NCL 条款均写"any time and without prior notice" |
| **2 临场决定** | 2–24h | 靠前一晚或当天上午才定 | 喜悦号出港后约 20h 才通知改靠；NCL Escape <24h 且登船当天在码头发纸质新行程；Costa Firenze 前一晚 PA 广播 |
| **3 day-of** | **0–3h** | 决定成立到落地只剩小时级 | 光谱号 09:04 通知改目的港 / 11:30 登船（≈2.5h）；**港口封港类（大雾/大风）本质是实时阈值触发，提前量结构性≈0**（坦帕湾大雾当晨由海岸警卫队决定、延误 ≥8h；上海港大雾封航曾持续 40h、延误逾 8h） |

**三条结构性判断**：
1. **"临场几小时内决定"不是边缘情形**：封港是阈值+实时判定（福克兰：风 30kn 且上升即封、能见度 <0.1nm 停 tender），而船公司本身有**主动压到最后一刻的动机**（嘉年华口径："wait… often within a day or so notice"，因为风暴路径不可靠、且想尽量交付原行程）；
2. **本系统拿不到"更早知道"**：气象/海事发预警、船公司 FOC 决定、船长对安全有独立决定权（ISM §5.2；《上海市邮轮旅游经营规范》第十六条）——**系统只能接收"已成立的决定"**；
3. **下游传导还要再吃一档**：同一事实，船司 16h → OTA 2h → 电话 30min——这正是"统一口径 + 分钟级触达"的直接依据。

**结论：C0 必须分两档，不能只当天级支路。**

| 档 | 覆盖 | 节奏 | 技术结论 |
|---|---|---|---|
| **C0-plan** | 档 0 / 档 1（趋势与计划性决定） | 天级 | 可异步、**可用云端增强**（B 档） |
| **C0-urgent** | 档 2 / 档 3（临场与 day-of） | 分钟–小时级 | **必须落在 A 档实时闭环内**——船上本地、分钟级出决策支持卡 |

- 技术上**同一组件、两档 SLA**（数据源不同：plan 用长周期预报与计划变更窗口；urgent 用实时封港通告、海况、ETA）；
- **对选型的直接后果**：前置决策支持**不能设计成"云端出决策卡"**——本地中模型必须能独立完成四维价值评估与多备选对比，否则 day-of 场景直接失效；
- **顺带一个答辩点**：我们的演示锚点（E09 决定成立 → 靠泊前约 23 分钟、L3 五分钟闭合）与公开案例同档（光谱号 ≈2.5h），**是真实量级，不是编的**。

### 1.3 业务倒推的五条结构性约束（技术架构的硬边界）

| 来源 | 约束 | 对技术架构的直接要求 |
|---|---|---|
| R1 | 确定性保底：数字不归模型 | 确定性内核必须是**纯净、可复算、无模型依赖**的代码；模型挂了它照跑 |
| R3 | 审批门结构性：执行路径不经模型 | **模型不持有任何执行句柄**——这条在技术上怎么落地，就是 §4 的沙箱 |
| R6 | 数据源诚实：真实/模拟/不可得三态 | 三态标签必须**跟着数据走**（贯穿适配器 → 模型上下文 → 界面 → 审计），不能只在界面上标 |
| R7 | 权限现实：不指挥港口/海关/交管 | 对外只有**只读订阅 + 既有渠道输出**两类接口，无反向控制通道 |
| R8 | 条款引用纪律：无出处不承诺 | 检索结果必须携带**原文编号**，且编号可被确定性校验（门 2） |

### 2.1 七层分层（与 [0.5]–[9] 运行时节点一一对应）

| L2 | 求解层 | [3] [3.5] | **纯代码**（排队论 / 四类分域模型） | 数字唯一来源 |
| L3 | 知识层 | [4] | 检索（embedding + rerank，本地） | 八库 + 评测集 |

### 2.2 选型三规则（沿用既有结论，不新立）

1. **能规则不 ML**——确定、可审计、零成本；
2. **实时闭环只用本地**——A 档业务一律船载；**云端永不进入 3 分钟闭环**；
3. **能小不大、能离线不联网**——只有非实时的长上下文/跨域任务才用云端大模型。

### 2.3 成本 · 速度 · 安全：三维选型口径

> 用户指定：写到"原则 + 量级区间"，不点具体型号与报价。下表的量级沿用 `ai-architecture-and-value.md` 四方案对比表（**演示级量级，正式值需原型实测标定**）。

| 维度 | 规则/确定性 | 本地小模型（0.5B–8B） | 本地中模型（7B–14B 量化） | 云端大模型（API） |
|---|---|---|---|---|
| **速度** | 毫秒级（<10ms） | 0.1–0.5s | 1–3s | 1–5s+，**卫星链路无可用 SLA** |
| **成本结构** | 边际≈0 | CAPEX（边缘硬件）+ 电耗，**边际≈0** | CAPEX 更高，边际≈0 | **OPEX 按 token**，随市场波动；无 CAPEX |
| **数据安全** | 数据不出船 | **数据不出船**、可完全离线审计 | 数据不出船 | **数据出船**；须逐条判定可出船范围 |
| **幻觉面** | 无 | 低（选择/填空，输出空间小） | 中 | 中–高（必须 RAG + 引用约束） |
| **可替换性** | — | 同构（同一 JSON Schema 契约） | 同构 | 需适配层；**换模型不改流程**是硬要求 |
| **适用环节** | 确定性计算、审批门、超时升级 | 分类、库外异常、话术、embedding/rerank | 影响推演、资源核算、方案组合 | 长文档/法规解析、跨域离线分析（C 档） |

**由此得到的三条成本结论（供答辩用）**：
- 本地方案的**固定成本高、边际成本≈0**——船队全航次反复推理时被摊薄，且不随事件数增长；
- 云端方案**边际成本线性增长**，但无 CAPEX——适合 C 档低频异步任务；
- 因此**"哪一档跑在哪"首先是成本结构问题，其次才是能力问题**——这与"实时闭环必须本地"的安全结论正好同向，不冲突。

**上下文窗口判断（沿用）**：实时链路各环节均为短输入，**4K–8K 足够**；只有离线长文档解析才需要长上下文。

### 2.4 第二轮讨论议题（技术侧）

## 3. 部署形态

> 沿用 `interface-map-and-ai-components.md` §1 与 `ai-architecture-and-value.md` 部署形态，不新增结论；此处只补**网段隔离**这一条技术落点（与 §4 沙箱配套）。

### 3.1 三层部署

| 层 | 位置 | 承载 |
|---|---|---|
| 船载边缘（必须） | 邮轮本地边缘节点 / 船载数据中心 | A 档全部：感知→分类→计算→推演→审批→触达，**不依赖卫星** |
| 岸基/云（可选） | 公司数据中心或云 | C 档：长文档解析、模型更新、远程审计；B 档的异步增强 |
| 卫星链路 | 外部传输 | **仅异步同步/远程支持**，不进实时闭环 |

### 3.2 三个网段的隔离（本档新增的技术口径）

```
[ 感知网段 ]──只读──▶[ 推理网段：模型 + RAG + 确定性内核 ]──提案(JSON)──▶[ 执行网段：编排器 + 代码门 + 端口适配器 ]──▶ 既有终端
        （外部/船方内部系统）        ▲                                              │
                                     └──────── 模型永不直连执行网段 ◀───────────────┘
```

- **模型所在网段与执行网段之间只有"提案"这一种单向信息流**（结构化 JSON），没有句柄、没有回调、没有共享通道——这是"模型没有执行工具"的网络级兑现；
- 靠港时可用陆地网络增强（同步、拉取），**但不得改变实时闭环的本地性**；
- 外部接口按 IACS 船载网络边界设计（PRD §8 安全一条）。

### 3.3 韧性 T0–T3 与部署的对应

| 档 | 触发 | 部署含义 |
|---|---|---|
| T0 | — | 全功能 |
| T1 | 外部（云/卫星/外部数据）不可用 | 熔断 + 缓存条款库；**本地链路不受影响**——这正是"实时闭环本地化"的收益 |
| T2 | 本地模型/部分感知不可用 | 模板回退、自动动作降为"建议 + 人工确认"、感知用上一快照并标注 |
| T3 | 断电/局域网/核心节点故障 | 人工预案；**审计不可降级**——恢复后补录 |

## 4. 模型/工具执行沙箱（安全边界）

> 用户指定口径：本节只谈**模型/工具执行沙箱**，即把"模型没有执行工具"从一句主张兑现成可检查的技术结构。

### 4.1 要解决的问题

"模型没有执行工具"如果只写在方案里，等于没有约束——真正要防的是四种越界：

| 越界 | 典型形态 | 后果 |
|---|---|---|
| 能力越界 | 模型被"顺手"赋予一个写接口 | 建议变成执行，审批门被绕过 |
| 数据越界 | 把全量乘客明细喂进模型上下文 | 隐私风险 + 数据出船风险 |
| 输出越界 | 模型自由生成未经 Schema 校验的内容 | 幻觉进入下游 |
| 追溯越界 | 越权调用没有留痕 | 审计链断裂 |

### 4.2 三重隔离 + 一道校验闸

| # | 机制 | 技术做法 |
|---|---|---|
| 1 | **能力隔离（工具面）** | 模型不持有任何执行句柄。所有工具调用经**工具代理（tool-proxy）**：按**节点静态声明能力白名单**（每个节点一份 JSON Schema），**只暴露只读工具与"提案"工具**（`propose_*`），不暴露任何写/执行工具；越权调用直接拒绝并留痕 |
| 2 | **数据隔离（输入面）** | 上下文最小化 + 脱敏：乘客数据以**群体切面或编号**进入模型（需要人群/语言适配时只给**人群标签**，不给个人标识）；🚫 不可得数据不喂；MOCK/REAL 显式分离（R6） |
| 3 | **网络隔离（运行面）** | 模型所在网段与执行网段物理/逻辑分离（§3.2），二者之间只有"提案"一种单向结构化信息流 |
| 4 | **输出校验闸（出口）** | 模型输出**必须过 JSON Schema / 模板槽位校验**才允许进入下一步；不通过 → 重试 → 降级为模板 → 转人工；推理附件另过**门 2 确定性校验**（引用编号真实存在、置信度在有效区间、公式可复算） |

### 4.3 与审批门、审计的关系（谁最终放行）

```
模型产出的"提案" ≠ 可执行动作
  提案 → 代码门（证据/置信度） → 人审（L1–L4 + 投放审核矩阵） → 编排器发起执行 → 端口适配器投放
                                                    ↑
                                        执行请求必须携带"人类签署凭证"
                                        （签署人 / 时间 / trace_id / 方案版本）
```

- **执行权在编排器（代码），签发权在人**：端口适配器只接受**带签署凭证**的执行请求，模型路径上不存在能构造该请求的通道；
- **幂等与可回滚**：执行请求以"幂等键 = 事件号 + 包号 + 方案版本"投递，失败可重试、可回滚；端口适配器**不提供删除/覆盖历史的能力**（append-only 语义）；
- **审计耦合**：沙箱的每一次拒绝、每一次校验失败都进 trace（G2），与推理附件（G3）、审批签署（C3.8）串成同一条链——**沙箱不是黑箱，它的拦截也是证据**。

### 4.4 沙箱在演示里怎么体现

- 架构图上画成 **"模型网段 ⇄ 提案通道 ⇄ 执行网段"** 的三段结构，审批门处画**断线 ⊥ + 人类签署**（与 `core-multi-agent-architecture.md` §4 一致）；
- 答辩一句话：**"我们不是靠提示词让模型别乱来，是靠它根本没有可乱来的通道。"**

### 4.5 第四轮讨论议题（沙箱侧）

1. 沙箱是否需要**演示级实现**（真做一个 tool-proxy + 白名单拒绝日志），还是图纸 + 日志样例即可？
2. 是否允许编排器在**无人在环**时执行 L1 自动类动作（如 A01 提示推送）？若允许，"签署凭证"由谁签发——系统代签（记录"L1 自动"）还是必须人工？
3. 沙箱的"越权拒绝日志"要不要作为作品集的一个证据点（类似坏例双轨）？
