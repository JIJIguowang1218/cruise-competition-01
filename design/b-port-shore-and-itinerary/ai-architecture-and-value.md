## 3. AI 价值判断与架构选型（修订版）

> 这一章回答两件事：**AI 在 B 线工程场景中的真正价值是什么**，以及**用哪种 AI 组织方式实现这些价值**。它不是“AI 帮忙写通知”，而是“AI 做人类做不快、做不全、做不一致的高并发判断与长链路调度建议”。

### 3.1 AI 在 B 线真正解决什么

| 工程价值 | 说明 | 对邮轮港岸/航变的具体含义 |
|---|---|---|
| **事件分类与态势判断** | 从多源信息中判断“发生了什么、严重吗、属于哪类事件” | 登离船滞留要区分：找不到路造成堵塞 / 乘客受伤 / 电梯扶梯故障 / 港口接驳中断 / 恶劣天气触发；不同类别对应不同资源、权限、预案 |
| **跨系统高并发整合** | 同时读港口、船期、天气、乘客清单、客服投诉、现场感知等，快速形成统一态势图 | 把“人工拼图 20–45 分钟”压缩成“分钟级局势图”：哪些区域拥堵、哪些人群受影响、哪些资源可调度 |
| **长链路推理与影响推演** | 基于当前事件推理后续影响：局部拥堵→疏散/改道→资源不足→是否需要更高权限介入 | 岸上事故时，AI 可快速给出“船上还没下船的人怎么调度、下船口怎么调整、接驳怎么分流、哪些人暂缓”的整体方案 |
| **方案组合而非方案编造** | 从事件库、策略库、条款库、历史预案中选择/组合已有策略，而不是现场发明方案 | 航变响应不是让 LLM 编一个赔偿方案，而是从“条款库+判例库+历史处理模板”中检索并组合出可审计的候选方案 |
| **证据与信度控制** | 每个判断给出依据、置信度、可选方案差异；低信度时主动转人工 | AI 可以回答“为什么判断是设施故障而不是受伤事件”：依据是哪路闸机数据、哪个摄像头、哪条工单记录 |
| **人机协同与权限分级** | AI 建议、人审批；高后果动作必须过代码级审批门 | 日常分流建议可自动；全量通知、赔偿执行、紧急响应必须由相应权限的人确认 |

### 3.2 证据线：为什么这些价值成立

- **证据线 A（旧模式基线）**：`design/evidence-line-a-baseline.md` 证明现状是人工拼图、逐批通知、口径不一致、信息延迟 3–4 小时；这正是 AI 高并发整合与长链路推理的发力点。
- **证据线 B（黑客松高分项目）**：
  - **CrowdPilot**：4-Agent 顺序流水线 `Forecast → Incident → Resource → Operation` 映射应急决策步骤，证明“先判断事件、再评估影响、再调度资源、最后生成行动”是有效的工程结构；
  - **FireGuard**：60 秒局势图 + 确定性威胁分 + what-if 重评，证明 AI 的价值是“把 20–45 分钟手工拼图压成 60 秒局势图”，而不是写文案；
  - **Globot Shield**：5 Agent 并行处理市场/物流/金融/合规 + 红蓝辩论，证明多 Agent 可以高并发读取多个系统并形成可辩驳的方案；
  - **Cassandra / AgentCI / Ripple**：Meta-Agent、自检、事故记忆，证明长链路 AI 需要“自我检查 + 回归验证”，不能只跑一次 prompt；
  - **StoreOps / DQ Sentinel / Mnemos**：证据抽屉、结构性审批门、只提案不执行，证明高后果场景必须让人审批、让证据可回溯。

### 3.3 AI 架构选型总览（认知层选型，非详细设计）

| 系统能力 | 建议技术形态 | 理由 |
|---|---|---|
| 事件分类/严重度判定 | 事件库 + 等级表 + 分类模型 + 规则复核 | 先判断类别再决定资源与权限；不能靠 LLM 自由发挥 |
| 跨系统信息并发读取 | API/事件适配器 + 并行编排（Workflow / 少量 Agent） | 高并发读取是工程能力，不是 LLM 生成能力 |
| 影响评估/时间窗/人数计算 | 确定性算法、规则引擎、排队论、仿真 | 数字必须可复现、可审计 |
| 方案组合 | 策略库 + 条款库 + 历史预案 + RAG 检索 | 从已有方案中选择/组合，避免编造 |
| 长链路计划生成 | 3–4 个职责单一的 Agent/模块串联：事件→影响→资源→方案→话术 | 每个环节独立输入输出，可回滚、可审计 |
| **推理附件生成（2026-08-18 新增）** | 方案生成模块后挂轻量"推理与证据链整理"组件（LLM 摘要 + 确定性校验） | 每个方案标配可展开详情；异常苗头提权为重点提醒；见 `event-governance-framework.md` §4.11 |
| 方案解释与多语言触达 | LLM 生成解释/话术（**下游表达层**） | 这是最后一步，不是 AI 的核心价值 |
| 自检与信度控制 | 独立审计/校验模块 + 确定性检查 | 防止 AI 自己给自己判作业；低信度转人工 |
| 客服/乘客问答（若做） | 意图识别 + RAG + 路由 | 查事实走 API、查条款走 RAG、投诉/紧急转人工 |

### 3.4 为什么不是“AI 只是聊天机器人”

把 AI 理解成“生成话术”会丢掉 B 线最核心的价值。B 线的 AI 价值是：

1. **并发**：同时处理港口、天气、船期、客服、现场感知等大量信息；
2. **推理链**：从事件分类→影响传播→资源调度→预案组合，形成完整决策链路；
3. **策略复用**：不是现场发明方案，而是从历史/条款/策略库中快速组合；
4. **可控执行**：给信度、给证据、给替代方案，再让人审批；
5. **一致性**：面对 5000 人、多种语言、多个渠道，AI 可以保持统一口径与统一调度逻辑。

语言生成只是这个链路最后输出的一部分，不能代表 AI 价值本身。

### 3.5 AI 使用边界

- AI 可以：分类事件、整合信息、推演影响、组合方案、生成话术、给出信度与证据、辅助客服分流。
- AI 不可以：直接算赔偿金额/时间窗、执行全量推送、决定最终方案、替代审批、编造未收录条款/预案。
- **AI 不可以：决定"是否发生航变"、发布航变预警（2026-09-04）**——航变预警与航变决定由外部体系负责（气象/海事发预警、船公司决定、船长安全确认）；AI 只推演**"已成立决定"之后**的影响链（登离船/接驳/时间窗/船员任务），并按 `event-governance-framework.md` §4.2.4 船长决策区判据路由审批。
- 所有高后果输出必须能回答三个问题：**依据了什么数据？用了什么规则/策略？谁批准执行？**

### 3.6 AI 不可替代性矩阵（2026-08-18 新增，回应用户"如果只是规则调用，旧系统也能做到"的质疑）

> 这是对全文最关键的审视：**逐环节问"换成规则引擎/传统系统行不行？"**。结论必须先立住：**一个纯规则系统（阈值触发 + 查表 + 模板）确实能覆盖我们 40% 的界面效果，但那不是产品，是装饰。** 我们与"旧系统 + 规则升级"的差异，全部集中在下面这张矩阵里。

| 环节 | 规则引擎/传统系统能做到什么 | AI 的不可替代增量 | 为什么规则不行 | B 线落点 |
|---|---|---|---|---|
| **非结构化信号理解** | 只能读结构化字段（数值>阈值） | 从**文本/语音/多来源描述**中判断"发生了什么"——客服投诉原文、现场口头描述、天气预警措辞 | 规则查不了"词没写进字典"的表达；语义模糊时规则直接哑火或误判 | M1 感知 → M4 事件分类（判断"拥堵"是找不到路/受伤/设备故障/恶劣天气，4 种处置完全不同） |
| **跨系统非结构化整合** | 能拼表，不能"读懂" | 把港口公告、广播、票务、客服信号、乘客 UGC **互相关联成一处局势图**，并发现"孤立看都不异常、合起来可疑"的弱组合 | 规则只能做字段级 join；"A 系统 3 条 + B 系统 2 条 + 时间接近"这类弱信号组合，规则无法表达 | M1 态势总览、库外异常识别（X 系列） |
| **长链路演绎推理** | 只能执行预写好的"如果-那么"链 | 对**未见过的组合**做多步推演：岸上事故 → 下船口调整 → 接驳分流 → 哪些人暂缓 → 时间窗连环更新 | 规则引擎的组合爆炸：预写所有分支不现实，漏掉一条就漏掉一次处置 | M4 航变响应影响推演、M2 登离船联动 |
| **非规则系统推理（开放域）** | 只能识别库内模式 | **发现库里没有的异常信号**——偏离常态但未收录,生成提醒卡并建议人关注 | 新事件一旦不在规则表里，规则系统"看不见"——这是封闭系统与开放系统的本质区别 | §4.11 库外异常识别（A18/A19） |
| **方案组合的"为什么"** | 能查表返回模板 | 从库中选择/组合后，**给出为什么选这个组合的逻辑论证**（推理附件），并能在人追问时解释 | 规则返回"模板 B"，但说不清"为什么是 B 不是 C"；评委/船员追问时无解释能力 | §4.11 推理附件、M5 建议卡片 |
| **多语言/多语境一致性** | 无法模板化 5000 人的个性化表达 | 同一决策翻译成不同语言、不同乘客群（老人/家庭/轮椅）的**一致但适配**的表述 | 规则模板固定，无法既统一口径又照顾人群差异 | M6 触达输出（话术生成） |
| **自检与信度校准** | 无自我评估能力 | 对自己的每个判断给出**置信度**；低信度主动转人工；推理链自检冲突时提权提醒 | 规则系统不知道自己"可能错了" | §4.11 提权机制、R11 低信度转人工 |

**由此得出三个"AI 高利益区间"（守住它们 = 守住产品）**：
1. **开放域异常发现**（§4.11）——纯规则系统物理上做不到，是我们区别于"旧系统 + 规则升级"的**头号卖点**；
2. **长链路推演 + 弱信号整合**（M4/M1）——把"人肉拼图 20–45 分钟"压成分钟级，是 V2 的直接兑现；
3. **推理附件/证据链（可解释性）**（§4.11）——"每个方案都能说清为什么"，规则系统天生不具备，是 V3 的直接兑现。

**反之，明确"AI 不背书的低值区间"（别在这些地方堆 AI）**：确定性计算（排队/时间窗/人数）必须纯代码；高后果执行必须走审批门与人工接管——这两处堆 AI 反而露怯。

> 答辩金句：**"我们不是用 AI 给规则引擎化妆，而是把系统立在规则引擎到不了的三块地上：看见没见过的、推演没写过的、解释说不清的。"**

### 3.7 推理附件模型的全系统推广（2026-08-18 新增，依用户意见 2 扩展）

> 用户问题："AI 证据链推理 + 附加推理附件的模型还能用在系统的哪些部分？"——答案是**所有 AI 参与的判断环节都标配推理附件**，不只是方案生成。推广清单：

| 环节 | 推理附件内容 | 主界面展示 | 详情附件可展开 |
|---|---|---|---|
| 事件分类（M4 步骤 1） | 为什么判为 E 系列哪一类、依据哪些信号、置信度 | 分类结果 + 置信度徽标 | 读到的信号清单 + 分类理由 |
| 影响推演（M4 步骤 2） | 为什么影响这批人、时间窗如何算出、哪些假设 | 影响摘要（人数/范围） | 计算输入 + 假设列表 |
| 方案组合（M4 步骤 4） | 为什么选 A03+A05、为什么不用方案 C | 方案卡 + 推荐理由 | 备选方案对比表 |
| 库外异常提醒（A18） | 为什么可疑、可能走向、建议观察项 | 风险横幅 + 高亮可疑环节 | 完整推理链 + 依据信号 |
| 客服问答（M4.5） | 答案依据的条款编号/时间线 | 答案 + 引用标记 | RAG 命中原文 |
| 审批决策（M5） | 给审批人的决策摘要：结论+证据+信度+替代 | 审批卡 | 完整证据链 + 签署所需材料 |
| 升级判定（R10 超时升级） | 为什么升级、超时多少、谁被通知 | 升级通知 | 时限计算 + 通知记录 |

> 统一原则：**推理附件是"判断的交付物"，不是附加品。** 每个 AI 判断 = 结论 + 置信度 + 推理附件（可展开）。这同时是 V3 可审计信任层的完整落地——不是"出事才查证据"，而是"每个判断自带理由"。

### 3.8 幻觉风险与兜底分层（2026-08-19 新增）

> 回应"AI 会不会胡说八道"：**幻觉不可根除，我们的设计是"流程兜底"而不是"模型兜底"**——不承诺模型不错，而是让每一条 AI 输出都能回答"依据了什么、置信度多少、谁复核"。

**幻觉的成因与 B 线的具体对策**：

| 成因 | 在 B 线的具体表现 | 现有对策（对照前文章节） |
|---|---|---|
| 知识截止 / 训练语料不含邮轮运营专有知识 | 编造"听起来合理"的条款、预案、赔偿口径 | 只检索已归档条款库/策略库（RAG），禁止无出处承诺（R8）；检索结果强制带条款原文编号或"待人工确认"标记 |
| 生成目标偏向"流利"而非"准确" | 方案组合时现场发明一个"像样的方案" | 方案只能从策略库/条款库/事故模式记忆库中选择组合（§3.3 方案组合、R8），模板槽位约束自由生成 |
| 上下文噪声 / 过载 | 长链路推理中途丢失关键信号（如漏掉"轮椅乘客"约束） | 职责单一 Agent/模块分步输入输出（§3.3），每一步独立可回滚；推理附件记录"读了哪些信号"（§3.7） |
| 采样随机性 | 同一输入不同时间输出不一致 | 确定性复核 + 置信度 + 低信度强制转人工（R11、§4.11） |
| 提示词歧义 / 语义模糊 | 事件分类判错类型（拥堵 vs 受伤） | 结构化 prompt + 事件分类库/等级表压缩类别空间 + 规则复核（§3.3 第一行） |

**分层兜底逻辑（答辩可展开的三层）**：

1. **RAG 给"事实锚"**：幻觉的机制之一是模型在无事实支撑处凭记忆平滑补全；RAG 检索原文并强制引用编号，等于把"凭记忆补全"替换为"基于原文作答"（参照 09b 挖掘的"逐字引用反幻觉"正模式：GitLab/Elastic/Dynatrace 三个 A 级项目的通用做法是"输出证据必须是工具输出原话，prompt 禁止改写"）。
2. **结构化约束缩输出空间**：JSON Schema / 模板槽位让模型在"选择和填空"里工作，而不是自由写作——输出空间越小，幻觉面越小。
3. **置信度 + 人工兜底收尾**：残余幻觉无法预测，所以每个 AI 判断都带置信度与推理附件；低信度转人工（R11），库外信号诚实标注"不在事件库内"（§4.11 异常提醒）。

> **答辩金句**："幻觉不可根除，所以我们不承诺模型不会错，而是把 AI 的错误成本从'一次错误的执行'降级为'一次多余的知会、一次更早的人工介入'"（错误成本结构沿用 §4.11.4：提醒只是多一双眼睛）。

### 3.8.1 幻觉兜底与系统运作的自检结果（2026-08-19 用户要求自检）

> 自检范围：把 §3.8 三层兜底逐条与我们真实系统运作对照——审批门（R3）、离线降级 T0–T3（§4.5）、人工接管与循环提醒（§4.12）、最新通过审计（§4.13）、库外异常识别（§4.11）、低信度转人工（R11）。**结论：无致命冲突，机制与各环节一致**；但有 4 处"边界需划清/风险需点名"，补如下，既防实现歧义也防评委追问。

1. **最高幻觉风险角 = 开放域异常发现（X 系列），需专门兜底**：它既是 AI 头号高地（§3.6），又是三层兜底覆盖最弱处——库外 → 层 1"RAG 事实锚"无库内原文可锚；开放域 → 层 2"结构化约束"无法把未知异常框进 JSON/模板。补救（与 §4.11.4 一致）：提醒卡一律用**"推测/建议观察"语气而非"断言"**，显式标注"不在事件库内"；风险等级仅供路由、**最终处置永远是人**；库外提醒置信度门槛**从严**（低于高阈值即仅提示转人工复核）。这是"错误成本 = 一次多余知会"的成立前提。
2. **"逐字引用"（层 1）与多语言/多人群适配（M6 话术）的边界要划清**：层 1"prompt 禁止改写"只约束**条款/事实引用**（原文 + 编号不可篡改，R8）；下行表达层（§3.3 话术生成）允许按语言/人群适配，但**不得改动被引用的条款原文与编号**。二者不冲突——隔离"引用原文"与"表达适配"即可，避免被读成"禁止改写 = 不能翻译"。
3. **推理附件自身也可能幻觉（LLM 解释 LLM）**：§3.7 附件由 LLM 生成，可能二次放大判断错误。缓冲：附件生成后过**确定性校验**（引用编号真实存在、置信度在有效范围、公式可复算、证据可回溯到 §4.13 trace_id），附件里的"为什么"是可核对的论证而非不可回溯的断言。
4. **与韧性降级 §4.5 对齐**：幻觉风险只在 AI 运行时存在——T2（本地 AI 不可用 → 模板回退）用确定性规则，无幻觉问题；T1（外部断）RAG 走**缓存条款库**，层 1 事实锚仍在。即：三层兜底是"AI 在线时的护栏"，不是离线系统依赖，避免误以为"RAG 离线就没兜底"。
5. **低信度转人工不得成为静默阻塞**："低信度转人工"应作为**优先复核队列**进入 §4.12.5 的循环提醒/超时升级节奏；尤其高频低信度事件（如批量通知后的同质询问）不能无限占用值班人力——转人工 ≠ 无人盯，超时仍按 §4.2 自动升级。

### 3.9 ML 范式与 B 线环节映射（2026-08-19 新增）

> 目的：**回答"我们用了什么机器学习方法、为什么不用别的方法"**。B 线不训练自研模型，本节是"范式 × 环节"的判断依据，不是教科书。

| B 线环节 | 所属范式 | 说明 / 为何这样选 |
|---|---|---|
| 事件分类与严重度判定（M4 步骤 1） | **有监督分类**（少样本/零样本 + 规则复核） | 事件分类库 30 类 + 等级表就是"标签体系"；分类模型 + 事件库/等级表 + 规则复核。用知识库缩小类别空间，不追求大模型单点精度 |
| **库外异常识别（X 系列，§4.11）** | **无监督异常检测** | 定义"常态"、偏离即可疑，无需预定义标签——这正是规则系统"看不见库外"的范式本质（§3.6 头号高地：开放域异常发现）。监督学习无法覆盖"没见过的事件"，所以这里天然是无监督思路 |
| 登离船/接驳短时客流预测（M2/M3，若进 Demo） | 有监督时序预测 | 07 调研 P7 有 CNN-Transformer 客流预测学术证据（景区场景近似）；若进 Demo 必须标定误差（MAE），否则不承诺准确值（诚实量化原则） |
| 长链路推演、方案组合、解释生成、多语言触达 | 生成式 LLM（预训练 + 指令对齐的产品） | 我们使用**现成对齐模型**（对齐正是 SFT/RLHF 的产物，常识口径见本节末补充注），不自训；推理侧成本按 token/算力计 |
| 确定性计算（排队/时间窗/影响人数） | **非 ML**（确定性算法/排队论） | 明确不归机器学习，R1 结构性保底 |
| 强化学习 | **不适用（显式结论）** | ① 审批门结构性禁止"自动试错"——RL 需要探索与奖励信号，高后果决策没有安全探索空间；② 航变/群体事件是低频高严重度事件，样本量不足以学习；③ 若未来做低风险场景的触达频控优化才可能涉及（仅预留口子，不承诺） |

> 一句话：**B 线只用"开箱即用"的 ML 能力——有监督分类、无监督异常检测、现成生成模型——并且只把它们放在规则引擎做不到的环节（§3.6 三高地）；需要自训、自探索的范式（自训 SFT/RLHF、RL）因数据、成本与安全性不适用。这不是能力问题，是产品决策。**

> 补充注（面试/答辩常识口径，不进入方案正文）：SFT（监督微调）用标注数据把通用模型对齐到任务领域，RLHF 用人类偏好反馈对齐"什么回答更符合期望"；两者成本集中在**训练侧**（数据标注人力、GPU 算力、多轮评测迭代，周期以周/月计），推理侧的延迟与成本主要由模型参数量、量化与部署硬件决定，与"是否微调过"关系很小。这也是"微调依赖稀缺的邮轮标注数据、周期赶不上航次事件时效"这一取舍的量化背景。

### 3.10 行业模式对照与模式选型（2026-09-15 新增）

> 回答三个必问题：**"你们这是不是多 Agent？""为什么不用 ReAct / 自主智能体？""行业到底有哪几种 agent 架构？"**
> 本节只做**模式选型**（产品层认知），具体框架产品的尽调见文末附录 A；一手来源与抓取快照归档于 `portfolio/research/agent-tech-selection-research-2026-09.md`。

#### 3.10.1 术语校准：Workflow 与 Agent；"八大类"不存在

- 据 Anthropic《Building Effective Agents》（2024-12-19，行业引用最多的模式文献）原文定义：**Workflow（工作流）= LLM 与工具按预定义的代码路径编排；Agent（自主智能体）= LLM 自己动态决定流程与工具使用**。该文给出 **5 种工作流**（提示链 Prompt Chaining / 路由 Routing / 并行 Parallelization / 编排者-工人 Orchestrator-Workers / 评估-优化 Evaluator-Optimizer）**+ 1 种自主智能体**。
- 多 Agent 拓扑各家官方口径不同：LangGraph 列 5 种（网状/主管/主管工具调用版/层级/自定义固定图），AutoGen 列 4 个团队预设 + 1 个实验性图工作流，微软 `ai-agents-for-beginners`（74.7k★，18 节课，多 agent 仅占 1 节）分集中式/去中心化/混合 3 类。**"主流八大类"无任何权威出处，对外不使用该说法。**
- 业界三条共识（均为官方原话级口径）：① 从最简单方案起步，"这可能意味着根本不构建 agentic 系统"，多数应用单次调用 + 检索 + 示例就够了；② 先把单 agent 的工具与提示优化到位，证实其力有不逮再升级多 agent（AutoGen）；③ Anthropic 自建多 agent 系统的实测：agent 约 **4 倍** token、多 agent 系统约 **15 倍**，且错误会复合累积、同输入路径不同使传统"给定 X 应走路径 Y"的评测失效。

#### 3.10.2 我们 [0.5]–[9] 每一段的模式归属

| 流水线段 | 技术形态（沿用 §3.3） | 行业模式归属 | 路径由谁决定 |
|---|---|---|---|
| [0.5] 前置决策支持 | 多源并行检索 + 单次 LLM 出多备选卡 | 并行-分段（Parallelization-Sectioning） | 代码 |
| [1] 接入适配器 | 纯工程代码 | 无 AI | — |
| [2] 分类 + 严重度 | 小模型分类 + 规则复核 | 路由模式里的"分类器"，**不是 agent**（类别空间被事件库锁死） | 代码 |
| [2.5] 库外异常 | 无监督异常检测 + 单次 LLM 提醒卡，只提醒不执行 | 无对应标准模式（自有高地，§3.6） | 代码 |
| [3] 确定性内核 | 纯算法/排队论 | 无 AI | — |
| [4] 知识检索 | 固定路径 RAG + 强制引用 | 标准 RAG（**非 agentic RAG**，检索路径不开放给模型） | 代码 |
| **[5] 方案推演** | 4 个单职责智能模块：事件→影响→资源→方案，每步 JSON 契约、可 gate、可回滚 | **提示链（Prompt Chaining）**；吸收 Plan-and-Execute"规划与执行分离"思想，但**规划权在产品、不在模型** | **代码焊死顺序，模型只填本步输出** |
| [5.5] 推理附件 | 单次 LLM 摘要 + **代码确定性校验** | 带程序化闸门的链路一步（不是评估-优化：裁判是代码硬规则，不是 LLM） | 代码 |
| [6] 信度门 | 规则裁决，低信度转人工队列 | 提示链中的程序化 gate | 代码 |
| [7] 审批门 | L1–L4 + 船长决策区 + 超时双路径 | Human-in-the-Loop 工作流中断 | 人 |
| [8] 执行触达 | 投放矩阵规则 + 槽位填充话术（条款原文不可改） | augmented LLM（单次调用 + 模板），表达层 | 代码 + 人 |
| [9] 审计 + 回流 | append-only 审计包；事故模式**人工审校后**回写 [4] | 组织学习（**不是 Reflexion**：不是模型失败后自我重试） | 代码 + 人 |

> **选型结论（V-2 主章论点，可直接上 PPT 的一句话）：全系统没有一个"模型自己决定下一步"的自主智能体。固定工作流承担全部确定性，模型的灵活性只开放在"读和想"；"写和发"全部是结构化提案 + 代码闸门 + 人审批。**
>
> [5] 的 4 个单职责智能模块，行业可以宽松地称为多 Agent 系统里**最确定的一种——固定拓扑、无自由交接**：顺序由代码焊死，模型不能临场改道，每个模块的输入输出是可回滚、可审计的结构化契约。这与证据线 B 的 **CrowdPilot 四节点顺序流水线（Forecast→Incident→Resource→Operation）** 是同一工程判断。

#### 3.10.3 为什么不用其他当红模式（评委追问储备）

| 模式 | 不采用的结构性理由 |
|---|---|
| **ReAct**（边推理边自行决定下一步工具） | 步数不可预测、错误逐轮复合、轨迹不可复算——与 3 分钟实时闭环的时延预算和审计要求直接冲突；我们的"想"和"做"被拆成固定节点，工具调用面更小 |
| **Orchestrator-Workers**（中心 LLM 动态拆任务） | 我们的子任务事先可枚举（影响/资源/方案就这几件事），动态拆解只引入"分解错了下游全偏"的不确定性，不换来收益 |
| **Evaluator-Optimizer**（LLM 生成、LLM 评估、循环精修） | 高后果方案不允许在线"生成-打回-再生"空转；我们的校验由代码按硬规则裁决（引用编号/置信度区间/公式复算），一次成稿、不通过则转人工 |
| **Reflexion**（失败后自我反思重试，不更新权重） | 高后果动作物理上不可试错；我们的学习机制是 [9] 事故模式库**离线、人工审校后**回写 [4]——节奏是"每个航次后组织学习"，不是"每次失败后模型重试" |
| **Network / Swarm 自由交接** | 谁交给谁由模型临场决定，则审计无法回答"为什么走这条路径"；去中心化交接直接排除 |
| **Agentic RAG**（模型自行决定检索几轮、检索什么） | 条款/策略检索路径固定可枚举，自由检索只会扩大编造面；[4] 固定检索 + 逐字引用编号（§3.8 层 1） |
| **Tree of Thoughts**（多路并行推理树搜索） | 调用量随分支指数增长，延迟与成本不可接受；论文场景（解谜）与实时高后果决策不匹配 |

## 部署与模型选型（初版）

### 部署形态

| 层级 | 部署位置 | 用途 |
|---|---|---|
| 本地边缘（船载） | 邮轮本地边缘节点/船载数据中心 | 实时闭环：事件分类、确定性计算、本地小模型、审批流、触达 |
| 云端/岸基（可选） | 云服务或公司数据中心 | 非实时任务：长文档解析、复杂方案离线优化、模型更新、远程审计 |
| 卫星链路 | 外部传输 | 仅异步同步/远程支持，不进入实时闭环 |

**许可证红线（船载商用前法务逐条确认）**：① Apache-2.0/MIT 可离线商用——Qwen3.5/3.8、Gemma 4（注意旧代 1–3 是自定义条款）、GLM-5、MiniCPM5、DeepSeek 权重与 R1 蒸馏、Phi-4（MIT）、Qwen3-Embedding；② 有附加条件——Llama 社区许可含 7 亿月活门槛、GLM-Edge 权重另附 Model License、Kimi K2.5 为修改版 MIT；③ 排除——Jina v4（CC-BY-NC 禁商用）。

**结构化输出口径**：2025–2026 各代模型普遍内建 JSON/工具调用能力，但严格 Schema 合规靠**推理框架的约束解码**（如 response_format=json_schema），不是裸生成保证。验收写"框架约束解码下的 Schema 合规率"，与 §3.8 层 2 对应。

### 四方案对比与量化口径（2026-08-19 新增）

> 回答"业务需求摆在面前，规则引擎 / 本地小模型 / 本地中模型 / 云端 API 怎么选"。延迟为 **2026-09-15 核验的公开实测区间（演示级量级，正式值需原型实测标定）**，硬件事实见下小节；token 价格随市场波动不承诺具体报价。

| 维度 | 规则引擎/确定性算法 | 本地小模型（0.5B–4B） | 本地中模型（4B–14B 量化，含思考档） | 云端大模型（API） |
|---|---|---|---|---|
| 单次延迟量级 | 毫秒级（<10ms） | **约 0.5–2s**（短 JSON 输出，Orin 级硬件；超低端 NPU 2s+） | **约 3–8s/节点**（短方案输出。实测生成速度：Orin Nano Super INT4 8B ≈19–22 t/s、AGX Orin W4A16 7B ≈42 / 13B ≈22 t/s；思考模型须设思考预算） | 1–5s+（含链路；卫星无统一 SLA，不能支撑实时闭环） |
| 全链路含义 | [3] 计算毫秒级 | [2][8] 各 1 次短调用 | **[5] 四节点链合计演示级约 10–30s**，仍在分钟级闭环预算内 | 不进闭环 |
| 吞吐/并发 | 高 | 中（多路并发需排队） | 低–中 | 高（按需扩容），但依赖网络 |
| 单次成本 | ≈0 | 电费 + 硬件折旧 | 同上（硬件更高） | 按 token 计费，随市场波动 |
| 离线能力 | 完全离线 | 完全离线 | 可离线（显存/算力要求高） | 海上不可实时依赖 |
| 幻觉风险 | 无 | 低（输出空间小：选择/填空） | 中（RAG + 结构化 + 置信度三约束） | 中–高（同三约束 + 数据不出船） |
| 适用环节 | [3] 确定性计算、[6][7] 闸门与超时升级 | [2] 分类、意图、[8] 话术、[4] embedding | [5] 方案组合/长链路推演（闭环内）；快档/深档双档 | 长文档/法规解析（岸基非实时异步） |

**边缘硬件现状（2026-09-15 核验，厂商标称另注）**：

| 硬件档 | 代表 | 算力/能力事实 | 对应模型档 |
|---|---|---|---|
| 低端 NPU | 树莓派 5 + AI HAT+（Hailo-8L/8，13/26 TOPS INT8） | 官方明确**不支持 LLM**；新一代 **AI HAT+ 2（Hailo-10H，40 TOPS INT4 + 独立 8GB）标称可跑约 6B**，无官方 t/s | 仅 ≤3B 试验级，不作主链路配置 |
| 低端 NPU（国产） | RK3588（6 TOPS NPU），rknn-llm 已支持 Qwen3/R1 蒸馏/Gemma | 第三方单机实测（参考级）：8B ≈3.7、3B ≈7、1.5B ≈11.5 t/s | 备份/极简配置 |
| 主力档 | **Jetson Orin Nano Super 67 TOPS / Orin NX 117–157 TOPS**（7–25W） | 实测 INT4：8B ≈19–22 t/s；NX 第三方 W4A16：7B ≈7.5 t/s | 分类/话术小模型 + 4B–9B 快档 |
| 高配档 | **AGX Orin 241–275 TOPS** | NVIDIA 实测 W4A16：7B ≈42.5、13B ≈22.2 t/s | 8B–14B 深档、[5] 主链路 |
| 下一代（已发售） | **Jetson AGX Thor T5000**（2025-08 GA，开发套件 $3,499；2070 TFLOPS FP4 sparse、128GB、40–130W） | 厂商标称 70B 级 W4A16 并发 8 达 41.5 t/s；8B/14B 绝对速度未核实 | 未来余量，当前方案不依赖 |

推理引擎生态（2026-09）：llama.cpp（128k★）、Ollama（181k★）、vLLM（92k★）均活跃；Jetson 侧官方路径为 vLLM + W4A16/NVFP4（jetson-containers 含 ollama/vllm/llama.cpp/TensorRT-EdgeLLM 包）；**INT4 量化已是默认档，W8A8 为 NPU 标配**。海事卫星实时性事实本轮未取得可引用来源，沿用既有判断（异步同步、不进实时闭环），不引用新数字。

**选型决策规则**：能规则就不 ML（确定、可审计、零成本）；需要语义理解且必须在实时闭环内 → 本地小模型；需要长链路推理且可在闭环内 → 4B–14B 量化模型（快档/深档双档，PoC 标定）；需要长上下文/跨域知识且非实时 → 云端异步。**云端永不进入 3 分钟实时闭环。**

**上下文窗口判断（2026-09 更新）**：B 线实时链路各环节 prompt 都是短输入——事件分类（事件特征 + 信号摘要）、检索（query + 片段）、方案组合（策略/条款片段 + 模板）、话术生成（几行文本），**需求侧仅需数 K**。供给侧 2026-09 端侧模型已普遍 128K–256K（Qwen3.5/3.8、Gemma 4 原生 256K/128K），**上下文在实时环节不构成选型约束**——选小模型的理由是时延、成本与确定性，不是窗口不够。长上下文（Qwen3.8/GLM-5.2 托管版 1M）只服务岸基离线长文档解析（法规/判例全文）。"小模型够用"的判据 = 输入长度 × 环节数量都在窗口内 + 无跨文档长程依赖。

**多模态能力边界**：B 线主场景是"结构化数据 + 文本信号"决策——摄像头只输出**计数**（R6 仅计数不识别，属 L1 物理感知层外部系统），天气/船期/客服信号均为文本/数值。**B 线 MVP 明确不需要图像理解、语音识别、红外等视觉/音频模型**；真正需要多模态感知的环节（落水检测、AI 无感登船）已在 `design/scope-and-boundary.md` L5 划为外部子系统，通过事件接口接入（`interface-map-and-ai-components.md` §1.2）。多模态在我们体系里是"接口属性"而非"模型需求"——这是显式的能力边界，不为炫技引入。
