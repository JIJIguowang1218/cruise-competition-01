## 1. 背景与问题（现状基线，来源：evidence-line-a-baseline.md）

5000 人级的邮轮是"资源固定、无法扩容"的封闭空间。餐饮高峰乘客到现场才知道要排队（自助餐"抢食"、热菜只有四个）；登离船靠叫号/广播，下船排队 3–4 小时、离船日 6–7 小时无水无餐；港口接驳信息是静态 PDF 手册，各港方案不一（免费/付费接驳、公交站 2km 外）；热门演出"去晚了抢不到座"；航变时客服逐批解释、口径不一，2026 年台风事件演变为群体拒下船。现有信息系统（预订/账单/预约）彼此割裂：改餐时间房卡不生效、账单数字不实时、热线占线。国际对照：机场已把实时等待时间做成产品、主题公园虚拟排队成熟、Virgin Voyages 已推虚拟餐饮排队——但**公开未见"实时感知→推荐分流"的端到端产品**。

## 2. 本期范围

**一句话：本期做一个 B 端"全船空间×时间调度决策层"——实时感知各空间占用 → 确定性计算资源状态 → AI 生成分流/预案建议 → 人审批后通过既有渠道触达。**

**非目标（明确不做）**：
- 不做 C 端乘客 App、船载屏/港口屏硬件终端（L4 只做接口与输出规范）；
- 不做消费引导/付费推荐（Q6=B，策略配置仅预留接口）；
- 不做落水检测、设备运维、能耗管理等专业子系统（作为外部事件源/扩展预留）；
- 不替代花城号已搭载的 AI 无感登船、智能客舱、智能机器人（边界划线，见 §5）。

## 3. 功能模块

> 初版各模块的"条件/状态、动作、系统行为"为**草稿逻辑**，待确认项见 §8；AI 规则遵循 V1（确定性计算保底）、V2（分钟级闭环）、V3（证据可审计）。

### M1 全船空间状态感知（L2 确定性层）【待讨论】

- **一句话**：把摄像头/传感器/预订系统数据变成"每个空间当前多少人、排队多久、还能进多少人"的确定性数字。
- **输入**：摄像头客流计数（V-Count/Outsight/海康类，仅计数不识别）、预订/POS 数据、登离船叫号进度、港口接驳状态（Demo 模拟）。
- **输出**：各空间满载率、排队人数、预计等待、剩余容量、趋势（当前值 + 短时预测）。
- **规则要点**：计数/等待/步行时间全部确定性算法（[待讨论] 精度要求与校准方式）；隐私按"仅计数不识别"法定论证（人脸识别司法解释）。
- **待确认**：感知精度阈值、数据源接入清单、预测时窗（3 分钟/10 分钟？）。

### M2 分流与推荐（L3，四大场景共用）【待讨论】

- **一句话**：在感知层之上，为"餐饮/登离船/港口/娱乐"四个场景生成"去哪儿、什么时候去、怎么去"的分流建议。
- **子场景**：
  - 餐饮：满载率超阈值 → 推荐替代餐厅（考虑口味/距离/等待）→ 分批触达；
  - 登离船：动态分时建议（替代固定叫号）→ 与港口接驳联动；
  - 港口：下船人流 → 交通方式分群 → 分时放行建议（数据 Demo 模拟）；
  - 娱乐：剧院/泳池/儿童俱乐部密度 → 替代活动建议（Q5 已拍板纳入 MVP）。
- **AI 角色**：LLM 只做三件事——把结构化数字翻译成人话话术、按乘客分群生成不同推荐理由、解释推荐依据（证据卡片）；**不做**计数/排队/时间窗计算。
- **关键机制**：分批去重（避免把所有人引导到同一处）；[待讨论] 推荐上限与冲突消解规则。
- **待确认**：分群维度（舱型/偏好/语言？）、触达时机、去重算法细节。

### M3 航变事件响应（事件模块，V2 主战场）【待讨论】

- **一句话**：航变/异常事件时，分钟级生成"事实→影响→方案→话术→审批任务"，人确认后统一触达。
- **流程**（三级审批，Q4 已拍板）：
  1. **自动**：确定性事实生成（变更内容/原因/时间窗）、影响评估（受影响乘客统计）、话术草稿（LLM）；
  2. **船员一键确认**：话术定稿、通知渠道选择、赔偿方案初稿；
  3. **正式审批**：赔偿执行、全量推送、航线变更正式通知。
- **规则依据**：条款/判例库（上海示范文本"台风须退赔"、维京合同结构、台湾法定应记载事项）作为确定性输入；LLM 只做话术与解释。
- **关键机制**：统一口径直达（解决"船司 16h vs OTA 2h vs 电话 30min"通知链衰减）；[待讨论] 群诉升级预案。
- **待确认**：与客服系统/OTA 的通知联动边界、话术模板库结构。

### M4 船员调度台（证据抽屉 + 审批）【待讨论】

- **一句话**：船员看到全船态势、每条建议的依据证据、并执行三级审批。
- **核心 UI 要素**（[待讨论] 界面布局）：
  - 全船热力总览（实时占用/趋势）；
  - 建议卡片（依据证据：如"餐厅 A 容量 380/当前 312/步行 4 分钟"）；
  - 审批队列（自动/确认/正式审批三级）；
  - 事件响应工作台（M3 的操作入口）。
- **关键机制**：证据抽屉（V3）——每个动作可回溯"读了哪条数据、算了什么公式、谁批准"；审计包导出。
- **待确认**：船员角色权限分级、告警阈值配置方式。

### M5 触达输出（L4 接口层）【待讨论】

- **一句话**：把批准后的建议/通知通过既有渠道输出（我们不建终端）。
- **输出渠道**：船公司既有乘客 App（Q1=A：输出标准接口，船司自行接入）、船载屏、船员端、广播/短信（紧急）。
- **输出物**：结构化建议 JSON（场景/目标空间/预计等待/话术/时间窗）+ 触发规则（何时推、给谁推、频控）。
- **Demo 边界**：静态/模拟视图展示"系统输出如何触达"，不进入产品范围（已拍板共识）。
- **待确认**：接口协议形态、推送频控与退订机制。

## 6. 非功能要求（初版，[待讨论] 细化）

- **性能**：感知→建议闭环 ≤3 分钟（船载局域网内，不依赖卫星）；[待讨论] 首字延迟指标。
- **离线**：船载边缘推理 + 本地小模型降级；卫星链路仅异步增强。
- **合规**：隐私（仅计数不识别+人脸识别司法解释）；船舶网络安全 IACS E26/E27 论证；条款/赔偿合规（航变模块）。
- **安全**：审批门代码级实现；审计日志不可篡改（[待讨论] 实现方式）。
