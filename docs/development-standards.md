## 0. 为什么需要这份规范

我们即将进入 DEMO 阶段——这是比赛加分项、也是我们公认的最大短板（对照报告：8 个高分项目全部"可跑"，我们尚无代码）。
不靠 SDD 的"实验室级复杂"，靠它**防失控**：规格写清楚→每次只改一件事→实现前先想好怎么测→每步留痕。这正好对冲 vibe coding"氛围编程"里最容易翻车的地方（AI 改一处崩一处、逻辑不可测、数据不诚实）。

---

## 1. 借鉴了什么、故意不借鉴什么

**采用（四件套 + 两条纪律）**：
1. **规格先行**：每个功能先写 `specify.md`（场景/用户/边界/交互/验收口径），它是唯一事实源，一次一个变化一个评审；
2. **设计 → 任务 → 测试 三层产物**：`design.md`（页面/组件/状态）→ `tasks.md`（可领取可验收任务）→ `test-scenarios.md`（由规格反驱动、可用于验收）；
3. **测试反驱动**：实现前先写用例（happy path / 边界 / 失败注入），实现后用其验收；
4. **每步留痕**：`progress.md` + 小步 git 提交（Mnemos 87 次提交 = 全库最高迭代分）。
5. **上下文管理（vibe coding 启发）**：把项目说明 + 本规范 + 交互说明 + Mock 说明喂给 AI 并写进 `AGENTS.md`，保证每次编码上下文一致；
6. **小步提交纪律**：每个阶段完成即提交，commit 用 `type(scope): 描述`（沿用仓库现有 `docs:`/`feat:` 风格）。

**故意不借鉴**：落地级 SDD 的完整斜杠命令体系、多人 PR 评审流、跨团队规格分发、企业级文档矩阵——本项目单人 + AI 结对、且外部数据（港口/监管/船司内部）公开不可得，代入那些只会拖慢节奏。我们要的强度是"**够严谨、不笨重**"。

## 2. 我们项目的 DEMO 工作流（四阶段，每阶段有可验收产物）

> 全局约定：所有 DEMO 交付物放 `prototypes/` 下；每个页面/场景先讲"交互说明"，再谈实现。

```
阶段A 规格(Spec)
  prototypes/specs/<场景>/specify.md
    - 场景一句话 / 目标用户（船长/值班/经理/乘客谁看谁操作）
    - 边界（管什么不管什么，引用 PRD §2.2）
    - 数据需求（真/模拟/不可得，三态标注）
    - 交互要点（入口、主流程、异常态）
    - 验收口径（能演示出什么、能测试什么）
        │
        ▼
阶段B 设计(Design)
  prototypes/specs/<场景>/design.md
    - 页面清单：每页"入口 / 主要控件 / 状态 / 跳转 / 异常态"
    - 数据模型：字段表 + 真/模拟/不可得标注
    - 事件流：感知→判断→方案→审批→触达的界面体现
        │
        ▼
阶段C 任务(Tasks)
  prototypes/specs/<场景>/tasks.md
    - 垂直切片：每个任务可独立验证（不一次性堆大功能）
    - 每任务：定义 / 验收点 / 依赖
        │
        ▼
阶段D 测试(Test)
  prototypes/specs/<场景>/test-scenarios.md
    - 正常路径（happy path）
    - 边界（低信度 / 库外异常 / 审批超时 / 离线降级）
    - 失败注入（断网、Mock 数据缺失、低置信度卡住）
    - 每条 = 前置 + 操作 + 预期 + 验收 checkbox
```

**阶段顺序不后置验收**：阶段 D 的用例在阶段 C 之前先写好**初版**（D 由 A 反驱动），实现时逐条勾。避免"做完才发现没测"。

## 4. 质量与"红线"（不可妥协，违规即返工）

1. **MOCK/REAL 显式分离**：可 mock **数据源**，不可 mock **核心逻辑**；每个字段标注真/模拟/不可得（R6）。
2. **诚实量化**：指标写"目标区间 + 待实测标定"，不写承诺值（§8.1 / B7）。
3. **AI 价值立场**：堆 AI 反而露怯——确定性计算用代码、高后果执行走审批门与人工接管；三高地（开放域异常/长链路推演/可解释性）是最低演示要求。
4. **答辩红线**：推理附件必露、审批与审计**演出来**而非讲出来、数据诚实标注（对照报告 §5.2）。
5. **低代价翻车自保**：每段 DEMO 设计 Plan B（该步失败怎么圆回来）。
6. **测试先行**：任何功能没有对应 test-scenarios 不算完成。

---

## 5. 与既有协作约定的衔接（角色分工不变）

- **用户**（产品负责人）：拍板**规格**（specify 的边界/交互/验收口径）、审**测试**、审**演示叙事**；不需要实现细节。
- **DSH agent**（实现者）：产出设计/任务/代码/测试，逐步向用户交验收产物。
- **重大决策**：agent 先给 2–3 选项 + 推荐，等用户拍板（沿用项目级约定）。
- **纵向流程**：出一个场景 → 用户审一次 → 通过再进下一场景；不一口气全做完再让用户看。

## 6. 下一步（审核通过后）

> **修正（2026-08-19 用户纠正）——UI 先行原则**：本规范的"规格/设计"对象是**完整可交互终端 UI（页面 × 功能 × 状态全集）**，不是"单个场景"。场景（台风应急/日常处置等）只是**展示切片**——从完整 UI 里选一段事件流来演示/录制，由 `demo-storyboard.md` 承载，位于 UI 设计与实现**之后**，不阻塞 UI 设计、不作为设计前提。相应地：开发顺序 = **完整页面功能规格 → 页面结构与视觉设计 → 实现完整功能模拟页面 → 展示切片与自动化脚本驱动**。

1. 定稿本规范（用户审核）；
2. **阶段 A（规格，UI 先行）**：`specify.md` 写**完整可交互终端的功能全集**——P1–P6 每页的完整功能、状态、数据字段（真/模拟/不可得）、交互规则（角色权限/响应/异常态），不依附单一场景；
3. 阶段 B `design.md`（页面结构 + UI 视觉，含**交互说明文档**），用户审；
4. 阶段 C 任务拆解 + 阶段 D 测试初版；
5. 实现完整功能模拟页面 → 逐条过测试 → 小步提交；
6. 展示切片（场景/分镜）+ 自动化脚本驱动 → 录制演示视频。
